# rubrics 质检（rubrics.json ↔ tests/rubrics.toml）

rubrics 是整题最容易被退回的一件：字段多、口径细、json 与 toml 两套写法还必须一致。
质检顺序固定为 **json 单条质量 → json 分布与覆盖 → 落到 toml 的写法 → 与题面/答案对齐**。

## 一、先跑门禁，再人工核

```bash
python scripts/validate_rubrics.py <task-dir>            # 条数/权重/分布/一致性/锚点
python scripts/check_rubric_style.py <task-dir> --strict # 措辞三要求 + 锚点待人工核
```

`validate_rubrics.py` 覆盖：json/toml 条数与正分池一致、negate 集合一致、标度唯一、
likert 锚点一致性、dimension 在固定清单内、内容质量占比、禁字符与换行、体量上限。
脚本没报 FAIL **不等于**判据可用——真实性、锚点出处、覆盖完整性都要人工判。

## 二·前、甲方人检口径：rubric 单条五准则

甲方人检 rubric 只按这五条判（《weakness&skill-人工质检内容》），本 skill 第二、三、五节
都是这五条的展开。写报告时按这五个词给结论，甲方能直接对号。

| 准则 | 甲方判什么 | 合格形态（人检报告原话） | 常见不合格 |
|---|---|---|---|
| **原子性** | 一条只聚焦一个模块或维度 | 「8 条各自聚焦一个模块或维度：R1 领域建模、R2 业务正确性…」；**同一件事的不同侧面不算捆绑**（reducer 的乱序/重复/冲突/授权/生命周期五项同属一条，判定合格） | 把多个独立要求塞进一条；或反过来把一步动作拆成一堆小项 |
| **客观性** | 描述可验证的代码/文本行为，无空洞主观词 | 「全部 8 条均为 Objective，描述可验证的代码行为…无空洞主观词」 | 「内容专业」「表达清晰」这类无法核验的表述 |
| **区分度** | 做对/做错清晰可判，不出现「部分满足与完全满足同分」 | binary 通过/不通过 + `negate` binary；Gradient 必须给出五档明确锚点（「四类全覆盖且每条有量化依据」→…→「缺失或全空泛」） | 档位之间没有可观察差异；正负样本同分 |
| **完整性** | 覆盖 instruction 的全部关键要求，不只堆在「能不能跑」 | 「8 条覆盖 instruction 全部关键要求…未只堆在「代码能不能跑」」 | 判据只覆盖格式/存在性，遗漏业务规则 |
| **鲁棒性** | 每条锚定具体交付物路径与具体行为，不同 judge 得一致判定 | 数值有容差（±0.005 / ≤1.5% / ≤3%），文本有关键词锚点或字段名锚点 | 只写「结果正确」，无路径、无容差、无锚点 |

两点容易判错，单独记：

1. **原子性 ≠ 一条只能有一个分句**。甲方明确认可「同一模块/同一状态机的多个侧面写进一条」；
   真正不合格的是把**互不相关**的独立要求合并（一个错就全丢）。
2. **条数与负分下限是领域相关的**。只有法律领域有明确依据（简单 25 / 中等 30 / 复杂 35）；
   金融、代码、skill 类目前未下发。实测：FIN1-skill-DEP-003 只有 8 条判据、1 条负分，
   甲方人检判「区分度 ✅ / 完整性 ✅ 合格」。非法律领域要报「该领域下限未下发」的 TBD，
   不要拿法律下限卡人（`validate_rubrics.py` 已按 domain 分流）。

## 二、单条质量（逐条过）

| 要求 | 合格标准 | 不合格形态 |
|---|---|---|
| 原子性 | 一条只查一个方面 | 一条里同时要求「表格齐全 + 数值正确 + 标注出处」，一个错就全丢 |
| 准确无歧义 | 不同评分者形成一致理解 | 「收入实现了明显增长」这种无锚点表述 |
| 客观可验证 | 优先核查事实、数据、结构、结果；必须主观时转成可观察标准 | 「排版美观」「内容专业」 |
| 粒度合理 | 不合并独立要求，也不把一步动作拆成一堆小项 | 把「文件名正确」拆成三条 |
| 明确打分对象 | 多交付物时写明针对哪个文件/片段 | 只写「报告」但题面有三个交付物 |
| 可独立判断 | 判断所需信息都在条目里 | 要评分者自己去查别的文件 |
| 来源合理 | 只来自题面显式要求、参考文件明确要求，或可合理推导的隐含要求 | 凭空增加「伪需求」 |
| 有判定锚点 | 用可核对的数值/名称/位置 | 「语言流畅」「结构清晰」 |
| 不双重计分 | 同一角度不同时写正分与负分，同一问题不重复计分 | 既给「引用规范」正分，又扣「未引用规范」 |

正反例：`收入实现了明显增长` → `收入同比增长 65%`；`PPT 排版美观` →
`单页正文不超过 150 字，文本无明显遮挡、重叠或溢出`。

## 三、措辞三要求（甲方中频退回项，`--strict` 会报 FAIL）

1. **陈述式**：先写应达到的结论与要求，不以「XX 是否 XX」提问式起头。
   提问式只点话题、不给判定锚点。例：`是否引用了规则原文` → `引用规则原文并写明条款编号`。
2. **档位量化**：不用「若干 / 个别 / 普遍 / 多数 / 一些 / 少量 / 大致 / 大约 / 酌情」等无定义量词，
   改「至少两项 / 三分之二以上 / 半数以上」。注意白名单：`全部或部分`、`部分使用`、`独立部分`
   属于规则原文说法，不算模糊量词。
3. **定位语贴合交付物形态**：法律题写「规则条款编号 / 协议条款序号 / 材料记载位置」，
   不要出现「可逐格复算（单元格、公式）」这类表格题模板用语；反之亦然。

另外：交付物本身即可核验的条目，`criterion_type` 写 `Objective`，不要随手写 `Subjective`。
脚本会把 `Subjective` 条目列成待确认项。

### 三·补、判据自身的三条禁令（甲方返修 #2 固化，2026-10-01）

| 禁令 | 不合格形态（真实退回实例） | 机器检查 |
|---|---|---|
| **description 不得重复给档位** | description 末写「按下列档位评分：1=…；0.75=…；0.5=…」，而 `levels` 又给一套——两套措辞还不一致 | `check_rubric_style.py`（json 层）；`validate_rubrics.py` 的「toml 中无旧 0–1 标度残留」「likert 锚点一致性」 |
| **levels 不得塞入与考点无关的样板句** | `levels["1"]` 追加「且须给出可逐格复算的定位（单元格、公式或条款级引用），仅文字承认不得分」 | `check_rubric_style.py` 的「含表格类定位语」 |
| **判据不得替题面兜底** | 描述里写「…是本任务明确要求的组成部分，不影响上述四部分的齐全性与顺序判定」 | `check_rubric_style.py` 的「替题面兜底的解释语」 |

三条的根因与整改动作不同，别混：

1. 前两条是**同一份档位被渲染两遍**。`gen_rubrics_toml.py` 会把 `levels` 渲染成
   「评分为 1–5 整数：5=…；4=…；3=…；2=…；1=…」，如果 description 里还留着旧的
   0–1 档位段，toml 里就出现两套标度（LAW-004 的 R04/R05/R06/R10/R19/R20、
   LAW-002 的 R04/R05/R06/R07/R10/R12/R20/R21/R22/R23 都是这个形态）。
   动作：**只保留 `levels`**，把 description 的档位段整段删掉；样板句直接从 `levels` 里删。
   改完必须重跑 `validate_rubrics.py`（它会报「旧 0–1 标度残留」与「levels 与描述档位段不一致」）。
2. 第三条是**题面缺陷的外溢**。题面写「必须包含以下四个部分、顺序一致」，实际列了五个
   组成部分（多一个「第X部分之后增加一段」），生产方不敢改题面，就在判据里写
   「不影响四部分的齐全性与顺序判定」把它按下去。动作：**回 `instruction.md` 把部分数
   与条目数对齐**，判据里只留判定标准（见 [instruction-qc.md](instruction-qc.md) 第一节 Q-T10）。

> 生成器会兜底删旧标度（`gen_rubrics_toml.py` 的 `strip_old_scale`），但**不要把兜底当整改**：
> json 里留着旧档位段，下一轮换工具重生成就会漏删，退回原形。质检要查的是 json 源头。

## 四、锚点可溯源（最高频的严重退回）

**判据里的口径、标准、门槛、数值，必须能在 `environment/input_files/` 的规则原文或材料记载中找到出处。**

- 内部邮件的口头说法、行业传闻、自造框架**不能**当**得分前提**。
  实例：把规则原文并不存在的「合并计算口径」写成算力门槛判据的得分前提，被人检判为
  「判据建立在规则原文不存在的法律标准之上」。
- 材料里出现的不可靠口径应转成**扣分项**（「直接沿用该口径」才扣分），不要当正分项的前提。
- `check_rubric_style.py` 的 NOTE 分两类：**引号里的口径短语**未命中（高优先人工核）、
  **数值**未命中（多为派生计算值或单位换算/格式差异，确认不是编造即可）。

## 五、weight 与分布

| 检查项 | 合格标准 |
|---|---|
| 取值 | `weight` 只能取 `{+10, +7, +3, -3, -7, -10}`，不能取其他值 |
| 关键项 | 每题至少 2 条 `+10` |
| 内容质量占比 | 内容质量维度（含全部二级标签）的正分合计 ≥ 全部正分的 30% |
| 权重梯次 | 不要用 `+3` 堆叠；关键结论/指令/规范给 10，重要补充依据/专业规范/论证理由给 7 |
| 负分项 | 数量与 `-10` 用法合理；`-10` 只用于重大专业错误、幻觉、业务安全、合规风险 |
| 双重计分 | 正负分不覆盖同一角度 |

维度只能取 11 个固定名之一（二级可为空）：
`指令遵循`、`内容质量-结论正确性`、`内容质量-数值与计算准确性`、`内容质量-专业规范`、
`内容质量-分析与论证质量`、`内容质量-事实忠实性`、`结构与组织`、`操作与交付安全`、
`安全合规`、`超预期贡献`、`视觉美感`。
自造维度名（如只写 `合规`）按**重要**报。

条数下限按领域与难度档：法律领域 简单 ≥25 / 中等 ≥30 / 复杂 ≥35。
低于下限按**阻断**报，补条时同步调整权重分布，别只堆 `+3`。

## 六、落到 tests/rubrics.toml 的写法（转换错了整题作废）

`rubrics.json` 是出题侧原始判据，Harbor 真正读的是 `tests/rubrics.toml`。用
`python scripts/gen_rubrics_toml.py <task-dir>` 生成，不要手写。

| json | toml | 说明 |
|---|---|---|
| `id` | `id` **且** `name` 与之逐字相同 | 只写 `id` 会让纯中文 description slugify 成空串，条目键塌缩、解析崩溃 |
| `type: Gradient` | `type = "likert"` + `points = 5` | 档位固定 5 档 |
| `type: Binary` | `type = "binary"` | — |
| `weight > 0` | `weight` 原值 | 只允许 3.0 / 7.0 / 10.0 |
| `weight < 0` | `negate = true` + `weight = abs(值)` | **绝不写负 weight** |

四个必须记住的坑：

1. **扣分项必须 `negate = true` + 正 weight**。写负 weight 会被平台判为异常条目并剔除，
   `verifier_error = 1`，整次评分作废；改写成「未违规则得分」会让扣分项进满分分母虚增基准。
   description 直接描述违规行为，不需要改写句式。
2. **likert 只允许一套标度**：description 里只能出现
   `评分为 1–5 整数：5=…；4=…；3=…；2=…；1=…。`
   同时留 0–1 与 1–5 两套标度会让判官输出小数被 schema（integer）拒掉或随机漂移。
   注意这一条在 toml 里才显形，**根因在 `rubrics.json`**：description 里留着
   「按下列档位评分：…」的旧段，生成时就会和 `levels` 渲染出的 1–5 段叠在一起。
   判定只认 toml 的最终形态，整改要动 json 源头（见第三节三·补）。
3. **`levels` 是锚点唯一来源**，映射固定 `1→5、0.75→4、0.5→3、0.25→2、0→1`；
   必须与条目设计意图一致（历史上出现过整体错位一档、最低档「未涉及」丢失）。
   Gradient 条目没有 `levels` 会得到一条只有引导语、没有档位的条目。**按阻断报。**
4. **`Deliverables to inspect:` 每条约一段、且不留空**。多段 → 判官误判；
   空路径 → 判官找不到交付物；结尾不要出现 `。。`、`。；` 这类重复标点。
   多交付物题目逐条写全该条涉及的交付物，不要只写目录。

## 七、跨件对齐

| 检查项 | 合格标准 | 等级 |
|---|---|---|
| Requirement Coverage | 题面的每条显式要求都有对应判据 | 有缺口 → 阻断 |
| 判据无凭空项 | 判据考的点题面必须写过或可合理推导 | 凭空项 → 重要 |
| 交付物并集覆盖 | 全部 criterion 的 `Deliverables to inspect:` 并集 = 题面全部交付物 | 有缺口 → 重要 |
| `metadata.scoring.s_max` | 顶层存在且等于正分池 | 缺失 → 阻断 |
| `tests/prompt.md` | rewardkit 模板原文：Material map / Reference-solution policy / Tool usage / **Fairness anchor** / `{criteria}` 都在 | 删锚点或自写评分宽严表述 → 重要 |
| 体量与字符 | 全文 LF、无 U+00A0 / U+3000；`prompt.md` + 全部 description < 100 KB | 超限 → 阻断 |
| Judge 配置 | `[judge]` 为 `claude-code` / `prompt.md` / `qwen3.7-plus` / `timeout=7200` / `weight=1.0` / `mode="individual"`；`[scoring] aggregation="weighted_mean"` | 供应商自行换裁判模型 → 重要 |

## 八、专项 / weakness 数据的差异

| 数据类型 | 附加要求 |
|---|---|
| 专项数据（skill / tool / workflow） | 判据要能区分「形式化调用了 Skill」与「真正用 Skill 改变了关键判断」——被形式化调用但没有改变关键判断的，应当被扣分 |
| weakness 数据 | 判据必须覆盖 trigger 的正确处理方式；只惩罚「没踩坑」或只认「绕开 trigger」都不成立 |

## 九、高频退回实例

- 扣分项没写成 `negate = true`（写成负 weight，或改写成「未违规得分」）。
- likert description 里 0–1 与 1–5 两套标度并存。
- 条数低于领域下限，补条时又只堆 `+3`。
- `levels` 与 description 档位段整体错位一档，或最低档「未涉及」在 levels 里丢了。
- `dimension` 自造（如 `compliance`、`合规`）。
- `rubrics.json` 顶层缺 `metadata.scoring.s_max`。
- 权重以 10/3 为主、`+7` 缺位。
- description 残留「按下列档位评分：」、重复句、空 `Deliverables to inspect: `。
- 判据措辞与题目领域不匹配（金融/表格用语写进法律题）。
- 裁判模型与参评模型同家族（供应商自行换了 judge）。
