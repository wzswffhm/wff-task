# 质检报告格式与结论口径

报告要能被三种人用：生产方照着改、第二个人照着复检、批量统计照着回填。
所以固定「结论 → 逐条问题（带证据与整改动作）→ 未覆盖项 → 待确认项」四段。

## 一、严重度与结论口径

| 严重度 | 含义 | 处理 |
|---|---|---|
| **阻断** | 必须整改，否则不能交付 | 机器门禁 FAIL、判据不可溯源、答案与题面不一致、hack、缺五件套 |
| **重要** | **可交付**；建议整改（不阻断交付） | 措辞不合规、字段缺失、继承漏项、命名不一致 |
| **提示** | 建议优化，可放行 | 可读性、结构、超预期改进 |
| **未验证** | 该核而没核成 | 单列，**不计入通过**；写明缺什么、由谁提供 |

**结论规则**：任一**阻断** → 不通过（打回）；仅**重要** → 有条件通过（**可交付**，重要项为建议整改项）；
仅**提示** → 通过。
三件套（题面 / 标准答案 / rubrics）分别给结论，再给总结论。存在**未验证**项时总结论最多写「有条件通过」。

> 口径提醒（2026-10-02 据本批实测固化）：本批 LAW-002 / LAW-004 交付文档只在「重要」级有项
> （题面部分数声明、判据措辞），**试标照样通过**；对照 `upstream-sync.md` 同批经验（fix1 里
> 措辞类残留未被退回），可见「重要」在甲方现行口径下不阻断交付。报告里必须把「能不能交」说清楚，
> 不要把建议项写成返修单：**只有「阻断」才是不能交**。

## 二·前、报告开头必须给的两句话

报告第一屏固定先写这两行，再写别的：

1. **结论**：通过 / 有条件通过（可交付） / 不通过（打回）
2. **是否需要重跑判分**：不需要 / 需要（标明**只重跑判官**还是**需重跑模型**，以及为什么）

判分重跑口径（据 2026-10 批次实测）：

- **不动判据与题面**（清残留、改打包权限、改元数据、补文档、删「参考答案自身也拿不到分且与题面冲突」的坏条目后按既有逐条明细离线重算）→ **不需要重跑**。
- **只改判据措辞/锚点**（题面与参考答案不变）→ 需要，但**只重跑判官**，模型产物沿用。
- **改题面或参考答案** → 需要重跑模型；若改的只是「部分数声明」这类不改变交付要求的表述，
  实务上可按「只重跑判官」处理，但必须在交付文档写明理由。
- **删掉的是支撑难度的判据** → 需要重跑并**重新定档**（先算一遍剔除后的均值，破 <0.7 要提前警示）。

## 二、每条问题必须写齐四要素

| 要素 | 要求 | 反例 |
|---|---|---|
| 位置 | 文件 + 条目号/段落名 | 「rubrics 里有问题」 |
| 证据 | 原文引用（截断到能定位） | 「描述不清楚」 |
| 判定依据 | 引规范原句或本 skill 的检查项 | 「不符合规范」 |
| 整改动作 + 复检方式 | 具体改什么、改完怎么验 | 「请优化」 |


## 四、批量报告与回填

批量质检时，除单题报告外再给一张汇总表，便于回填到任务表/多维表格：

| 字段 | 取值 |
|---|---|
| `task_id` | 题目编号 |
| `verdict` | `通过` / `有条件通过` / `不通过` |
| `blocking_count` / `important_count` | 数字 |
| `blocking_items` | 阻断问题的简短清单（分号分隔） |
| `unverified` | 未验证项（分号分隔，无则空） |
| `checked_at` | 质检时间 |

`qc_check.py` 写出的 `qc_machine_report.json` 已含 `machine_summary`，可直接作为该表的机器部分底稿；
人工结论补在同一目录的 `qc_report.md` 里，不要写进题包目录（会污染交付包）。

## 五、已知冲突与默认口径（质检时按此判定，不确定就标 TBD）

| # | 问题 | 默认口径 |
|---|---|---|
| 1 | 14 种 weakness 完整词表 | 以算法侧正式词表为唯一来源；规范正文的 `["W07-流程跳步","W12-约束遵循"]` 是占位示例，照抄即错 |
| 2 | A1 难度区间 | 主方案写 `60% ≤ 得分 < 70%`，Guideline 只写 `< 70%`，取更严格的 60%–70% |
| 3 | 每领域题量与领域数量 | 按文档数字理解，7 领域均分方案待确认 |
| 4 | 三级/四级标签知识体系 | 表未下发时按细分场景填并标来源，到位后回填 |
| 5 | 打分项计分公式（负分项在分母中的处理） | 与 rewardkit 规范核对后再落盘 |
| 6 | json 字段与 rewardkit 配置的映射、大小写口径 | 以 rewardkit 交付规范为准 |
| 7 | `environment_template` 模板名 | 向平台索取，缺失标 `TBD` |
| 8 | 参考答案阈值符号 | 取 `≥ 0.85` 为下限，`> 0.85` 为目标 |
| 9 | rewardkit 与主方案冲突 | 一律以 rewardkit 为准，并把差异记入本表 |

「不臆造清单」：weakness 词表与编号、知识体系表、环境模板名、judge 网关与 key、
