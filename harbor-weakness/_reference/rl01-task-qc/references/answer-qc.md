# 标准答案质检（参考答案 / golden output）

标准答案在题包里由三部分构成，质检要一起看：

| 载体 | 路径 | 作用 |
|---|---|---|
| 交付物本体 | `solution/golden_output/` | 参考答案的实际内容，判分基准 |
| 生成脚本 | `solution/solve.sh` | oracle 跑分入口，必须能在 env 镜像里重放出交付物 |
| 判官侧副本 | `tests/__golden_output/` | 判分链路读到的副本，必须与交付物本体逐字节一致 |

## 一·前、甲方人检口径：solution 只判「答案业务正确性」

甲方人检对标准答案只给一个结论：**答案业务正确性**（另外两项是 instruction 真实性与
rubric 五准则）。核法是把参考答案的每个关键数值/结论**回算到输入数据与权威规则**，
逐项写「数值 → 来源 → 是否一致」。人检报告里「正确部分（已逐条核对 Skill 规则与输入数据）」
下面的一串编号条目就是这个形态——质检报告照这个写，别只写「答案正确」。

两个必查的坑：

1. **LIVE 参数 vs 草稿/干扰材料参数**。真实案例：golden 用 live 汇率 USD=7.18 / EUR=7.88
   （而不是备忘里的 7.00/7.50）、净债务 168,000,000（而不是年报的 150,000,000）。
   参考答案必须走权威来源，用草稿口径就是业务错误——同时要看判据有没有把这件事设成负分项。
2. **多步计算链要逐步复算**，不能只对最终值。真实案例的核法：
   EBITDA `1,200,000,000 × 0.155 × (1-0.14) - 32,000,000 = 127,960,000` →
   peer 双门槛筛选（四家只过两家）→ 倍数取 min（≈5.71 而非中位数）→
   EV 链（折价 12% → 后置调整 -42,000,000）→ 股权价值减净债务。
   任一步用了错误口径，最终值可能仍然「看起来合理」。

## 一、一致性（机械可查，`check_task_qc.py` 覆盖前四项）

| # | 检查项 | 合格标准 | 不合格 → 等级 |
|---|---|---|---|
| 1 | 齐全 | `solution/golden_output/` 里的文件与题面声明的交付物集合一致 | 缺文件 / 多文件 → 阻断 / 提示 |
| 2 | 命名逐字节一致 | 与 `instruction.md`、`artifacts`、`[[metadata.deliverables]]` 完全同名 | 差一个字 → 阻断 |
| 3 | 两份副本一致 | `tests/__golden_output/` 与 `solution/golden_output/` 内容相同 | 不一致 → 阻断 |
| 4 | 格式可打开 | 声明的格式确实成立（.docx 能打开、.xlsx 有工作表、.md 有正文） | 空壳 / 损坏 → 阻断 |
| 5 | 脚本可跑 | `solve.sh` 为 LF + 0755，且可复现出同一份交付物 | CRLF / 无可执行位 → 阻断 |
| 6 | 不泄题 | Dockerfile 里不得 `COPY solution/` 或 `tests/` | 出现 → 阻断（Agent 能读到答案） |

## 二、与题面逐条对齐（人工，最核心）

把题面的「产出要求」拆成条目，逐条在参考答案里找落点：

- **类型/文件名/数量**：题面说 3 个交付物就只能是 3 个，不能合并成 1 个。
- **必须包含的模块**：如「报告含公司概况…投资建议」共 11 节，逐节确认存在且顺序一致。
- **数量与精度**：字数区间、小数位、单位、时间范围，与题面写的完全一致。
- **禁止项**：题面禁止的做法（如不得改动输入文件、不得使用某格式）参考答案里不能出现。

**答案与题面对不上，是双重问题**：参考答案不达标，且说明题面或判据至少一处写错了。
报告里要同时指出两侧，不要只写「答案不符」。

## 三、与判据对齐（oracle 得分是硬门槛）

1. **逐条对照正分项**：每一条正分项，参考答案是否明确命中。命中不了就是判据过严或答案不全。
2. **逐条对照 negate 项**：参考答案不得命中任何 `negate = true` 条目。
3. **跑 oracle**：`harbor run -p <task-dir> -a oracle`，参考解得分 **须 > 0.85**（下限 ≥ 0.85）。
   - 得分 ≤ 0.85：判据与参考答案不一致，按**阻断**报，并指出是哪些条目没拿满。
   - `criteria_counted = 0` / `verifier_error = 1`：判分链路挂了，不是得分低，先修链路。
4. **判据是否只认一种写法**：如果题面允许多种合理做法，而判据只认参考答案那一种，
   这是「判据过窄」，会让正确作答被判错——按**重要**报（影响三模型均值可信度）。

改动参考答案后必须重跑判分，否则交付的逐条判分记录与判据对不上。

## 四、专业正确性（人工，脚本查不了）

抽样核对（至少覆盖每个交付物的 3 个关键结论/数值，多交付物逐份抽）：

| 维度 | 怎么核 | 不合格形态 |
|---|---|---|
| 数值与计算 | 挑关键数值回算：口径、分母、时间范围、单位换算、精度 | 用错统计口径、跨期混算、单位差 10000 倍 |
| 结论正确性 | 结论与材料证据是否一致，有无方向错误 | 材料是净流出，答案写净流入 |
| 专业规范 | 是否符合所属行业/领域的规则与通行做法 | 引用不存在的法规条款、政策口径 |
| 事实忠实性 | 引用与来源是否真实可追溯，跨文件是否区分主体/版本/时点 | 把 A 公司数据挂到 B 公司名下 |
| 依据可溯源 | 答案里的口径/门槛/数值能否在 `environment/input_files/` 找到出处 | 依据来自「内部邮件口头说法」这类不可靠来源 |
| 不依赖未提供信息 | 答案里有没有用到题面与环境里都没有的数据 | 凭空出现外部市场数据并作为核心依据 |

数值回算优先用脚本辅助：判据里的关键数值可用
`python scripts/check_rubric_style.py <task-dir>` 的材料比对结果，检查「未在 input_files 命中」的项——
命中不了的数值要人工确认是「派生计算值」还是「编造」。

## 五、weakness 题的额外要求

- 参考答案必须走**正确分支**：trigger 仍然存在，但正确解法不被诱发失败。
  如果参考答案是「绕开 trigger」而不是「正确处理 trigger」，说明埋点设计有问题（重要）。
- 参考答案要能在正确的状态下通过全部正分项——用它反证 trigger 不必然导致失败，
  否则整题变死题（所有执行体都拿不到分）。

## 六、高频退回实例

- `solution/golden_output/` 与 `tests/__golden_output/` 少同步了一个文件，判官找不到交付物。
- 题面写了字数 3500–6500，参考答案只有 2100 字，oracle 分数被 likert 扣到 0.7。
- 参考答案把三个交付物合成一个 docx，判据按三个交付物打分，必然丢分。
- 参考答案用了材料里没有的行业数据，判据把它写成得分前提 → 锚点不可溯源。
- `solve.sh` 在 Windows 上写成了 CRLF，容器里 `bash` 直接报错，oracle 跑分为 0。
