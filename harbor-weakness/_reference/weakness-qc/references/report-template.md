# 报告模板、结论口径与重跑决策

## 一、结论口径（三档，唯一）

| 档位 | 触发条件 | 结论写法 |
|---|---|---|
| **必须整改** | 元数据/判据/打包硬性不合规；判据锚点在材料里找不到唯一出处；材料自相矛盾导致判据不成立；题面/材料变更后未重跑对应环节 | 不通过（打回） |
| **提示** | 不影响验收的问题：归档习惯、白名单外的取证文件、区分度偏弱、文档缺项、可选加固 | 通过（附优化建议），每条**必须写"不构成退回理由"** |
| **已核实通过** | 门禁 PASS、判分可复算、独立重算一致、结构与打包合规 | 通过 |

判定顺序：先看有没有**必须整改**；没有再看**提示**；两者都没有＝通过。
**默认倾向通过**——只在问题真正影响交付可用性、可复算性、合规性或难度证据有效性时才进"必须整改"。

## 二、报告骨架（一题一份 md）

```markdown
# <题目编号> 质检报告

| 项目 | 内容 |
|---|---|
| 题目 / 批次目录 / 版本 | … |
| 申报难度 · 复杂度 / 判据条数 | … |
| 参考解 / 三模型实测 / 均值·档位 | … |
| 质检方式 / 日期 | 门禁脚本 + 判分复算 + 独立重算 + 结构与安全检查 |
| **质检结论** | **通过** 或 **不通过：仅 N 项必须整改（…）；其余全项核实通过** |

## 一、结论
（一句话说清：能不能交；不能交的唯一原因是什么；其余是否全部通过。）

## 二、必须整改（逐项）
### <编号> <一句话标题>
- **证据三件套**：位置（文件 + 条目号）／原文引用／判定依据（引规范或材料原句）
- **影响面**：受影响判据 + 权重合计 ÷ 正分池 = 占比
- **整改动作**：可选项 + 各自代价
- **是否需要重跑**：明确写"不用跑 / 只跑判官 / 跑 agent + 判官"
- **难度风险**：修正后均值预计如何变化、会不会破档

## 三、提示（不影响验收，均不构成退回理由）
（逐条一句现象 + 一句建议 + "不构成退回理由"。没有就不写这节。）

## 四、已核实通过项
### 门禁与结构（表）
### 判分与算术
- 判分自洽：逐条复算与 reward.json 完全一致；description/weight 与现行判据逐条一致
- 独立复算：<对照表：复核点 / 材料出处 / 我的复算 / 金标 / 结论>
- 难度：参考解、均值、档位、非死题

## 五、重跑影响说明（表）

## 六、质检边界
（覆盖了什么；未覆盖什么、为什么、由谁补：如金标排版观感、prompt.md 与权威模板的字节一致性、
标签体系对齐、批次级配额等。）
```

**落盘规则**：

- 一题一个文件，文件名 `<题目编号>_质检报告.md`；
- 写到用户可见的 `outputs/`，**不要写进题包目录**（会污染交付包）；
- 多题时不要合并成一份（除非用户明确要求），合并版容易在返修时同步漏掉。

## 三、报告语气（甲方与生产方都要看得下去）

- **结论先行**：第一屏就要能看到"能不能交、为什么"。
- **不鸡蛋里挑骨头**：不影响验收的写法差异、可优化的地方，一律进"提示"并注明不构成退回理由。
- **不许把未验证写成通过**：跑不了判分、缺产物、拿不到规范原文，标 `未验证`/`TBD` 并单列。
- **每条问题必须可执行**：给出具体改哪个文件、改哪一句、改完跑哪个脚本。

## 四、重跑决策与命令

| 改动内容 | agent | 判官 | 难度档 |
|---|---|---|---|
| `task.toml` 元数据（复杂度档/weakness_tag/难度/标签）、`.md` 文档、证据文件移到 `轨迹/` 下 | 不用 | 不用 | 不变 |
| 判据 description / 权重 / 金标数值 | 不用（产物沿用） | **重跑** | 可能变，按新均值回填 |
| `instruction.md` 或 `environment/input_files/` | **重跑三执行体** | **重跑** | **重定** |

重跑判官（复用题包 env 镜像，四执行体并行；25 条约 40 分钟、51 条约 1–2 小时）：

```bash
# 0) 先清代理，否则容器内请求会走不存在的代理
#    Windows: 置空 HTTP_PROXY / HTTPS_PROXY / ALL_PROXY；Linux/macOS: unset 同名变量
# 1) 凭据写成文件传入，不要写进题包
#    judge.env 内容形如：JUDGE_API_KEY=…  JUDGE_BASE_URL=…
# 2) 镜像复用题包 env 镜像（docker images 里 <题号小写>__<hash>__env-main:latest）
python "$S/weakness-data-construction/scripts/rejudge_by_docker.py" <task-dir> <镜像> \
  oracle=<task>/solution/golden_output \
  gpt=<runs>/gpt-5.6-sol/output \
  opus=<runs>/claude-opus-4-8/output \
  qwen=<runs>/qwen3.8-max-0902/output --creds judge.env
```

**两个必踩的坑**：

1. `tests/test.sh` 一启动就会写一份 fail-closed 占位 `reward.json`（`criteria_counted=0`、
   `verifier_error=1`），**不能用"文件存在"判断跑完**；完成判据是 `criteria_counted > 0` 且
   `verifier_error = 0`，或 `reward-details.json` 已生成。
2. 判分会往挂载的 `tests/` 写 `__pycache__`，**打包前必须清掉**。

重跑后要同步的地方：四份 `reward*.json`（覆盖回 `跑分产物与轨迹/<题目>/<执行体>/`）→
`交付文档.md` 批次内容表（参考分/三模型分/均值/难度档）→ `task.toml` 的 `difficulty`/`keywords`/`tags`
→ 证据目录 README 的"未通过考点"表（PE 类题包还可能有生产者聚合的 `scores.json`）。

**分数变化要先预估**：若判据修正会让模型答案从判错变判对，按「该组权重 ÷ 正分池」估算涨分，
并对照 0.7 门槛判断档位是否会失效——破档就意味着要补难度，而不是简单重跑。
