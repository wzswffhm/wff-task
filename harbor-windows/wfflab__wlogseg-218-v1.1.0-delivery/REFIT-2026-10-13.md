## 1. 逐条闭环

### R1｜流式测试引入未声明的 8192 字节读块阈值
对应甲方要求：**第 1 条「性能 / 流式类断言不得固定魔法阈值」**；手册 QD-SP-02、VV-02、VV-03。

**缺陷**：`tests/test_wlogseg_semantics.py::test_iter_segments_is_streaming` 写过
`assert reader.max_request <= 8192`，并用 `bytes_read < len(blob) // 4`。题面 F 节只
要求「惰性 + 用带长度的 `read(n)` + 尾部校验」，**未声明任何缓冲大小**：合法的
64 KiB 定长缓冲会被误杀，而「先吐第一条、随后一次性读完剩余」的伪流式实现可能
因为只看第一条而漏过。

| 专家步骤 | 处置 |
| --- | --- |
| ① 依据公开契约设计随输入规模增长的观测，不私自固定块大小 | **删除 `max_request <= 8192`**。改为规模对照：构造总长约 120 KB 与 960 KB 的两个容器（同构段集合，只是段数不同），断言「取到第一条段之前」的累计读取量满足 `big.bytes_read <= small.bytes_read + 65536`——窗口不得随容器规模线性增长；**不再指定任何具体缓冲大小**，128 B 与 128 KiB 的实现都能通过。 |
| ② 完整消费迭代器，检查中途与末尾阶段 | 新增 `test_iter_segments_consumes_every_segment_and_the_tail`：对 400 条段**完整消费**，逐条比对；断言读完时 `bytes_read == len(blob)`（不允许跳过索引区或尾部）；再翻转尾部校验和的最后一个字节，确认完整迭代到末尾时抛 `WSegError(kind="checksum")`。 |
| ③ 尾部 CRC 错误 + 阈值依据 | 同上新增用例承担「先产出全部段、再报尾部校验和」的断言；阈值依据全部来自公开契约（题面 F 节），新断言的每一条都能回到题面文字。 |

**验收对照**（本机实测，`pytest 8.3.5`）：

| 控制 | 结果 |
| --- | --- |
| Golden（`solution/reference/wlogseg`） | **25/25 PASS** |
| no-change（原始 workspace） | **17 FAIL / 8 PASS** → 二值门禁 0 |
| 参考实现 `_CHUNK = 8192` | 照常通过（未再绑定块大小） |

**涉及文件**：`verifier/tests/test_wlogseg_semantics.py`、`tests/run_tests.ps1`、
`tests/required_testcases.json`、`tests/rubric.json`、`tests/judge.toml`、
`verifier/rubric.conditions.json`。

新增 required：`f2p-iter-segments-consumes-every-segment-and-the-tail`，
required 由 25 → **26**（F2P 17 → 18 / P2P 8），rubric `streaming` 项 test_ids 同步
收纳，`run_tests.ps1` 的 `$slugByFunction` 同步映射
`test_iter_segments_consumes_every_segment_and_the_tail → iter-segments-consumes-every-segment-and-the-tail`。

### R6｜公开测试与隐藏验收必须分层，并给出负访问证明
对应甲方要求：**第 6 条「公开测试与隐藏验收必须分层」**；手册 QD-IN-02、QD-IN-06。

**缺陷（本轮最实质的一条）**：v1.0.0 的 `run_tests.ps1` 解析顺序是
`… → <任务根>\tests → <任务根>\tests\verifier → C:\verifier\…`，也就是**按路径拼接
隐式命中包内 `tests/`**，而且把候选工作区放了进来。候选改写
`environment/workspace/tests/` 下的同名文件，就可能让判分取材落到自己手里。v1.0.0
也没有任何负访问证据，无法证明隐藏材料不可达。

**处置**（先弄清平台的投放契约再改，避免改成"谁也拿不到套件"）：

实测 Harbor 的 Windows 通道：`EnvironmentPaths.tests_dir = C:/tests`，
**Harbor 在跑 `tests/test.ps1` 之前把包根 `tests/` 目录整体复制到容器内 `C:\tests`**；
`C:\verifier` 是另一条判分侧注入通道。也就是说：**套件必须在包根 `tests/` 里放一份**，
这是平台的明文契约，不是可选项。我第一次整改时把包内副本删掉、只留
`verifier/tests/`，控制组立刻以
`INVALID: the verifier-side hidden semantic suite was not injected` 失败——这条失败
记录本身就是"平台通道只有 `C:\tests`"的实测证据。

据此定稿的处置：

1. 包根 `tests/test_wlogseg_semantics.py` **保留**为平台投放副本，并与判分侧正本
   `verifier/tests/test_wlogseg_semantics.py` **逐字节一致**（sha256 对账，由探针
   第 5 项与 `logs/local_checks.py` 双重检查）；
2. `run_tests.ps1` 的 `$verifierCandidates` 改为
   `-VerifierRoot` → 环境变量 → `C:\verifier\wfflab__wlogseg-218` → `C:\verifier`
   → **`C:\tests`（显式声明的只读平台通道）** → 包内平级
   `outside_harbor-verifier\…`（仅本地复现、不进容器）。
   **候选工作区与 `<任务根>\tests` 彻底不在列表内**——判分取材不可被候选篡改；
3. 新增 `verifier/ISOLATION.md`：先写清平台投放机制（§0），再列三类材料的目录、
   容器内位置、用途与作答期权限，并说明"为什么进了 `tests/` 仍满足隔离要求"；
4. 新增 `verifier/negative_access_probe.ps1`：以 agent 同身份只读探针，7 项断言
   （可见树无 withheld 命名 / 无隐藏符号与样本期望值泄漏 / `C:\verifier`、
   `C:\solution` 不在 workspace 内 / 判分侧必需材料存在 / **平台投放副本存在且与
   正本 sha256 相同** / **解析顺序不含 workspace 与任务根** / 可写面只有候选包）
   并输出可归档 JSON；
5. `environment/agent_visible_paths.json` 新增 `verifier_side_material` 与
   `platform_delivered_material` 两段，把 `tests\verifier\`（legacy 重复副本位置）
   显式列入 `not_present_in_agent_container`。

**验收对照**：`tests/` 下 `test_*_semantics.py` 命中数 **1**（平台投放副本）、
`tests/verifier/` 下 **0**（legacy 重复已删）、`verifier/tests/` 下 **1** 且与前者的
sha256 相同；解析顺序命中 workspace 的行数为 **0**；探针 `verdict=PASS`（7/7，输出见 §5）。
