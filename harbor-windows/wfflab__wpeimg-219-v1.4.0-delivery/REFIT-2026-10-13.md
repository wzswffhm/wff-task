## 1. 逐条闭环

### R1｜流式测试引入未声明的读块阈值 + 判据可被"首条正确"蒙过
对应甲方要求：**第 1 条「性能 / 流式类断言不得固定魔法阈值」**；手册 QD-SP-02、VV-02、VV-03。

**缺陷**：`tests/test_wpeimg_semantics.py::test_iter_sections_does_not_slurp_the_stream`
写过 `consumed < len(blob) // 4`——一个凭空规定的 25% 比例；而 `_Recorder` 只记录
`read` 的**尺寸**，无法区分「读了多少」与「读到哪里」，所以一个"先把整个映像读完、
再吐第一条节区"的实现只要在首条之前不调用 `read()` 就能绕过，而合法的大缓冲实现
又可能因为这 25% 被误杀。

| 专家步骤 | 处置 |
| --- | --- |
| ① 依据公开契约设计随输入规模增长的观测，不私自固定块大小 | 判据换成**尾部放大对照**：PE 的节区表位置由 `e_lfanew` + `SizeOfOptionalHeader` + `NumberOfSections` 决定，**与文件总长度无关**。测试用同一映像与它的「尾部加长 8 倍」版本，断言「取到第一条节区之前」的累计读取量**逐字节相等**——线性增长的实现（先整体读进来再看）必然不相等。**完全不再出现任何比例或字节阈值。** |
| ② 完整消费迭代器，检查中途与末尾阶段 | 同一用例内：交出第一条节区后继续迭代，断言后续仍然发生读取（`len(calls)` 增长）——先整体读完再吐的实现不满足；并断言 6 个节区按序产出。另把 `test_verify_rejects_every_structural_variant` 归入错误分类组（它检查 6 类结构违规，属于分类语义）。 |
| ③ 明确阈值依据 | 新判据的依据全部来自公开契约：题面 F 节只要求「惰性 + 不得整体读入 + 首条节区前的读取有界」，而「首条节区前的读取量由节区表位置决定」是 PE 格式的公开事实。 |
| 附属修正 | `_Recorder.calls` 从记录尺寸改为记录 **(起始偏移, 尺寸)**，使探针能表达"读到哪里"，并据此断言**不存在无尺寸读取**（`read()` / `read(-1)`）。 |

**验收对照**（本机实测）：

| 控制 | 结果 |
| --- | --- |
| Golden（`solution/reference/wpeimg`） | **27/27 PASS** |
| no-change（原始 workspace） | **19 FAIL / 8 PASS** → 二值门禁 0 |
| 原始 workspace 的 `iter_sections`（`fileobj.read()` 整体读） | 被新用例拒绝（no-change 中 FAIL） |

**涉及文件**：`verifier/tests/test_wpeimg_semantics.py`、`tests/run_tests.ps1`、
`tests/required_testcases.json`、`tests/rubric.json`、`tests/judge.toml`、
`verifier/rubric.conditions.json`。

### R6｜公开测试与隐藏验收必须分层，并给出负访问证明
对应甲方要求：**第 6 条**；手册 QD-IN-02、QD-IN-06。

**缺陷（本轮最实质的一条）**：v1.0.0 把隐藏套件放在**两个位置**——
`tests/test_wpeimg_semantics.py` 与 `tests/verifier/tests/test_wpeimg_semantics.py`，
而且 `run_tests.ps1` 的解析顺序是**按路径拼接隐式命中包内 `tests/`**，并把候选工作区
放在可解析路径上。候选改写 `environment/workspace/tests/` 下的同名文件，就可能让
判分取材落到自己手里；v1.0.0 也没有任何负访问证据。

**处置**（先弄清平台的投放契约再改，避免改成"谁也拿不到套件"）：

实测 Harbor 的 Windows 通道：`EnvironmentPaths.tests_dir = C:/tests`，
**Harbor 在跑 `tests/test.ps1` 之前把包根 `tests/` 目录整体复制到容器内 `C:\tests`**；
`C:\verifier` 是另一条判分侧注入通道。也就是说：**套件必须在包根 `tests/` 里放一份**，
这是平台的明文契约，不是可选项。第一次整改把包内副本删掉、只留 `verifier/tests/`
之后，控制组立刻以
`INVALID: the verifier-side hidden semantic suite was not injected` 失败——这条失败
记录本身就是"平台通道只有 `C:\tests`"的实测证据。

据此定稿的处置：

1. 包根 `tests/test_wpeimg_semantics.py` **保留**为平台投放副本，并与判分侧正本
   `verifier/tests/test_wpeimg_semantics.py` **逐字节一致**（sha256 对账）；
   `tests/verifier/` 下的**第二份重复副本删除**（v1.0.0 两份副本不同步）；
2. `run_tests.ps1` 的 `$verifierCandidates` 改为
   `-VerifierRoot` → 环境变量 → `C:\verifier\wfflab__wpeimg-219` → `C:\verifier`
   → **`C:\tests`（显式声明的只读平台通道）** → 包内平级
   `outside_harbor-verifier\…`（仅本地复现、不进容器）。
   **候选工作区与 `<任务根>\tests` 彻底不在列表内**；
3. 新增 `verifier/ISOLATION.md`：先写清平台投放机制（§0），再列三类材料的目录、
   容器内位置、用途与作答期权限，并说明"为什么进了 `tests/` 仍满足隔离要求"；
4. 新增 `verifier/negative_access_probe.ps1`：7 项只读断言（含**平台投放副本与正本
   sha256 一致**、**解析顺序不含 workspace 与任务根**、`tests/verifier/` 下无 legacy
   重复），输出可归档 JSON；
5. `environment/agent_visible_paths.json` 新增 `verifier_side_material` 与
   `platform_delivered_material` 两段，并把 `tests\verifier\` 记入
   `not_present_in_agent_container`。

**验收对照**：`tests/` 下 `test_*_semantics.py` 命中数 **1**（平台投放副本，v1.0.0 为 2）、
`tests/verifier/` 下 **0**、`verifier/tests/` 下 **1** 且与前者的 sha256 相同；
解析顺序命中 workspace 的行数为 **0**；探针 `verdict=PASS`（7/7）。

### R8｜区分度不足（v1.2.0：补 PE 目录表与 Authenticode 尾部）

对应甲方门禁：**四模型区分度**（`Opus model_score_sum > Qwen model_score_sum`）。

- **触发**：v1.1.0 的实测结果是 Qwen **3/3 全满**（27/27）、Opus 5 **2/3**，
  于是 `opus_score_sum (2) < qwen_score_sum (3)` → 硬门禁 **FAIL**。
  也就是说：弱主模型一次不错，强模型反而掉分，这道题对主模型没有区分力。
- **处置**：题面新增 **A2 节**（数据目录表与 Authenticode 尾部），并新增两个互相
  独立的程序化评分组：`data-directories`（0.08，4 条）与
  `authenticode-detection`（0.06，3 条）。required 由 **27 → 34** 条。
- **复验**：v1.2.0 实测 Qwen **3/3 全满**（34/34）、Opus 5 **2/3**（替代轮 33/34，
  只错 `f2p-iter-sections-does-not-slurp-the-stream`）。
  期间 Opus 第 1 轮撞上供应商 `http_502 Bad Gateway`，按甲方要求单列
  `jobs/invalid-slots.json` + `jobs/INVALID-SLOTS.md`，并以
  `model-opus-1-rerun` 绑定同一计划槽位重跑。
- **结论**：**仍然 FAIL**。增加「格式字段的数量」不足以拉开区分度——两个模型都能
  把这些字段读对。这条结论直接决定了 R9 的方向。

### R9｜区分度仍不足（v1.3.0：要求自行解析 PKCS#7 SignedData 的 DER）

- **触发**：R8 复验后区分度仍不成立。
- **处置**：题面新增 **F2 节**，要求新增公开函数 `signature_info(data)` **自己走
  PKCS#7 `SignedData` 的 DER**：报出 `contentType` 的点号 OID、`digestAlgorithms`、
  证书条数、签名者条数，并对 `dwLength` 与文件对不上的记录抛
  `WImgError(kind="structure")`。新增评分组 `signature-decoding`（0.06，5 条），
  required 由 **34 → 39** 条。
- **复验**：v1.3.0 实测 Qwen **0/3**（三轮均为 **37/39**，第 1 轮正是栽在
  `f2p-signature-info-describes-the-real-signed-data` 与
  `…-is-offline-and-standard-library-only`），Opus 5 **3/3 全满**。
  `opus_score_sum (3) > qwen_score_sum (0)` → **区分度成立**。
  期间 Opus 第 1 轮撞上 `http_500 upstream unreachable`，同样单列无效槽位并重跑。
- **结论**：**有效**。「必须真正解析一种编码」比「多读几个字段」更能区分模型。
  但这一轮也暴露了一个更深的问题，见 R10。

### R10｜判据未落到操作系统机制（v1.4.0：判分期真实调用 Windows 系统服务）

对应甲方要求第 3 条「Windows 价值必须真实映射到操作系统机制」。

- **触发（自检结论）**：把 9 个评分组逐个压过一遍后发现——
  **判分套件一次 Windows API 都没有调用**（`import` 只有
  `__future__/io/pathlib/pytest/re/struct/wpeimg`）。唯一与 Windows 系统组件相关的
  是校验和那一组，而它的权威值是**构建期**离线取得后固化成常量的。换句话说，
  v1.3.0 及以前主张的是「Windows 专属**格式**与权威值来源」，不是「Windows
  **操作系统机制**」。这个差距不能用措辞掩盖，只能改判据。
- **处置**：题面新增 **F3 节**（说明判据来源，不新增实现要求），并新增评分组
  **`windows-live-services`（0.12，4 条）**，把判据来源从离线常量换成真实系统调用：
  | 系统组件 | 调用点 | 断言用途 |
  | --- | --- | --- |
  | `imagehlp!MapFileAndCheckSumW` | `verifier/tests/win_services.py` | 对样本**与判分时现场构造的变体**取权威校验和；要求 `compute_checksum()` 逐例相等，且 ≥3 个变体的权威值互不相同（硬编码答案不可能通过） |

  是两条独立要求，两边不冲突。
- **同时修掉的两个判分链缺陷**（都在容器里才会暴露，本机 pytest 直跑发现不了）：
  1. `tests/run_tests.ps1` 只把**隐藏套件单个文件**复制进判分临时目录，
     同目录的 `win_services.py` 没有被 stage，容器内直接
