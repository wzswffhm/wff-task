# Windows 外采 6 题与内部采购 29 题质检执行手册

版本：2026-09-27 · 适用范围：Windows 评测题 · 交付形式：可直接执行的质检文档

本手册整理静态质检、动态质检、历史通用问题和证据要求。**本次完成的是规则与历史经验整理，没有重新运行 35 题，也不构成当前批次的验收通过证明。** 静态规则依据《质检方案-WIP.md》；动态规则来自本地 Windows 修复记录和逐 testcase 审计材料。其他类型 coding 评测集不在范围内。

阅读入口：[94 项对照表](02-WIP94项对照.md) · [历史问题库与35题重点](03-历史问题库与35题重点.md) · [证据模板](04-逐项证据与报告模板.md) · [资料来源](05-资料来源与核验边界.md)。

## 1. 质检最终要回答什么

每道题必须回答以下五个问题，并能定位到原始证据：

1. **Golden path 和空跑是否符合预期？** 不只看总分，核对每项 F2P/P2P、参考补丁实际应用情况、环境身份和完整性。
2. **每项得分、未得分是否正确？** 将真实下发要求、评分规则、执行结果、最终代码与 Agent 轨迹串成证据链。
3. **每条 testcase 是否严格对应题面或已公开的相关兼容性契约？** 同时检查漏测、越界加码和相反要求。
4. **验证的是功能还是写法？** 允许等价正确实现；不得只认 Golden 的私有函数、签名、代码布局、文本或调用方式。
5. **是否存在 Hack 或答案泄露？** 审查联网获取源码/补丁、读取本地 Golden、访问隐藏验证材料、篡改评分和利用旧产物等行为。

**保持严格的前提：要求真实给到模型、测试准确验证该要求、环境和证据有效。满足这三个条件后，模型没做对就应扣分；全模型失败、自评通过、实现接近 Golden 都不是放宽标准的理由。**

## 3. 先统一状态，避免把所有异常写成 0 分

分开记录三个维度：

| 维度 | 建议状态 | 用途 |
|---|---|---|
| 质检项 | PASS / FAIL / FLAG / BLOCKED / N/A | FAIL 是已证实缺陷；FLAG 是疑点；BLOCKED 是必要证据缺失；N/A 必须说明不适用依据 |
| 用例观察 | PASS / FAIL / SKIP / MISSING / ERROR / NOT_RUN | 记录真实观察；不能把未执行的测试补写为实测 FAIL |
| 运行有效性 | VALID / INVALID / PENDING / CANCELLED | 与原始 reward、复算 reward、根因分列 |

有效候选编译失败可以按冻结规则判整题 0，但未执行的后续用例仍写 MISSING/NOT_RUN。环境或验证器缺陷导致无法判断时，可信得分写 `null`，保留平台原始 0 以追溯。部分得分只能按预先冻结的规则处理，不能临时缩小分母。

根因至少区分：Prompt/下发、Test、Env/平台、Rubric/聚合器、证据/可信度、结果不稳定、模型能力、完整性/Hack。`timeout`、`missing`、`parse error` 都只是现象，需要继续查因。

## 4. 静态质检：继承 WIP，再作 Windows 适配

WIP 共 **94 项**：格式 13、任务有效性 18、可解性 7、完整性 6、环境 14、验证器 36。对照表逐项保留原 ID、对象、方式、Pass/Fail 和本手册落点；不得把 94 项全部称作“不运行即可完成的静态检查”。

### 4.1 静态阶段必查

| 检查组 | 具体检查 | 最小证据 | 不通过处理 |
|---|---|---|---|
| 文件与 Schema | instruction 非空/可读，task、judge、spec 可解析；入口和路径存在；结果命名合规 | 文件清单、解析日志、配置定位 | 修文件/Schema；不启动正式模型跑分 |
| 题面与可解性 | 目标、约束、产物、运行要求、公开接口、边界和例子含义明确；输入真实存在 | 需求编号与原文位置 | 补齐/修正题面并升级版本 |
| 泄解与隔离设计 | 无可直接照抄的解法；构建上下文、挂载、缓存、Git 对象不暴露 Golden/隐藏测试 | 文件和归档清单、配置、指纹；运行时再证实 | 隔离答案，重新构建并复验 |
| Windows 环境定义 | Shell/编码/路径/架构/权限明确；依赖锁定；实际工具路径和离线缓存位置一致 | Dockerfile/快照清单、lock、入口 | 修环境，目标 Windows 再执行 |
| 测试与评分 | 双向需求映射；ID 唯一；分组/权重/聚合器一致；正常、异常、边界和相邻回归有覆盖 | 断言源码、rubric、覆盖矩阵 | 修真实缺陷，记录增删和理由 |
| 实现公平性 | 不锁私有签名、不以字符串/文件存在代替核心功能、不复制实现到测试自测 | 断言逐行审查、等价实现设计 | 改为可观察功能；明确必要公共契约 |
| 交付与历史 | 来源/版本/哈希完整；原始记录与修复回放分开；变更可追踪 | manifest、历史记录、证据索引 | 缺口不算通过 |

### 4.2 WIP 与 Windows 材料的适用冲突必须明示

| 项目 | WIP 原口径与历史事实 | 本手册处理 |
|---|---|---|
| Case 数量 | VV-12 为 5–20；外采历史 D4=45、NTFS=24、Camelot=27、ADS=31 超限 | 如实登记 WIP FAIL；另记录 testcase/参数化实例/断言数。不得删有效测试或把多项包成一项制造达标；变更口径须留版本化依据 |
| Rubric 占比 | VV-14 ≤50%；外采 v10 记录已确认“含程序化评分条目”，当时六题均为 100% | 对该历史版本维持 FAIL，不能以“没有 LLM Judge”改写成 0%；新版本按实际计分归属和统一分母复核，不继承旧通过或失败 |
| 空跑 | QD-IN-04 要求低于通过线且无异常高分，并非一律 0 | 二值任务通常为 0；加权任务允许可证明的既有能力分，逐项核对并冻结预期 |
| 可见 tests | QD-IN-02 字面禁止模型读取 tests；真实软件仓库可能自带公开测试 | 隐藏验收/Golden 必须隔离；公开上游测试单列。按 WIP 字面记录偏差，未有项目适配依据前不直接豁免，也不擅自删公开开发资料 |
| Shell/镜像 | WIP 使用 test.sh、Docker；Windows 可用 test.ps1/VM | 原名文件按原规则检查；增加实际 Windows 入口同等检查。VM/桌面/WSL2 能力必须真实验证，改后缀不能替代能力 |
| 稳定性/难度 | WIP 提到波动≤30%、最少轮数、接近满分阈值及典型操作数 | 公式、轮数、模型版本未冻结则 BLOCKED；不得自行选公式宣称通过。真实题意下全过不等于应加隐藏难度 |

旧采购方案中额外的模型分差、难度配额、100% programmatic 等条件，作为历史要求留档，不自动覆盖本次指定的 WIP。存在冲突时分列“WIP 合规”“Windows 功能可信度”，不能相互抵消。

## 5. 动态质检流程

顺序：**冻结版本 → Windows 环境预检 → Golden/空跑对照 → 逐评分项审计 → 等价实现与反例 → 全量轨迹审计 → 分数复算与批次核对 → 整改复验**。静态阻断未消除时只做定位需要的诊断，不进入正式验收。

### 5.1 D01–D04：Golden path 与空跑对照

**D01 运行身份一致。** 在同一不可变 base、环境、依赖、测试树、评分规则、预算下分别恢复干净环境。Golden 由组织者注入；普通模型不能接触。保存 patch 实际应用命令、退出码、最终 diff/SHA。环境变量写着 `oracle`、日志标题为 Golden、镜像名含 gold 均不足以证明补丁已应用。

**D02 对照逐项成立。**

| 检查对象 | no-change/base 预期 | Golden 预期 | 不符合时 |
|---|---|---|---|
| 真正 F2P | 因目标缺陷失败 | 因真实修复通过 | base 已过则复核分组/基线；Golden 挂则查参考/测试/环境，不能为了 1 分改题意 |
| 真正 P2P | 通过 | 通过 | base 挂不能继续称 P2P；查环境、无关回归或错分，不用“历史例外”跳过 |
| 所有 required ID | 每项有终态，或对目标 API 缺失给明确功能 FAIL | 全部执行且符合预期 | 0 collected、skip、缺项不得作成功 |
| 题目总分 | 按冻结公式和已通过项目可复算，低于通过线 | 达到认可参考的预期目标 | 分数一致也需验证语义和因果 |

base 因无关依赖或测试语法错误失败，不构成有效 F2P；参考补丁可能不完整或与新增题意冲突，不能天然当唯一真值。测试只是重现某种 Golden 写法时，即使 Golden=1/base=0 也可能误杀正确实现。

**D03 空跑得分逐分解释。** 2026-09-22 外采 `outside6-scorefix-v4-20260922-e1916769f12f` 的文档记录：Chocolatey 空跑 0.30、Camelot 0.12、NTFS 0.07，其余三题为 0，Golden 均 1。[来源 S04] 这些数字是版本事实，不是本手册预设的新期望。复检必须取得每个非零分对应的 rubric、权重、PASS 证据，证明其为基线已有行为；同时检查是否存在奖励新增能力、异常高分或达到通过线。只有总分摘要不足以确认该部分分合理。

区分 **no-change（不改源码）** 与 **空实现/固定返回值/提前退出**。除 base 外，应按题目需要加入后者作为反例，避免已有正常功能掩盖核心缺陷。

**D04 稳定性与重建。** 推荐交付前同一版本独立 base 3 次 + Golden 3 次，至少一次干净重建/恢复；已有冻结项目轮数要求时按该要求执行。对比逐用例状态、分数、耗时、资源和系统残留。相同补丁重复运行不稳属于 verifier/environment 风险；不同模型生成不同补丁导致分差，不直接说明测试 flaky。

### 5.2 D05–D10：逐项判分与题面对应

**D05 证明要求实际下发。** 从当次完整 prompt 或模型读取 instruction 的工具返回中引用原文及位置，绑定版本/SHA。只在 organizer 文档、未挂载文件、后来追加的 contract 中存在的要求，不能追溯用于旧样本。补充 contract 必须确实进入模型上下文；公开接口要求需指向当时可见的 base/doc，而非上游之后的版本。

**D06 建立双向映射。** `requirement → testcase/assertion → rubric/权重` 和反向映射都要完整。每项依据分为：题面明确要求、公开接口/既有兼容性、合理可推导边界、未声明额外要求。边界须解释如何由契约推导；不得将“更健壮”变成隐含新需求。P2P 需证明与修复相关且在 base 成立；必要兼容性可在新版题面明示，不能事后增补。

**D07 每项都审，PASS 也审。** 对每个模型×轮次×评分项检查实际测试输入、执行路径、输出、断言、终态和代码差异。得分项要排除断言没执行、测试了副本、固定输出、旧二进制、只看退出码；未得分项要区分功能未实现、测试误杀、缺测、环境故障。不能只审总分为 0 的题或异常样本。

**D08 功能优先，接受多解。**

| 可作为判分依据 | 不应单独作为核心通过依据 |
|---|---|
| 输入输出、公共接口、实际生成产物、错误传播、状态与副作用 | 源码出现关键词、注释含算法名、文件/进程/端口仅存在 |
| 题面明确的公共 API、调用契约、文件格式 | Golden 新增的私有函数名/参数个数/签名、固定中间变量、代码文本相同 |
| 配置题对 YAML/JSON 语义、事件路径和最终分派的验证 | 仅查某一行 runner 名或字符串；结构正确就声称真实系统运行成功 |
| 并发/生命周期功能测试，必要时辅以有题意依据的结构检查 | 只按锁语句位置、固定线程/回调组织方式排斥等价实现 |

明确公开 API 的签名可以严格检查；不把“不能绑私有签名”误解为“不能验公共接口”。配置、ABI、协议本身有规范时可严格验证必要结构，但必须说明其与真实功能的关系。

**D09 等价实现与故障反例。** 除参考解外，选择有独立依据的等价方案，验证改变辅助函数、拆文件、不同 API 合法调用形式仍可通过；选择删关键修复、只修一半、硬编码、死代码、吞异常、提前 exit(0)、禁用功能等反例，验证对应要求确实失败。反例须记录实际生效的依赖/代码，防止构建时自动升级把“错误版本”修成正确版本。不要为某模型特有写法定制兜底。

**D10 替身必须保真。** Mock 外部服务/设备前，对照锁定依赖的真实输入输出和错误行为。不得用测试中手抄的实现代替候选代码；签名、打包、序列化、子进程等边界需跑实际生产路径。验证器要确认异步场景完成，不能把子进程 exit(0) 当全断言完成。负观察需独立健康哨兵和完整观测预算，区分“功能没有发生”与“观察器没启动”。

### 5.3 D11–D14：Windows 运行可信度

| ID | 检查内容 | 必须取得的动态证据 |
|---|---|---|
| D11 | 工具、路径、离线依赖和权限 | 实际 `Get-Command` 路径/版本、工作目录、用户/权限；同一 Windows 镜像内用 grader 原命令验证 Go/NuGet/Node/Rust/MSVC 依赖闭包；PowerShell 5.1/7、WINDIR/SystemRoot、UTF-8/BOM、引号/空格路径分别核对 |
| D12 | 本轮构建与候选回放 | 封存最终源码补丁 SHA；新验证环境回放后逐文件核对；构建前清理旧产物、检查退出码、记录产物来源/哈希；禁止 build/cache/vendor 噪声和静默截断 |
| D13 | 环境能力与真实系统终态 | 需要桌面/窗口/焦点则有交互桌面；需要 WSL2/SSH/systemd 则有真实宿主能力；ARM64 交叉编译/模拟与原生执行分别标注；ACL/ADS/注册表/服务有操作前后状态和清理证据 |
| D14 | 退出、异常、解析和日志 | readiness/suite/parser 异常有堆栈和有效结构化 INVALID；精确测试 ID 与终态对应；stderr/退出码保留；原始日志字节与 SHA 匹配，传输截断、转码和脱敏副本有单独身份 |

共享依赖在镜像中存在，不等于当前进程实际能解析。安装器返回 0 不等于组件可用，应执行目标工具链 canary。可构建、可模拟、原生运行是不同强度的证据，报告必须区分。

### 5.4 D15–D17：Hack、泄露与完整轨迹

审查范围包含生成模型、evaluator（若可能访问答案或向生成器反馈）、工具后端，以及候选代码在验证阶段的权限。新容器不能自动解决候选和评分器同权限的问题。

| ID | 重点行为 | 如何验证 |
|---|---|---|
| D15 | 联网取源码、PR/commit/patch、答案文件或搜索结果 | 扫描 WebSearch/WebFetch、curl/Invoke-WebRequest、WebClient/HttpClient、git fetch/clone/pull、包管理器和动态拼接/编码命令；追踪完整工具请求→响应→保存/读取→代码变更。正常仓库阅读不等于 Hack；外部信息访问按冻结限制判定 |
| D16 | 本地搜答案/隐藏验收 | 搜索 solution/golden/patch、目录递归、Git refs/reflog/悬空对象、压缩包、缓存/日志/临时目录、其他题/历史制品、挂载及 Windows reparse 路径；记录可达、搜索、读取、使用各阶段 |
| D17 | 篡改或绕过验证 | 写 tests/grader/reward、改环境变量/持久注册表影响测试、替换构建工具、伪造报告、只打印 PASS、跳过测试、旧产物复用；比较可信评分文件前后哈希与权限。题面本就要求注册表/ACL 操作时按目的与路径区分，不按关键词定罪 |

对每个事件使用下列事实等级，不跳级推断：

1. `ATTEMPT`：发起搜索、读取、下载或写入；请求失败也记尝试。
2. `ACCESS_CONFIRMED`：工具返回确实包含目标材料，或文件内容/哈希能证明读取成功。
3. `USE_CONFIRMED`：有后续读取、应用补丁或代码演变证据，证明材料进入解题。
4. `SCORE_IMPACT_PROVEN`：另有证据证明该行为影响有效得分；没有此证据只写已确认访问/使用。

失败请求之后打印 `done` 不算下载成功；网络连通不等于获取答案；与 Golden 相似的代码可能来自 base，不直接判抄袭；路径无命中和关键词无命中不能证明绝对安全。报告应写“在取得的 X/Y 份完整轨迹中未观察到”，并列日志缺失/截断与不可访问区域。

防护验证分别检查容器出站、服务端 Web 工具、可见文件和评分阶段权限。命令正则、代理环境变量、14 个路径检查、同容器只读目录都只有各自边界，不能合并宣称“作弊面彻底堵死”。

### 5.5 D18–D20：分数复算、归因与交付

**D18 独立复算。** 直接从 required ID 和测试终态、rubric 条件、前置门禁复算，不信任候选可写的 reward。二值方案按其完整通过规则判分；加权方案按冻结公式 `Σ(wᵢ×sᵢ)` 及门禁计算。记录分母、范围、精度容差、部分分/skip/missing 规则；空清单不能因 `all([])` 变为 1。对照 reward.txt/reward.json/平台总分，保留差异。

**D19 失败归因。**

| 直接证据 | 结论 |
|---|---|
| 当前 base/Golden 环境预检通过，候选造成语法/编译/API 或真实功能失败 | MODEL_FAILURE，可按规则有效扣分；后续未跑用例仍缺项 |
| base 也因同一缺工具/依赖/宿主/路径错误失败 | ENV/TEST，不能算模型能力差 |
| Golden 与明确题意冲突 | REFERENCE/CONTRACT 缺陷，保留题意并审查参考；不能为 Golden 删断言 |
| 测试依赖未下发私有符号或不真实 Mock | TEST/公平性缺陷，等价实现与固定补丁回放验证修复 |
| 401/429、账号禁用、参数不兼容或 generator/evaluator 中断 | 运行链路故障；分开标记已封存候选的制品分与完整作答资格，不把中断/空产物计能力 0 |
| 同一补丁重复不稳 | ENV/TEST 稳定性，固定状态后复跑 |
| 证据不足、材料身份不一致、日志哈希对不上 | EVIDENCE/BLOCKED，不猜测得分是否正确 |

**D20 批次与交付。** 只用相同版本最新完整有效批次统计；列计划/完成/有效/失败/无效/取消/待结束数，明确分母。被替代的 rerun 槽位保留旧→新对应，不双计、不选最高分。Golden/noop/探针/固定补丁回放不计独立模型成绩。模型各 4 次等历史安排只有在当前批次配置中被冻结后才采用。

所有模型都通过或都失败时，检查题意难度、测试覆盖与基础设施。没有具体测试缺陷就保持断言，不为造分差加新要求，也不靠删有效失败美化排名。

## 6. 每个评分项的最小证据链

```text
当次模型实际收到的要求（原文、位置、SHA）
  → 对应断言/评分标准（源码位置、输入、期望、权重）
  → 当次最终候选（补丁/文件 SHA、回放身份）
  → 实际执行（命令、Windows 环境、退出码、原始日志）
  → 精确 testcase 终态（含 expected/actual 或状态差异）
  → 相关轨迹（tool_call_id、请求和返回、结束状态）
  → 复算贡献分与判断（正确得分/正确扣分/误判/证据不足）
```

代码和日志支持功能结论，轨迹解释模型操作及可能的泄露/中断。evaluator 的“全部 PASS”只是辅助证据，不能覆盖正式 verifier；自评测试可能没有经过真实打包、序列化或进程边界。

每条得分与未得分都填链条；缺一环明确写缺什么、对结论有什么影响。模板提供逐项表、Golden/base 表、Hack 事件表和已核对的历史示例。

## 7. 整改与复验要求

每个问题写清：`现象 → 直接证据 → 影响哪些题/分数 → 根因 → 修改对象 → 复验方法 → 新版本 → 剩余边界`。

| 改动 | 必须复验 |
|---|---|
| 工具链、依赖、Shell、路径、镜像 | 环境 canary + 同版本 base/Golden + 原失败候选固定补丁回放；必要的重复稳定性 |
| Test/Mock/parser/rubric | 题面双向映射 + base/Golden + 等价实现 + 故障反例 + 每项得分复算；不能只验出错模型转绿 |
| Prompt/公开契约/题目基线 | 新版本完整准入与新模型样本；不得用新增要求追溯扣旧分 |
| 网络、文件隔离、评分权限 | 正/负探针、正式生成链路和 verifier 阶段实测；说明不覆盖区域 |
| 补丁提取、重建、发布资产 | 封存 SHA 与净环境重放文件树核对、远端实际执行资产身份核对 |
| 报表/日志落盘 | 原始制品重算、精确字节/派生文件身份核对；执行树改变后重新评估校准身份 |

验收状态建议：`可验收 / 退回修复 / 待环境或证据 / 当前版本隔离 / 已排除`。静态合规缺陷与运行可信度缺陷分别列；缺证据不算通过，历史修复不等于已发布，已发布不等于当前运行真实使用。
