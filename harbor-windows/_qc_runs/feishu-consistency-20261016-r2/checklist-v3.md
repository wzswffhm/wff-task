# 清单 v3 → 通用检查表（用于自查 wfflab__ 题包）

来源：`C:\Users\Administrator\Desktop\Windows评测待修复清单_20261016_v3.md`（28 项，涉及 zq-id 3/30/31/32/48/49/95/96/97）。
本表把 28 项**归并成同一类别的通用检查项**，用于逐包静态自查（只读源码与包内记录，不跑容器）。
每条结论必须给出 `文件:行号` 证据；无法判定时写「待人工确认」，不得凭印象下结论。

判定取值：`PASS`（本包不存在该问题）/ `FAIL`（存在）/ `N/A`（本包不适用）/ `待确认`。

---

## C1 测试与私有实现耦合（来自 3-1）

- 检查什么：隐藏语义测试（`tests/test_*_semantics.py`）是否直接引用候选包的**私有符号**（`_` 前缀函数/模块、内部辅助函数名、内部数据布局），使「合法重命名或重构私有实现」的候选在收集/导入阶段就失败。
- 判定方法：枚举隐藏测试里所有 `import` 与属性访问，标出访问了候选包私有名称的位置；再看这些名称是否属于题面公开契约（`instruction.md` 中列出的公开 API）。
- FAIL 判据：测试导入了题面未公开的私有函数/模块，或断言依赖具体私有函数名/内部组织结构。
- 同时记录：测试是否只用题面公开入口（好坏参半，需给出实际引用清单）。

## C2 未公开的判分条件（来自 30-1、95-1、96-2）

- 检查什么：测试断言的**额外条件**是否在 `instruction.md` 里写明（长度门槛、强度、元数据 UserName、特定错误 ID、特定异常类名、特定返回类型细节等）。
- 判定方法：把测试里每个 `assert` 的关键期望抽出来，与题面「验收标准」小节逐条对照；题面没有对应表述的即为「题面外断言」。
- FAIL 判据：存在会影响整题二值分的题面外断言（即使合理）。
- 输出要求：列出「测试断言 → 题面依据（有/无）」的对照表（不超过 20 行）。

## C3 断言缺口 / 可被绕过（来自 32-1、31-2）

- 检查什么：① 是否存在「候选自报即算过」的断言（只信候选返回值，没有独立系统观测）；② 是否存在条件性核对（例如仅在计数 > 0 时才核对内容、仅在文件存在时才校验）；③ 清理/残留类断言是否只扫描固定命名前缀（如只查某个临时目录名前缀），换名即可漏检。
- 判定方法：找 `if` 包起来的断言、只比较候选返回值的断言、按固定名字/前缀枚举的断言。
- FAIL 判据：存在可被「空值/谎报/改名」绕过的整题关键断言。

## C4 覆盖不足：题面要求 vs 实际用例（来自 30-2、32-2、48-2、49-2、95-3）

- 检查什么：题面验收条款逐条是否有对应用例，尤其：故障注入（IO 失败、权限失败、中途失败）、边界值（上下界、负值、超大值）、反例（应拒绝/应不成立的场景）、终态断言（进程存活、内核终态、注册表终态）。
- 判定方法：把 `instruction.md` 验收条款编号化，逐条映射到 `tests/test_*_semantics.py` 的测试函数；无对应函数的列出来。
- FAIL 判据：题面明确要求的可验收行为在测试中**完全无对应用例**，或只测了「没报错」而没测终态。
- 输出要求：给出「题面条款 → 用例」映射表（缺项的标注出来）。

## C5 F2P 在空跑基线上是否已通过（来自 48-1、97-1）

- 检查什么：`tests/required_testcases.json` 中标为 `F2P` 的用例，在 `jobs/ctl-nop-*/` 三次空跑里是否已经 PASS。
- 判定方法：读 `jobs/ctl-nop-1..3/` 下的 result/report（`result.json`、`verifier/report.json`、`verifier/reward-details.json`），取出逐 case 状态；与 required 清单比对。
- FAIL 判据：任一 F2P 用例在三次 NOP 中有 PASS（说明它不是 F2P）。

## C6 golden / 空跑对照是否齐全（来自 97-1）

- 检查什么：`jobs/` 是否含 `ctl-oracle-1..3`（参考解）与 `ctl-nop-1..3`（空跑），且各自 VALID 且分数符合预期（oracle=1、nop=0）；`verifier/evidence/` 是否有 golden / no_change 记录。
- FAIL 判据：缺任一类记录，或记录无效（checksum 不匹配、INVALID）。

## C7 评分入口是否唯一且规则一致（来自 96-3）

- 检查什么：包内是否存在两个以上评分入口（例如 `tests/test.ps1` 与 `tests/aggregate_results.ps1`、或 `grade.py`），其计分规则是否可能给出不同分数（二值 vs 比例分）。
- 判定方法：读所有评分入口，比较 `formal_score` / `verdict` 的计算规则。
- FAIL 判据：入口之间存在可导致同一输入得到不同分数的规则差异。

## C8 基础设施故障是否被当成 0 分（甲方 2026-10-16 质检意见 2 的同类项，与清单 48-2 同族）

- 检查什么：依赖缺失/测试收集失败/pytest 内部错误（setup 报错）时，判分链路是否输出 `VALID/0`（错误）还是 `INVALID`+空分数（正确）。
- 判定方法：读 `tests/run_tests.ps1`（收集数、outcome 映射、exit code）与 `tests/aggregate_results.ps1`（run_validity 计算）与 `tests/test.ps1`（是否写 reward 文件）。
- FAIL 判据：任一基础设施故障路径会产生 `run_validity=VALID` 且 `formal_score=0`。

## C9 模型区分度（来自 3-3、32-3、48-3、49-3）

- 检查什么：`jobs/model-opus-*` 与 `jobs/model-qwen-*` 的整题分数，是否满足 `sum(Opus) > sum(Qwen)` 或至少不双满/双零。
- 判定方法：读各 model job 的 `verifier/reward.json` / `result.json`；`jobs/_index/` 若有汇总直接引用。
- FAIL 判据：Opus 与 Qwen 整题分数完全相同（含同为 0 或同为 3）。

## C10 对照模型身份是否可信（来自 97-3）

- 检查什么：`jobs/model-opus-*/config.json`（或 job.json）里声明的模型名与端点，是否确为要求对照的模型（不得是 claude-opus-4-8 之类不同型号，或发生回落）。
- FAIL 判据：模型名与要求的对照模型不一致，或缺少可核验的模型标识。

## C11 有效样本完整性（来自 97-4）

- 检查什么：是否有因环境/脚手架异常而未进入有效评分的运行（如 paging file too small、进程非零退出），以及是否被静默剔除或计 0。
- 判定方法：`jobs/invalid-slots.json`、`jobs/INVALID-SLOTS.md`、各 job 的 `job.log`、`jobs/config.json`。
- FAIL 判据：存在异常运行且未单列说明/未重跑。

## C12 题面混入无关模板文字（来自 49-4）

- 检查什么：`instruction.md` 是否包含与本题验收无关的内容（别的题的技术约定、模板残留、DPAPI/文件流之类无关约定）。
- FAIL 判据：存在与本题任务和解收无关的段落。

## C13 题面描述不准确（来自 96-4）

- 检查什么：题面里的技术概念、平台语义、行为描述是否有事实错误或自相矛盾（与题面后文的验收条款冲突）。
- FAIL 判据：存在明确的事实性错误或前后矛盾。

## C14 题面范围 vs 测试覆盖范围（来自 97-2）

- 检查什么：题面要求的范围是否远大于测试覆盖（例如题面要求「整个子系统都符合规范」，测试只覆盖其中一个函数），导致满分不能支撑题面结论。
- FAIL 判据：题面明确要求的行为集合中，有未被任何用例覆盖的**公开方法/行为**（同 C4，但强调「夸大整题结论」这一点，可合并结论但需分别注明）。

## C15 跨平台/其他平台要求与回归（来自 3-2）

- 检查什么：题面是否要求「Unix/POSIX 行为保持不变」「跨平台兼容」，而包内只有 Windows 侧测试、没有其他平台的编译或行为回归。
- FAIL 判据：题面有跨平台不变要求，但没有任何对应验证。

## C16 失败结果的证据完整性（来自 31-1）

- 检查什么：失败时落盘的记录是否含逐 case 的原始证据（输入参数、实际退出码、stdout/stderr、期望与实际值、每个子断言），还是只剩布尔值/汇总矩阵。
- 判定方法：看 `aggregate_results.ps1` 输出的 `cases[]` 结构（只有 `test_id` + `passed` 即为不足）、`verifier/report.json`、`verifier/reward-details.json` 是否含明细，pytest json 报告是否随包保存。
- FAIL 判据：交付物里失败项无法逐一复核（缺实际值/输出）。

## C17 答案污染与联网（来自 96-1）

- 检查什么：评测环境是否禁网（`environment/Dockerfile`、`task.toml`、adapter/network_mode 设置），题面/包内是否指向可下载上游补丁的地址；`jobs/model-*` 轨迹里是否有网络取源码/补丁的痕迹。
- FAIL 判据：环境允许出网，或轨迹中出现取得上游源码/补丁的证据。

## C18 镜像 OS 版本（来自 49-1，清单特别说明「镜像检查仅关注 OS 版本是否过旧」）

- 检查什么：`environment/Dockerfile` 的 `FROM` 是否为过旧镜像（Windows Server Core 2004/build19041 及更早、Nano Server、Server Core）；要求为 Windows Server 2022 / LTSC2022（build 20348）或更新。
- FAIL 判据：基础镜像为 Server Core / Nano Server / build < 20348。
