# wspawn：子进程句柄移交不正确

`wspawn` 是我们沙箱执行器的**子进程启动模块**。采集器、构建器和插件宿主都用它拉起辅助进程，这些辅助进程只应该拿到调用方明确交出去的那几个对象（一条日志管道、一条输入管道），**不应该**顺带看到宿主进程里其它的文件、管道或事件对象。

## 目标平台（范围声明）

本任务的目标平台是真实的 Windows，验收不使用其他操作系统，也不需要实现其他操作系统的版本。

`wspawn` 的验收建立在真实 Windows 进程创建的句柄语义上：「只移交列出的对象」必须在子进程里**真的成立**，评测器会把子进程实际能访问到的对象与调用方声明的清单逐一比对，**不采信** `wspawn` 自己的返回值。

跨平台兼容（POSIX 的 `FD_CLOEXEC`、`close_fds` 之类）不在验收范围内，也不构成替代实现。

## 现象（仓库 issue #218）

1. **子进程拿到了一堆不该拿的对象**：沙箱里拉起的辅助进程能读写宿主的日志文件、连上宿主开的管道；把 `close_fds` 关掉之后更严重，连临时文件句柄都漏过去了。
2. **没法只交一部分**：调用方想要「只把这一条管道给子进程」，实际结果是「要么全给，要么连标准流都断掉」，中间没有可用的挡位。
3. **可继承位改不动或看不出来**：`set_inheritable()` 之后，从外部看对象的可继承状态没有任何变化，`is_inheritable()` 也和环境对不上。
4. **子进程里的句柄值对不上**：调用方按自己手上的值去子进程里用，发现指向了别的对象或者干脆无效。
5. **不支持时不报错**：在拿不到所需能力的情况下，模块静默退化成一个「尽量做」的实现，既不报错也不说明。

## 任务

修复 `wspawn` 包，使其满足下列验收标准。`docs/NOTES.md` 是早期草稿，与 Windows 的实际语义已经不一致，请以本说明的验收标准为准。

## 验收标准

### A. 精确移交（硬门槛）

- `spawn(argv, inherit=[...])` 必须让子进程**只能**访问 `inherit` 里列出的那些对象，加上调用方显式指定的标准流。
- 调用方进程里**其它**处于可继承状态的对象，不得出现在子进程中。
- 不传 `inherit`（或传空序列）时，子进程除标准流外不应拿到任何调用方对象。

### B. 移交的对象必须真的可用

- 出现在 `inherit` 里的对象，子进程必须能用它完成正常读写。
- 移交必须是**可用**的，而不只是「句柄值存在」：子进程读到的内容要与调用方写进去的一致。

### C. 可继承状态可控且可外部观测

- `set_inheritable(handle, True/False)` 必须真的改变该对象的可继承状态，且改变结果可以用系统接口从外部独立读到。
- `is_inheritable(handle)` 的返回值必须与外部读到的状态一致。
- 对不支持该操作的对象，必须按 F 报错，不得静默返回。

### D. 句柄值在子进程内保持

- 调用方交出去的对象，在子进程里必须仍然用**同一个数值**访问到。
- 子进程按该数值操作时，必须作用在同一个对象上。

### E. 对象类型识别

- `handle_kind(handle)` 必须区分至少这几类：文件、管道、控制台、以及无法识别的对象。
- 对无效句柄必须按 F 报错。

### F. 不支持时的错误分类

- 当底层对象、参数或运行环境不支持所请求的操作时，相关接口必须抛出 `WSpawnError`，且 `err.kind == "unsupported"`。
- 参数不可用时抛 `WSpawnError(kind="badarg")`；底层系统调用失败抛 `WSpawnError(kind="os")`。
- 不得出现静默成功，也不得只抛出无分类的 `OSError`。

### G. 不得回归

- 可见冒烟测试 `tests/test_wspawn_basic.py` 必须继续通过。
- 公开 API 的名称与签名保持不变（`spawn` / `set_inheritable` / `is_inheritable` / `inheritable_handles` / `handle_kind` / `WSpawnError`）。
