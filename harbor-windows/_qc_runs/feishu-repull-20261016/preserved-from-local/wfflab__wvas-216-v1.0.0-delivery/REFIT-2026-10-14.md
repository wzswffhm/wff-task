## 0. 为什么换掉题目主体，而不是就地修补

原 216 号位（`wchunk`，分块容器格式）的返修意见把问题指到了根上：它考的是二进制布局、
CRC 变体与流式读取，**判分过程不调用任何 Windows 系统组件**，换到 Linux 上同一份验收
标准可以原样复算。就地补几条判据改变不了这个结论，因此本包换掉题目
主体，改成一个**只能由 Windows 虚拟内存 API 回答**的题：审计一个真实进程的地址空间。

被审计的缺陷族同样来自公开仓库：psutil 的 Windows `memory_maps` 长期存在 64 位地址与
区间长度按 32 位处理（gh-863、gh-3019）、映射文件路径缓冲区不足（gh-2934）、
`\Device\...` 设备路径未翻译成盘符路径（gh-2494）这几类问题。本包把这一族问题抽成一个
独立的小包 `wvas`，验收标准按 Windows 的语义重写，样本与用例全部原创。

## 1. 逐条闭环

### R1｜参考解与隐藏测试必须随包交付，入口不得依赖包外注入

原文：*"这个包目前不能单独复现验收：`solution/solve.ps1` 需要的 `reference/wchunk`
没有交付，`tests/run_tests.ps1` 需要的 `test_wchunk_semantics.py` 也没有交付，入口依赖
包外注入。"*

| 处置 | 落点 |
| --- | --- |
| 参考解载荷随包交付 | `solution/reference/wvas/`（`__init__.py`、`_winapi.py`、`errors.py`、`vas.py`），与 `verifier/oracle/reference/wvas/` 逐字节一致（自检第 7 项） |
| 隐藏套件随包交付 | `tests/test_wvas_semantics.py`，与 `verifier/tests/test_wvas_semantics.py` 逐字节一致，`sha256=4ae09187956700db8496ec3ef759987274269b91dafaf5007170db2cdb363500` |
| 入口不依赖包外路径 | `solution/solve.ps1` 只把包内 `solution/reference/wvas` 覆盖到镜像工作区，不读取任何包外路径；`tests/test.ps1` 只引用 `$TaskRoot/tests` 与 `$TaskRoot/verifier` |
| 隔离 | 隐藏套件不进镜像：`environment/agent_visible_paths.json` 与 `task.toml` 的 `withheld_from_agent = ["tests", "solution"]` 一致；`verifier/README.md` 记录模型可见面 |

### R2｜14 份 job 的 Task checksum 必须与当前 Task 一致

原文：*"14 份 job 的 Task checksum 和当前 Task 不一致，不能把它们作为当前版本的通过
证明。"*

| 处置 | 落点 |
| --- | --- |
| 单一冻结快照 | 控制组（Oracle ×3 / no-change ×3）与模型轮全部在同一份**内容不再改动**的包目录上跑；`jobs/` 组装发生在全部轮次之后 |
| 包内除 `jobs/` 外不再改动 | 本文件、`verifier/WINDOWS_VALUE.md`、`verifier/SEALED_MANIFEST.json` 都在跑分前写完并封存；跑分之后只新增 `jobs/` |
| 复算口径 | 甲方复算用的 Harbor dirhash **排除 `jobs/`**，因此「跑分时 dirhash = 交付包 dirhash(排除 jobs/)」，逐轮 `result.json` 的 `task_checksum` 与之一致 |
| 核验数据 | `jobs/_index/assembly_report.json` 逐轮列出 `task_checksum`；交付 `README.md` 给出该值的汇总 |

### R3｜飞书填写的模型分数必须与该轮原始产物一致

原文：*"日志里 Kimi 实际为 1/1，但飞书填写的是 0/1，也需要核对。"*

| 处置 | 落点 |
| --- | --- |
| 以原始产物为准 | 飞书记录里的分数一律取自 `jobs/<job>/verifier/reward.txt`，不手抄、不换算 |

### R4｜Windows 价值必须真实映射到系统组件

原文：*"题目主要检查二进制布局、CRC 和流式读取；`task.toml` 及 `verifier/WINDOWS_VALUE.md`
对该题的归类与「测试没有 Windows 专属行为」这条判断不符，不满足当前 Windows 题要求。"*

| 处置 | 落点 |
| --- | --- |
| 判据落到真实系统组件 | 八条机制逐条对应 Windows 调用：`kernel32!VirtualQueryEx` + `MEMORY_BASIC_INFORMATION`（地址宽度、长度宽度、`MEM_RESERVE` 可见性）、`psapi!GetMappedFileNameW`（文件背衬命名、匿名映射无文件名）、`kernel32!QueryDosDeviceW`（设备路径 → 盘符/UNC）、`OpenProcess` 错误码分类、`psapi!EnumProcessModulesEx` + `GetModuleFileNameExW`（映像清单） |
| 门禁产物 | `metadata/windows_mechanism.json`：反事实答案「否」，八条机制各带 `instruction_quote`、`test_ref`、`f2p_case`；`non_windows_must_fail` 锚定 `environment/validate_environment.ps1` 的 `Win32NT` 硬失败 |
| 非 Windows 必然失败 | 隐藏套件模块级 `os.name != "nt"` 跳过；`environment/validate_environment.ps1` 在非 `Win32NT` 主机直接 `Fail` |
| 价值论证 | `verifier/WINDOWS_VALUE.md`（逐条映射 + 证据强度分级） |
| 自检 | `python harbor-windows/skills/harbor-windows/scripts/check_windows_mechanism.py --task-dir <包目录>` → `PASS`（F1–F6 全过，无自我否认表述） |

原文返修意见最后一节要求按 Windows 机制重写判据；同时本轮按甲方补充口径处理题面

| 处置 | 落点 |

| 题面只留现象与验收标准 | `instruction.md` 的「现象」逐条是调用方能观察到的错误结果（地址偏小、6 GiB 保留区长度离谱、`state == "reserve"` 不出现、路径贴进资源管理器打不开、匿名映射报空串、进程不存在抛 `OSError`、模块列表重复几百次） |

### R6｜交付形状自检：必测清单顶层数组、缺测即 INVALID

按 218/219 的实测形状复检后改了两处：

* `tests/required_testcases.json` 由「带 `testcases` 键的对象」改为**顶层 JSON 数组**（每项 `{id, group}`），
  与 `wfflab__wpeimg-219` / `wfflab__wchunk-216` 一致，`tests/aggregate_results.ps1` 同步按数组读取。
  旧形状会让按数组解析的检查器读出 0 条，进而误报「少于 5 条」「缺 F2P/P2P」。
* `tests/run_tests.ps1` 对「套件没有采集到的 required 用例」不再写 `FAIL`，改记 `INVALID`；
  `aggregate_results.ps1` 只把 PASS/FAIL 当作已观测状态，其余一律计入 `invalid` ⇒ `run_validity=INVALID`、
  不写 `reward.txt`、容器入口 exit 2。这正是甲方在 215/216 返修原因里点名的「缺测应为 INVALID、不能输出正式 0 分」。

本机用同一条判分链路实测三种场景：缺陷模块 `VALID` + 0 分（16 项 8 过）；参考解 `VALID` + 1 分（16/16）；
人为让一项 required 用例无法采集 → `INVALID` + `invalid=1`，正式分不成立。

## 2. 设计冻结：wvas 契约

公开 API（名字与签名不得改变）：`regions(pid, include_reserved=True)`、
`file_backed_regions(pid)`、`modules(pid)`、`protection_name(value)`、`type_name(value)`、
`WVasError`。

| 契约面 | 要求 | 对应缺陷 |
| --- | --- | --- |
| 区间地址 | 完整 64 位真值，不得截断到 32 位 | `base & 0xFFFFFFFF` |
| 区间长度 | 超过 4 GiB 的区间报真实长度 | `RegionSize & 0xFFFFFFFF` |
| 保留区 | `include_reserved=True` 时已提交与已保留都要出现 | 只收 `MEM_COMMIT` |
| 路径形式 | 盘符路径或 UNC，`\Device\`、`\??\`、`\\?\` 前缀不合格 | 直接回传 `GetMappedFileNameW` 的原始设备路径 |
| 无文件背衬 | `path is None`，不得是空串 | 无名称时返回 `""` |
| 错误分类 | 全部走 `WVasError(kind=...)` | `OpenProcess` 失败抛裸 `OSError` |
| 映像清单 | 按 `base` 升序、同一文件路径只出现一次、`path` 可打开 | 直接由 `image` 区间推导且不去重 |

缺陷版本（`environment/workspace/wvas/vas.py`）保留原样的错误行为，可见冒烟套件
`tests/test_wvas_basic.py` 只描述返回结构，对上述缺陷全部为绿：这正是原题「问题被
可见测试掩盖」的形态。

## 3. 判分链路与隔离

| 环节 | 说明 |
| --- | --- |
| 注入 | Harbor 只把包根 `tests/` 挂到容器 `C:\tests`；`verifier/` 不上传 |
| 判分 | `tests/test.ps1` → `tests/run_tests.ps1`（pytest `--json-report`，函数名 → 稳定 slug）→ `tests/aggregate_results.ps1`（补 `f2p-`/`p2p-` 前缀、与 `required_testcases.json` 对齐、算二值 `formal_score` 与 `run_validity`）→ `result.json` |
| 报告协议 | `aggregate-v1`：`schema_version`、`run_validity`、`total/passed/failed/invalid`、`formal_score`、`cases[]`、`rubric` 条目全部带前缀 |
| 缺测处置 | 某个 required 用例若没被套件采集到，`checks.json` 记 `INVALID`（既非 PASS 也非 FAIL）→ `invalid>0` → `run_validity=INVALID`、容器入口 exit 2，不写 `reward.txt`，绝不落成正式 0 分 |
| 用例集合 | 16 项：F2P 8 项（`f2p-*`）+ P2P 8 项（`p2p-*`）；`tests/rubric.json` 七组权重和 = 1.0，`tests/judge.toml` 绑定其 sha256 |
| 目标进程 | 判分时由隐藏套件自己拉起一个目标进程（1 MiB 文件映射视图、4 MiB 匿名映射、1 MiB 私有提交、6 GiB 保留、加载 `version.dll`），不采信被测包自报的数字 |
| 参考解 | Oracle 轮把 `solution/` 送进容器执行 `solve.ps1`，把包内参考载荷覆盖到工作区 |
