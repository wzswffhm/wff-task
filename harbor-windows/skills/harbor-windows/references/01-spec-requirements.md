## 一、需求信息（第一章）

| 项 | 内容 |
|---|---|
| 需求名称 | Windows 专项 Coding Bench 数据采购 |
| 数据用途 | Agentic Coding 模型评测、横向比较、能力缺陷分析、稳定性回归 |
| 采购规模 | 本轮正式题数量、候选题数量和批次安排另行书面确认；**本文档暂不冻结总题数** |
| 历史题处理 | 原外采 6 题作为**候选题转换**，与新题一并生产、运行和交付；只有完成标准 Harbor 转换并按本版本重新验收通过后方可计入正式交付，**不继承历史验收结论** |
| 最终交付 | 计分题本体必须是符合冻结 Schema 的标准 Harbor Task；Evidence、Metadata、模型运行、质检报告、来源与版本材料仍须完整交付，但**统一放在 Harbor 题包外的批次级伴随交付区** |
| 正式判分 | 仅使用**真实 Windows Runtime** 中的独立程序化测试；所有 required F2P 与 P2P 全部通过得 1，否则得 0 |
| 参考模型 | Qwen3.8-Max-0902、Opus 5 为主要难度模型，**各独立运行 3 次**；GLM-5.3、Kimi K3 用于可运行性和基础质量检查 |
| 单题时限 | 单次端到端评测原则上**不超过 12 小时**；具体资源预算随 Harbor 执行配置冻结 |
| 结算口径 | **仅以采购方最终验收通过、版本冻结且可稳定复现的标准 Harbor 题目计数**；未通过题不计入交付数量，补题要求按后续书面数量约定执行 |

> 精确模型标识、Harness 版本、Harbor Schema、Windows 镜像或快照、工具权限、Token/时间预算和采样参数
> 应在**首批生产开始时冻结**。模型或平台版本变更后，不得与旧结果直接比较；需要用于准入时应统一回刷。

## 二、采购目标与核心原则（第二章）

### 采购目标

采购能够**真实暴露 Coding Agent 在 Windows 开发、调试、构建、运行和系统状态处理方面能力缺陷**的评测题。

题目难度**应来自**：真实工程语义、跨文件状态、执行时序、环境约束、版本差异、失败路径、多目标权衡。

题目难度**不得来自**：歧义、信息缺失、错误环境、错误测试、冷僻知识背诵。

### 正式题必须同时满足的 5 条

| # | 原则 | 判据 |
|---|---|---|
| 1 | **Windows 有价值** | 核心实现、错误根因或验收机制**实质依赖** Windows 平台语义 |
| 2 | **能力可真实验证** | Agent 在冻结的 Windows 环境中完成任务；Evaluator 在**真实 Windows Runtime** 中触发并验证目标能力 |
| 3 | **题面与测试一致** | 每条计分 testcase 都能追溯到题面明确要求、题内可见的公共契约或与修改相关的既有兼容性要求 |
| 4 | **验证功能而非写法** | 允许合理的等价实现；**不得**绑定 Golden 的私有函数、参数个数、内部布局、固定调用顺序或代码文本 |
| 5 | **结果可复现、可审计** | 初始态、Golden、模型运行、逐 testcase 结果、环境身份和最终补丁能够**闭合对应** |

> **红线**：不得因为某模型全部失败、模型自报成功、实现接近 Golden 或项目进度紧张而**放宽题面、测试和验收标准**。

## 三、题面与内容红线（第四章摘录）

### 每题必须具备 8 项

1. 明确、真实且不泄露解法的 `instruction.md`
2. 可稳定复现初始问题的代码仓、工程资产或系统状态
3. 冻结的 Windows 版本、Edition、架构、Locale、Shell/Runtime、依赖与权限
4. 可执行、可清理、可恢复的环境
5. Oracle/Reference Solution
6. 与参考解实现**相互独立审查**的隐藏测试，包含 F2P 与 P2P
7. 来源、Repo、Commit、Issue/PR、License、授权、Lineage 与污染风险记录
8. 初始态、Golden、空实现/错误反例和模型运行的可核对结果

### 题面应写 / 不得写

| 应写 | 不得写 |
|---|---|
| 背景或现象 | Golden Patch |
| 目标 | 答案路径 |
| 功能边界 | 隐藏测试 |
| 约束 | 精确修改位置 |
| 允许修改范围 | 可直接照抄的实现步骤 |
| 用户可见的验收标准 | |

### 禁止

- 重复题
- 仅替换名称、常量、路径、语言和描述的**表面变体题**
- 被测工作树和可见 Git 历史包含 Solution、Golden Patch、隐藏 Tests、预期答案或 Reward 信息

## 四、评分口径（第六章摘录）

```
score = 1，当且仅当：
  所有 required FAIL_TO_PASS testcase 均 PASS；并且
  所有 required PASS_TO_PASS testcase 均 PASS。

score = 0：存在任一 required testcase 为 FAIL。

score = null / INVALID：存在 required testcase 未执行、缺失、SKIP，
  或发生环境、Runner、Verifier、解析、授权等基础设施异常。
```

- **不设置 testcase 权重、部分分、LLM/Agent Judge 或主观质量分**
- INVALID **不得伪装成模型 0 分**，也不得纳入难度统计；修复后须在**相同冻结条件**下补跑
- **不得**临时缩小 required 清单、改变分母或删除失败 testcase 以得到 1 分
- 测试级通过数量**只用于**故障定位和"双方均为 0"时的模型区分度辅助比较，**不产生任何正式部分分**

## 五、验收结论四态（第十二章）

| 结论 | 处理 |
|---|---|
| **通过** | 计入正式采购数量并冻结版本 |
| **退回修改** | 修订后重新执行所有受影响环节 |
| **淘汰并替换** | 不计入数量，由供应商补充新题 |
| **暂停批次** | 出现集中性质量、安全、泄漏或版本问题，完成根因整改后恢复 |

### 质保

- 数据、代码、测试、环境定义、Reference Solution、运行记录和衍生成果的使用权与交付范围以合同为准
- 供应商须保证来源和授权合法，提供**不少于 90 天**的质量保证期
- 因环境漂移、依赖失效、Evaluator 缺陷、答案泄漏、重复或授权问题导致题目失效时，应**免费修复或等量替换**
- 具体交付批次、日期、基础设施提供方、模型账号/API 费用及付款节点另行书面确认
- **本文件冻结的是题目质量、标准 Harbor 交付、二值判分和验收口径，不以排期变化降低标准**
