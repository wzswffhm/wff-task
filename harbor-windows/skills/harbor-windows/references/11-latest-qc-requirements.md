# 最新质检要求（20261012 批次沉淀）

> **来源**：甲方质检报告《Windows-48题质检-专家修复详解版-20261012》第 004 / 005 篇
> （`zq-id=11` wchunk-216、`zq-id=12` wfmt-215），以及该批次逐条复验通过后确认的整改口径。
>
> **适用**：所有 Windows 专项题包的**新生产**与**返修**。这 6 条是通用要求，不限于被点名的两道题。
>
> **口径**：本次说明不代表修改或重评了原始产物；新要求不得追溯扣旧样本。

---

## 1. 性能 / 流式类断言不得固定魔法阈值

**要求**：验证"流式/惰性/有界内存"时，**不得**私自固定某个块大小（如 `max_request ≤ 8192`）作为判据。

**为什么**：题面只要求"边读边处理"，并未规定 8 KiB。合理的 64 KiB 缓冲实现会被误杀；而"先吐第一项、随后一次性读完"的伪流式实现反而可能漏过。

**必须怎么做**：

1. 依据**公开契约**设计**随输入规模增长**的观测：把输入放大 N 倍（如 8×），比较读取窗口与"尚未消费的记录数"是否增长——合法实现保持常量级，伪流式实现线性增长。
2. **完整消费迭代器**，检查中途与末尾阶段的行为（不能只看第一条）。
3. 构造**尾部错误**（如尾部校验和翻转），确认完整迭代时抛出约定异常，且异常类型/`kind` 正确。
4. 若确实需要阈值，阈值必须有公开依据，不能来自某个模型的代码写法。

**反例（被质检点名）**：旧套件只消费 `next(stream)` 一次，断言 `max_request ≤ 8192` 且"首条前读取少于整体 1/4"。

## 2. API 失败必须单列无效槽位，不得计入能力分

**要求**：原始调用发生**配额 / 限流 / 传输 / 超时**失败时，该轮**不得**被解释为算法能力失败。

**判据（无效槽位）**——满足任一即记无效：

- 该轮 `agent_result.metadata.result.status` 不是 `completed`（如 `error`）；
- 最终/错误文本是**提供商侧**的传输或配额故障（HTTP 429、`AccountQuotaExceeded`、HTTP 5xx、timeout）；
- verifier 从未在候选修订上真正运行（无 `verifier_result` / 无真实运行产出的 `checks.json`）。

**必须怎么做**：

1. 保存 API 错误原文、原请求、终止时间，以及**候选是否被改动**的指纹。
2. 无效槽位**单列**（如 `jobs/invalid-slots.json` + `INVALID-SLOTS.md`），**不得改写归档树**——`result.json`、原始日志保持逐字节原样，无效性只在**注解层**表达。
3. 替代轮**绑定同一计划槽位**（同模型别名、同计划顺序、每槽位一轮），不得给某模型额外加权；各模型重试规则统一。
4. 记录**真正执行时**的 runner 源码/版本 SHA，而不是只记录事后打包文件的 SHA。
5. 原始错误不得被覆盖，重复运行不得冒充独立正常生成。

---

## 3. Windows 价值必须真实映射，否则归入通用编码题池

**要求**：**在 Windows 上运行**不等于**测试 Windows 专属能力**。

**必须怎么做**：

1. 把题目要求**逐条映射**到真正依赖的操作系统机制。若核心是纯 Python 字节格式、CRC、异常与流式 IO，且断言不依赖注册表 / NTFS / Win32 / Windows 特有进程语义——这是**通用编码能力**题。
2. 保留通用题时，**明确归入通用编码能力并调整采购分类**，在 `tasks_index.csv` 的 `primary_direction` 等字段与价值说明文档中体现。
3. 若需要 Windows 专属评测，**新增有实际产品需求的 Windows 语义**，发布新版后重新作答。
4. **禁止**只改题名或强加平台标签；**新需求不得追溯扣旧样本**。

**复验通过标准**：分类与采购目标有明确对应；不得用"跑在 Windows 上"充当价值证明。

---

## 4. 声明了权重就必须有证据，否则正式废止

**要求**：评分配置里声明了评审/LLM 权重，就必须有**逐候选的评分证据与合成公式**；不用就正式删除，不能保留"不生效的 50%"。

**必须怎么做**：

1. 区分三个通道：**程序化门禁结果**、**各评审项得分**、**采购最终总分**。
2. 逐候选补齐：评审输入、判定理由、分值、评分器版本、合成公式。
3. 若实际不使用评审项，按正式口径修订配置并写**版本化废止说明**（如 `llm_judge_weight = 0.0` / `programmatic_weight = 1.0` 并注明废止缘由与生效版本）。
4. 历史程序化分**不得冒充**缺失评审后的完整分。

---

## 5. 判分配置必须能被标准解析器读取

**要求**：`tests/judge.toml`、`environment/adapter.toml` 等配置文件**必须能被标准解析器**（如 Python `tomllib`）完整读取。

**必须怎么做**：

1. 按报错行修复 TOML 的转义、引号或注释（典型坑：多行注释续行缺 `#`；Windows 路径反斜杠被当作非法转义）。
2. 用标准解析器读取**整个文件**，并核对必要字段类型与引用的 case ID。
3. 从**正式评分入口**再做一次配置加载与公式核验，并记录生效配置的 SHA。
4. "历史 score 存在" **不能**作为配置可用的证据——某个旧脚本绕过该文件也能出分，不等于交付后的标准入口能加载它。

---

## 6. 公开测试与隐藏验收必须分层，并给出负访问证明

**要求**：模型读到**公开开发测试**不等于读到隐藏验收或参考答案。必须说明测试材料的分层与作答期权限。

**必须怎么做**：

1. **单列三类材料的目录、用途与作答期权限**：公开开发测试、隐藏验收套件、参考解/Golden。
2. 保留必要的公开开发资料，并记录适用的验收口径。
3. 用**运行时权限 / 挂载配置**证明隐藏材料在作答阶段不可达，并归档负访问证据（探针脚本 + 结果）。
4. **禁止**仅凭目录名声明隔离，也**禁止**仅凭"读过公开测试"就定性作弊。

**复验通过标准**：既能证明已公开文件的身份，也能证明隐藏材料在相关阶段不可达。

---

## 7. 复验通过标准（通则）

| # | 标准 |
|---|---|
| 1 | 每条质检意见都有**可复算的证据**（文件、脚本、日志、哈希），不是口头说明 |
| 2 | 整改后**控制系统复现**：Golden 全 1、no-change 全 0，与整改前一致 |
| 3 | 改动过题包内容 → 旧 jobs 的 `task_checksum` 失效 → **必须整批重跑**，不得复用旧轮次 |
| 4 | 区分度按主模型判定（Opus 与 Qwen），辅助模型结论不得替代主判据 |
| 5 | 分类与采购目标有明确对应；不得只改题名或强加平台标签 |
| 6 | 归档为 **archive-only**：只做聚合与注解，不新增执行、评分、run id 或 task checksum |

---

## 8. 现行验收基数：12 个 job（2026-10-13 起）

**要求**：交付包 `jobs/` 下**恰好 12 个** job 目录（每个须含 `result.json`）：

| 类别 | 个数 | 说明 |
|---|---|---|
| Qwen3.8-Max-0902 | 3 | 主难度模型（必需） |
| Opus 5 | 3 | 主难度模型（必需） |
| Oracle 控制轮 | 3 | `agent.name = "oracle"`，须 VALID/1 且 required 全 PASS |
| NOP（no-change）控制轮 | 3 | `agent.name = "nop"`，须 VALID/0、P2P 全 PASS、至少一个 F2P FAIL |

**判据来源**：甲方 `validate_model_jobs.py`：
`expected_jobs = sum(REQUIRED_COUNTS.values()) + 6`，其中
`validate_model_gate.py: REQUIRED_COUNTS = {"qwen": 3, "opus": 3}`。

**GLM / Kimi**：自 **2026-10-13** 起**可选**，既不计入这 12 个、也不参与主判据
（`REQUIRED_COUNTS` 里根本没有 `glm` / `kimi`）。若运行了，只要求"不得有模型无关的
infra/权限/依赖/Verifier 故障"，其结果不得替代 Opus/Qwen 的区分度结论。

> 旧文档里的「14 个 job」「8 轮模型 + 6 轮对照」「GLM ≥1 次 + Kimi ≥1 次必需」
> 均已作废 —— 那是 2026-10-12 及更早批次（含 GLM/Kimi 各 1 轮）的历史口径。
