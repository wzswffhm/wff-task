# wcancel：挂起的异步读取无法精确取消

`wcancel` 是我们采集器的**异步读取层**。大文件会被切成多个重叠（后台）读取请求并行下发，读到一个分片就交付给下游；用户在界面上取消某一个分片时，只有那一个请求应该停下来，其余的必须照常把数据取回来。

## 目标平台（范围声明）

本任务的目标平台是真实的 Windows，验收不使用其他操作系统，也不需要实现其他操作系统的版本。

`wcancel` 的验收建立在真实 Windows 异步 I/O 的取消语义上：「只停掉被点名的那个请求」必须在内核里**真的成立**，评测器会自己持有对象、自己发起挂起读取、自己从另一个线程发起取消，并以内核报告的终态为准，**不采信** `wcancel` 自己的返回值。

跨平台兼容（POSIX 的 `aio_cancel`、`io_uring` 之类）不在验收范围内，也不构成替代实现。

## 现象（仓库 issue #219）

1. **取消一个，停一片**：界面上取消某一个分片，结果同一批下发的读取全部被中止，下游拿到一半数据就断了。
2. **换个线程取消就静默失效**：负责取消的是另一个工作线程，调用看起来返回成功，但请求还在那儿挂着，直到超时才报错。
3. **分不清「取消」和「失败」**：被取消的请求最终以一种普通的 I/O 错误抛出来，调用方无法把它和真正的读失败区分开，于是把用户主动取消记成了故障。
4. **取消已经读完的请求也报成功**：请求其实早就完成了，取消照样返回成功，调用方以为数据被丢弃了。
5. **不支持时不报错**：在不支持后台读取的对象上，模块不报错，退化成同步读取，调用方以为取消能力存在。

## 任务

修复 `wcancel` 包，使其满足下列验收标准。`docs/NOTES.md` 是早期草稿，与 Windows 的实际语义已经不一致，请以本说明的验收标准为准。

## 验收标准

### A. 精确取消（硬门槛）

- `cancel(request)` 必须**只**停止 `request` 指向的那一个挂起请求。
- 同一个对象上由本模块提交的**其它**挂起请求不得受影响：它们必须仍然能够正常完成，并交出与写入内容一致的字节。
- `cancel_all(handle)` 是唯一允许成批停止的入口，它返回被它停止的请求数量。

### B. 取消必须跨线程生效

- 从**任意线程**调用 `cancel(request)` 都必须真的停止那个请求；不得出现「返回成功但请求仍在挂起」的情况。

### C. 被取消的请求有独立终态

- `wait(request)` 对收到取消的请求必须产出 `status == "cancelled"`，`bytes_read` 反映实际完成的字节数。
- 被取消不得等同于普通 I/O 失败：不得以 `WCancelError(kind="os")` 之类的形式上报取消。

### D. 不得谎报取消

- 只有确实发出了取消（请求当时仍挂起）才返回 `True`。
- 对**已经完成**的请求调用 `cancel(request)` 必须返回 `False`；对同一个请求重复调用取消，第二次也必须返回 `False`。

### E. 能力判定

- 对不支持重叠读取的对象，`submit()` 必须抛出 `WCancelError`，且 `err.kind == "unsupported"`；不得静默退化成同步读取。

### F. 错误分类

- 参数或句柄不可用时抛 `WCancelError(kind="badarg")`；底层调用失败抛 `WCancelError(kind="os")`；`wait()` 等待超时抛 `WCancelError(kind="timeout")`。
- 不得出现静默成功，也不得只抛出无分类的 `OSError`。

### G. 不得回归

- 可见冒烟测试 `tests/test_wcancel_basic.py` 必须继续通过。
- 公开 API 的名称与签名保持不变（`submit` / `cancel` / `cancel_all` / `wait` / `Request` / `Completion` / `WCancelError`）。
