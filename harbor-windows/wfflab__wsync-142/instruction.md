# wsync 在企业 Windows 目标环境下的镜像同步失败

## 背景

`wsync` 是备份 Agent 使用的目录镜像同步库：它把一棵源目录树完整复刻到目标目录树——
源里有而目标没有的文件会被创建，内容有变化的会被更新，目标里多出来的会被删除，
同步结束后目标的内容与结构要和源一致。同一份配置在 Linux 备份节点上跑了很久都没问题，
迁到 Windows 服务器之后运维开始持续收到工单。

工单的共同点是：**同一份源数据、同一台机器，在 Linux 上正常的同步，在 Windows 上会中断、
会把文件弄丢、或者让目标留下不该有的东西。**

1. **同步跑到一半停住**

   目标目录往往是从旧备份盘、文件服务器或另一台机器整盘拷过来的，里面残留着不少只读条目。
   只要碰到这种文件或目录，同步就会抛权限错误并中断，排在它后面的文件一个都不处理。
   手工去掉只读属性再重跑就好，但备份任务不能靠人工盯着。
   即使把多余文件删干净了，那些只剩只读属性的空目录还会赖在目标里不走。

2. **同一个文件被来回倒腾，甚至消失**

   源目录里是 `Report.PDF`，目标目录里已经有同名的 `report.pdf`（内容不同）。
   同步跑完之后，目标里那个文件有时内容不对，有时干脆不见了。
   同样的输入在 Linux 上不会出现这个现象。

3. **一个被占用的文件拖垮整次同步**

   目标目录里存在业务程序正打开着的文件（运行中的日志、正在导出的报表等）。
   同步碰到它时直接抛出异常退出：前面已经处理完的条目白做，后面的也都没同步到。
   还有更麻烦的：有些条目既被占用，又带着只读属性。

4. **目标结构要给文件“让位”时就崩**

   源里 `bundle/` 是目录、目标里 `bundle` 是同名文件——同步在这一步直接失败，
   后面所有条目都不再处理；反过来（源里是文件、目标里是一整棵同名目录）同样失败。
   大小写不同也算：源里是 `Data/` 目录、目标里是 `data` 文件，在 Windows 上这是同一条路径。

5. **内容变了却当成没变，改完又白改**

   上游有些工具会就地改写文件并把修改时间戳原样保留。这种文件在源和目标上大小、修改时间
   完全一样，内容却不同，同步会认为“没变化”而放过它，目标上留着的还是旧内容。
   反过来，同步自己写完文件之后不保留源的时间戳，于是第二次同步又认为目标“变了”，
   一遍遍重复做无谓的动作。

## 目标

让 `wsync.sync_tree` 在上面五类真实的 Windows 文件系统状态下都能给出正确结果：

1. 目标里已存在的**只读文件或只读目录**在被覆盖或被删除时，不得阻塞这次同步；
   清空之后残留的目标目录（包括只有只读属性的空目录）必须被清理干净。
2. 当目标平台的文件系统不区分文件名大小写时，源与目标中**只有大小写不同**的两个路径必须被认定为同一个文件，
   并得到正确结果：该保留的条目要保留，该更新的内容要更新，不得出现重复条目或内容丢失。
3. 单个目标条目处理失败（例如被其它进程占用）时，`sync_tree` 不得中断整次同步：
   该条目要出现在返回结果的失败清单里，其余条目继续正常完成。
   纯粹只读的条目属于**可以自动修复**的情况，必须真正完成而不是记成失败。
4. 当源与目标在**同一条路径上的条目类型不同**（一边是文件、另一边是目录）时，
   `sync_tree` 必须先把目标侧的旧条目清掉，再按源的类型和内容落地；
   目标路径的**上级分量**被一个同名文件占住时同样要处理。
   为此所做的清理只允许影响真正构成冲突的那条路径，不得波及其它无关条目。
5. 内容是否需要更新必须依据**内容本身**判定，不得仅凭大小与修改时间就认定“没有变化”。
   同步完成后，目标中每个与源对应的文件的修改时间必须与源一致；
   紧接着再执行一次同样的同步，不得产生任何创建、更新或删除。

## 功能边界

- **需要支持**
  - `sync_tree(source_root, target_root, dry_run=False)` 在上述状态下返回正确的 `SyncResult`
  - 结果对象要能区分“已完成的条目”和“未能完成的条目”
- **不需要处理**
  - 网络共享路径、UNC 路径、超过 `MAX_PATH` 的超长路径
  - 权限提升、UAC、以其它账户身份运行
  - 多个进程同时同步同一个目标
  - NTFS 备用数据流（ADS）、重解析点、符号链接、目录联接

## 约束

- 目标环境：Windows Server 2022（x64），Python 3.12
- 只允许使用 Python 标准库，**不得引入新的第三方运行时依赖**
- 不得改变 `build_plan` / `sync_tree` / `SyncResult` / `Plan` 的公开签名与既有语义
- 不得修改或删除仓库自带的测试，不得为了通过而放宽既有行为
- 必须保持断网可运行

## 允许修改范围

`wsync/` 包内的源码。`tests/` 下只允许新增测试文件，不得改动既有测试。

## 验收标准（用户可见）

1. 目标里存在只读条目时，需要更新或删除它的同步仍能正常完成：文件内容更新为源中的内容，
   目标中多余的文件与目录被删除干净，清空后留下的只读空目录也随之消失。
2. 源与目标只有文件名大小写不同、且内容不同时，同步后该文件存在且内容为源中的内容，
   目标目录里不会因此多出条目、也不会少掉条目。
3. 源与目标只有文件名大小写不同、且内容一致时，同步不产生多余动作：既不更新也不删除。
4. 目标中某个条目被其它进程占用时，`sync_tree` 正常返回而非抛出异常：
   该条目出现在结果的失败清单中且未被删除，同一批次的其它条目正常完成。
   只读的条目如果去掉只读属性后可以完成，就必须真正完成；去掉之后仍然删不掉的条目
   只记失败、不中断整次同步。
5. 同一条路径上源与目标的条目类型不同（文件 ↔ 目录，含仅大小写不同的情形）时，
   同步结束后目标上的类型与内容与源一致，不残留旧条目的内容。
6. 为消解上述类型冲突所做的清理不得波及其它无关条目，只读条目也不例外。
7. 源与目标的文件大小、修改时间都相同但内容不同时，目标内容必须被更新为源中的内容。
8. 同步完成后，目标中与源对应的文件其修改时间与源一致；紧接着再同步一次不产生任何动作。
9. 以上任何情况下，源中只读文件仍然能被正常读取并复制到目标。
