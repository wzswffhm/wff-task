# 打分项规范

打分项 = 一个得分点或扣分点。符合"在实际生产中被要求或有正向收益"的标准则得分；符合"实际生产中应杜绝或避免"的标准则扣分。全部打分项写在题包的 `tests/rubrics.json`。

## 单条字段

```json
{
  "id": "R06",
  "description": "DCF 估值模型中使用的 WACC 取值应落在合理区间 [10%, 12%] 内，越接近得分越高",
  "dimension": "内容质量-数值与计算准确性",
  "criterion_type": "Objective",
  "criterion_necessity": "Explicit",
  "type": "gradient",
  "weight": 7.0,
  "levels": {
    "1": "WACC 落在 [10%, 12%] 区间内",
    "0.75": "WACC 偏离合理区间不超过 ±1%（如 9.0%–9.9% 或 12.1%–13.0%）",
    "0.5": "WACC 偏离合理区间 ±1%–±3%（如 7.0%–8.9% 或 13.1%–15.0%）",
    "0.25": "WACC 偏离合理区间 ±3%–±5%（如 5.0%–6.9% 或 15.1%–17.0%）",
    "0": "WACC 完全未给出，或偏离合理区间超过 ±5%"
  }
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `id` | 题目内唯一 | 如 `R01` |
| `description` | 文本 | 具体的评判标准描述 |
| `dimension` | 一级-二级 | 见下方维度表，二级可为空 |
| `criterion_type` | `Objective` / `Subjective` | Objective = 可度量、可验证，仅凭回答本身即可明确判定；Subjective = 需要打分员的判断与语境解读（语气/质量/风格，或对某理由、断言、示例是否成立的判断） |
| `criterion_necessity` | `Explicit` / `Implicit` | Explicit = 在 prompt 中逐字明文给出的要求；Implicit = 没明说但从语境中必然推导出的要求 |
| `type` | `Binary` / `Gradient` | Binary = 要么满足要么不满足，中间状态无意义；Gradient = 存在程度差异且该差异对最终质量有意义 |
| `weight` | `{+10, +7, +3, -3, -7, -10}` | 不能取任何其他值；正分奖励，负分扣分 |
| `levels` | 仅 Gradient | 五个档位，键为 `0` / `0.25` / `0.5` / `0.75` / `1`，每档给出可观察的判定描述 |

Binary 示例：

```json
{
  "id": "R17",
  "description": "计算2025年盈利净值为50万美元，相较于2024年盈利净值环比增长20%。",
  "dimension": "内容质量-数值与计算准确性",
  "criterion_type": "Objective",
  "criterion_necessity": "Explicit",
  "type": "binary",
  "weight": 3.0
}
```

⚠ 文档中 `criterion_type` 用大写首字母（`Objective`/`Subjective`），`type` 在小节标题里写 `Binary/Gradient`、在示例里写 `binary/gradient`。落盘前确认平台实际解析的大小写口径，并在同一批次保持一致。

## 单条打分项的质量要求

- 原子性：每条只检查一个方面，不把多个独立事实或多个可接受值绑在一条里。
- 准确无歧义：表述完整、事实正确、依据可靠，不同评分者能形成一致理解。
- 客观可验证：优先评价能直接核查的事实、数据、结构和结果；必须评价主观质量时，要转成具体的可观察标准。
- 粒度合理：既不合并多个独立要求，也不把一个完整动作拆成一堆无意义小项。
- 明确打分对象：交付物有多个时，写明本条针对哪个文件/片段。
- 可独立判断：判断所需关键信息都写在条目里，不要求评分者补充标准或二次推导。
- 来源合理：只能来自项目描述中的明确要求、参考文件中的明确要求，或根据任务目标和使用场景可合理推导的隐含要求。不得凭空增加"伪需求"。
- 有明确判定锚点：禁止"语言流畅""结构清晰""内容专业"这类空洞描述。
- 同一角度不得既写得分点又写失分点，否则造成双重得分或双重扣分。

正反例：

| 不推荐 | 推荐 |
|---|---|
| 收入实现了明显增长 | 收入同比增长了 65% |
| PPT 排版美观 | 单页正文不超过 150 字，文本无明显遮挡、重叠或溢出 |

## 打分项之间的关系

- 具有区分度：正分项与负分项的判定边界要明确；`gradient` 项要能区分"部分满足"和"完全满足"，避免不同表现获得相同评价。
- 整体覆盖完整：所有打分项合起来覆盖任务的主要目标和关键能力，从不同维度评价交付物质量，不遗漏关键要求。
- 互不重复、互不冲突：不同打分项评价不同内容，同一问题不被重复计分，判定标准之间不矛盾。
- 判断结果稳定：同一套打分项由不同 Judge 或在不同时间多次评分，结果应基本一致；波动大就要进一步明确描述、判定边界和示例。

拆分示例——"公文是否专业、有条理且合规"应拆为：文种选择是否正确；格式要素是否齐全（标题、主送机关、正文、落款、发文字号等）；请求事项是否明确、是否符合"一文一事"。

## weight 五档

| 级别 | 分数 | 含义 |
|---|---|---|
| Critically Important | +10 | 不满足就是"答错大题"，核心要素 |
| Important | +7 | 明显增色，但不一定是最低标准 |
| Slightly Important | +3 | 细节 / 锦上添花 |
| Slightly Detrimental | -3 | 小错误、小跑题 |
| Detrimental | -7 | 重要错误，但整体还能用 |
| Critically Detrimental | -10 | 致命错误，直接毁掉答案本身，一票否决项 |

同一份打分文件中，各条 weight 应体现其对任务结果的影响程度，避免机械地全部使用同一权重。可以设置合理亮点项（评价项目要求之外、但基于常识会影响用户判断或交付质量的内容），但要有明确价值和依据，不能无限扩展任务范围。

## 评价维度

| 一级维度 | 二级标签 | 主要检查什么 |
|---|---|---|
| 指令遵循【必须】 | — | instruction 中显式要求的任务内容与交付约束是否被完整执行：范围限定、数量、命名、路径、格式、单位、精度，以及明确要求包含或禁止的内容。只检查 instruction 明确提出的要求；内容本身是否正确、专业、深入归入内容质量维度 |
| 内容质量【必须】 | 结论正确性 | 基于已有事实、数据和分析形成的最终判断、结论、推荐或决策是否正确、是否与证据一致、是否存在结论与数据矛盾、方向错误或关键结论遗漏。重点看"最终得出了什么判断"，而非计算过程或论证深度 |
| 内容质量【必须】 | 数值与计算准确性 | 数值提取、公式计算、统计口径、单位换算、聚合方式、分母选择、时间范围、精度及容差是否正确 |
| 内容质量【必须】 | 专业规范 | 内容是否符合所属行业/领域的专业知识、规则、标准和通行实践，包括会计准则、法律规则、医学规范、行业标准、专业术语及业务口径 |
| 内容质量【必须】 | 分析与论证质量 | 论证是否成立、理由与断言是否经得起推敲、举例是否恰当 ⚠ 文档中该行说明与"事实忠实性"重复（PDF 排版问题），按标签名理解 |
| 内容质量【必须】 | 事实忠实性 | 事实、数据和引用是否忠实于输入材料及可验证的客观事实，不无依据地编造、篡改或混淆；引用与来源是否真实可追溯；跨文件处理时是否正确区分主体、版本、时间和统计口径。既查 workspace 内事实，也查任务涉及的外部客观事实 |
| 结构与组织 | — | 信息架构和组织方式是否合理：章节/页面结构是否完整、层级是否清晰、顺序是否符合逻辑、信息分组是否合理、关键模块是否缺失，文字表格图表是否放在合理上下文中 |
| 操作与交付安全 | — | Agent 执行过程中是否安全处理用户已有文件和 workspace：不得误删、覆盖、破坏无关源文件，不得因编辑或格式转换造成数据、公式、页面或其他原有内容意外丢失 |
| 安全合规 | — | 产出内容及执行行为是否满足隐私、数据安全、版权、法律法规及业务合规要求，避免泄露敏感信息、违规使用内容或产生明显误导、偏见及其他实际风险 |
| 超预期贡献 | — | 其他要求都满足之后，进一步提升交付价值的部分，如事实二次核对、指出 instruction 中的隐患、给出更完善的交付物 |
| 视觉美感 | — | 排版、配色等是否让接手交付物的人感到欣赏，偏主观。仅针对有美观度要求的交付物（如 PPT）配置得分点，普通任务不建议包含 |

维度权重策略：内容质量、操作与交付安全应总是较高 weight；PPT 等设计类交付物视觉美感与格式规范维度应较高；行业性突出的交付物专业规范维度应较高；写作类交付物结构与组织维度应较高；数学计算要求高的交付物（如金融场景）数值与计算准确性维度应较高。维度根据任务要求动态调整，不同任务之间要有区分度。

## 分布要求

- 领域锚点占比：内容质量维度（其下所有二级标签）的锚点正分，占全部正分的 30% 以上——即本题对专业性要求很高，不是只靠指令遵循就能满分，要求有较强的领域知识理解。
- 关键项占比：每题至少包含 2 条 `+10`（Critically Important）评分项。
- `-10` 仅用于重大专业错误、幻觉、业务安全、合规风险等真正影响答案可信度的情形，不得滥用。
- 一般来说，指令遵循、结论正确性、分析与论证质量、事实忠实性这些维度总是需要的。
- 行业性突出的交付物应覆盖专业规范维度；PPT 等设计类交付物应覆盖视觉美感与格式规范维度；写作类交付物应覆盖结构与组织维度；数学计算要求高的交付物应覆盖数值与计算准确性维度。

## 计分

正分项 P：`w_i > 0`；负分项 N：`w_j < 0`。

- `s_i`：binary 正分项命中取 `1`，未命中取 `0`；gradient 正分项取实际档位 `∈ {0, 0.25, 0.5, 0.75, 1}`。
- `h_j`：binary 负分项命中取 `1`，未命中取 `0`；gradient 负分项取实际档位 `∈ {0, 0.25, 0.5, 0.75, 1}`。

单题得分 = 正分项加权得分 ÷（全部正分项权重之和 + 负分项命中扣减），即

```text
Score = Σ_{i∈P} (w_i · s_i) / ( Σ_{i∈P} w_i + Σ_{j∈N} (|w_j| · h_j) )
```

⚠ 文档中的公式排版错乱，上式是按各符号定义还原的读法。分母对负分项的确切处理方式（是否取绝对值、是否单独扣减）需与 rewardkit 交付规范核对后再落盘。

三模型平均分 =（score1 + score2 + score3）/ 3。
