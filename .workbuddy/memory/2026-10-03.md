### ★ WSL 长任务反复中断的真正根因（推翻全部旧假设）
- **现象**：harbor 试次每 17–19 分钟被杀；`dockerd` 重启；systemd 单元被 `Stopping ... Deactivated successfully`。
- **误判**：以为是 VM 空闲回收 / 心跳失效 / 后台任务被回收 / 我的调用触发。
- **实测结论**：**Ubuntu 发行版（systemd 实例）被反复关机重启** —— `last -x` 显示 14:03–14:18 间 6+ 次 `shutdown`→`boot`；journal 为**有序关机**（`Reached target shutdown.target` → `systemd-poweroff.service` → `Shutting down`），即有人从 Windows 侧执行 `wsl --terminate`/`--shutdown` 类操作。底层 VM **没**重启（`vmmemWSL` 自 11:41 持续、`dmesg` 首行 11:42、`/proc/sys/kernel/random/boot_id` 不变 —— WSL 发行版共享 VM 内核，发行版重启不改 boot_id，这也是我早先误判"VM 没重启"的原因）。
- **★ 关键操作规律**：**发行版只在有 `wsl.exe` 客户端附着时存活**；客户端一断开，短则 20s 长则 3 分钟即被关机，连带杀掉里面所有进程（harbor/containers/systemd 单元）。之前 12:59–14:03 能稳 64 分钟，是因为当时有 keepalive 客户端一直挂着；三次崩溃（11:26/12:04/13:20）都发生在"我停止调用 → 客户端被回收"之后。
- **★ 正确解法（已验证）**：**把等待写在 WSL 内部**（`wsl -d Ubuntu -u root -- bash -c 'sleep 400; <status>'`），让每个长工具调用全程持有客户端；相邻调用间隔仅数秒，发行版就不会被回收。**绝不能把 `sleep` 放在 Windows 侧的 Git Bash 里**——那段时间没有 WSL 客户端附着，发行版照关。本次用此法连续附着 2h45m，4 个试次全部跑完。
