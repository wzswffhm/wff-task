## 加速克隆 wff-task 仓库到 wff-task-main

**背景**：新环境 `C:\Users\Administrator\Desktop\wff-task-main` 只有一份从旧 zip 解压的
**残缺副本**（`OBM` 仅 10913 文件，缺 `README.md`/`deliverables/`/`harbor-16/`/`harbor-sota/`/`skills/`），
需从 GitHub 重新完整 clone，但直连速度过慢。

### 诊断结论

- **HTTPS 直连 `github.com` 完全不通**（curl 超时，code=000）
- SSH 22 端口可通，但仅 **80–180 KiB/s**
- 本机 **7897 端口有 HTTP 代理**（Clash 默认混合端口）；走代理测速 **9.6 MB/s**
- 关键点：**SSH 不读 `http_proxy`/`https_proxy` 环境变量** → 代理开着也吃不到带宽

### 解法：SSH over HTTP CONNECT 隧道

用 Python 标准库实现最小 HTTP CONNECT 隧道，作为 OpenSSH 的 `ProxyCommand`，
让 SSH 流量经本地代理转发。**保留原有 SSH 免密认证，无需 PAT**。

```bash
git -c core.longpaths=true \
    -c core.sshCommand="ssh -F <临时ssh_config>" \
    clone --progress git@github.com:wzswffhm/wff-task.git <target>
```

### 结果

- **769.98 MiB / 3 分 32 秒**，平均 4.69 MiB/s，峰值 6.16 MiB/s —— **提速 35–50 倍**
- 18862 对象、**12 个 commit 完整历史**（非浅克隆，`fsck` 通过）

### 踩坑记录

1. **`git status` 误报大量 ` D`（文件"已删除"）** —— 实为 Git 读不到 >260 字符深路径，
   `git config core.longpaths true` 后立刻干净。**不是文件真丢，不要急着 reset / 重 clone**。
2. **checkout 后 `.gitignore`、`.workbuddy/memory/2026-09-29.md` 显示 modified** ——
   CRLF/LF 差异（clone 默认 `autocrlf=true`，本仓库约定 `false`）。
   修正：`git config core.autocrlf false` + `git checkout -- <path>`。
3. **`mv .workbuddy` 报 Permission denied** —— 被当前会话占用，改用 `cp -r`。
4. **中文路径在 `git status` 输出中被转义** —— 比对时需 `-c core.quotepath=false`，否则误判"缺失"。

→ 终态 `[]`，正对应 `assert [] == ['Data/report.txt']`。
题面**显式声明**了该要求（目标 4「再按源的类型和内容落地」、验收 5），故**不是过约束**；
Kimi/GLM/Qwen 同一条用例全过。

**为什么加难度无法达成门槛**：条件 1 需要 Opus 更高（已 0，只会更低）；
退到条件 2（双 0 比 testcase 总数）需把 Qwen 压到 <20.3/24 而 Opus 不掉更多，
