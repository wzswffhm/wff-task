# 法律题打包分项设计

> 通用规则（字段约束、权重档位、likert 锚点、维度体系、五项准则）见
> `../delivery/03-rubrics-and-prompt.md`。本文只讲**法律专属检查点与示例**。

## 1. 必须覆盖的维度（法律题）

| 维度 | 是否必须 | 说明 |
|---|---|---|
| 指令遵循 | **必须** | 文件名、路径、字数、格式、必须/禁止包含项 |
| 内容质量-结论正确性 | **必须** | 最终法律判断/建议是否正确、与证据一致 |
| 内容质量-分析与论证质量 | **必须** | 论点有准确论据支撑，给出 ≥2 条有证据支撑的论证路径 |
| 内容质量-事实忠实性 | **必须** | 事实、数据、引用可溯源，无编造 |
| 内容质量-专业规范 | **必须（法律行业性强）** | 法条现行有效、条文定位、请求权基础、术语口径 |
| 内容质量-数值与计算准确性 | 有金额/期限计算时**必须** | 赔偿额、违约金、利息、税费、期间 |
| 内容质量-结构与组织 | 写作类交付物**必须** | 法律意见书四段式等 |
| 操作与交付安全 | 建议 | 源文件未被破坏 |
| 安全合规 | 建议（对外文书**必须**） | 敏感信息脱敏 |
| 超预期贡献 | 可选 | 指出任务书疏漏、补充对照 |
| 视觉美感 | **不建议**（除非明确要求排版） | — |

**权重**：专业规范、数值准确性应给较高 weight；结构清晰但内容错误的答案不得靠结构得分。

## 2. 法律专属检查点（逐条给出可核验写法）

| # | 检查点 | ✗ 空洞写法 | ✓ 可核验写法 |
|---|---|---|---|
| L1 | **法条现行有效性** | "法律分析专业" | "法律意见引用的核心法条应**现行有效且与争点契合**，越准确得分越高"（配 likert 5 档） |
| L2 | **条文定位准确** | "引用准确" | "援引《民法典》第五百八十五条第二款时，**条、款、项定位准确**（写成第五百八十五条或第五百八十六条均不得分）" |
| L3 | **请求权基础匹配** | "论证清晰" | "对争议焦点提出的请求权基础须与事实构成要件匹配；主张违约责任却援引侵权条款视为不匹配" |
| L4 | **判例可核验** | "引用判例充分" | "引用的案号与裁判要旨可在随附材料中核对；**存在虚构案号或伪造裁判理由**则命中负向项" |
| L5 | **事实可溯源** | "事实清楚" | "『A 公司于 2016 年成立』须能在工商档案材料中溯源；溯源不到即视为编造" |
| L6 | **数值准确** | "计算正确" | "赔偿金额合计 = 各项分项之和（±0.01）；万元与元换算正确；违约金上限规则适用正确" |
| L7 | **结构合规** | "结构清晰" | "法律意见书按『事项概述—事实与证据—法律分析—结论与建议』四部分组织，缺任一部分命中负向项" |
| L8 | **脱敏合规** | "注意保密" | "对外文书不得出现身份证号、手机号、银行账号；出现即命中致命负向项" |
| L9 | **交付安全** | "注意文件安全" | "处理完成后 `/app/input_files/` 下源文件仍完整可打开、内容未变" |
| L10 | **字数/篇幅** | "篇幅适当" | "意见书正文 2500–4000 字；超出上限或不足下限命中负向项" |

## 3. likert 锚点样例（法律语境）

### 正向：法条时效性与契合度（weight 7.0）

```toml
[[criterion]]
id = "R06"
name = "R06"
description = "法律意见引用的核心法条应现行有效且与争点契合，越准确得分越高。 评分为 1–5 整数：5=全部核心法条现行有效、版本正确且与争点契合；4=核心法条有效，个别次要法条存在效力或适用瑕疵（不超过 1 处）；3=核心法条有效，但存在 2-3 处效力或适用瑕疵；2=引用了已失效或明显不适用的法条，但主体结论未被推翻；1=引用已失效法条或适用错误，直接支撑了错误结论。 Deliverables to inspect: `output/LAW1-001_法律意见书.docx`."
type = "likert"
points = 5
weight = 7.0
```

### 负向：结论缺乏依据（weight 7.0，negate，按违规程度）

```toml
[[criterion]]
id = "R11"
name = "R11"
description = "给出法律结论但缺少对应的证据或条文支撑。 评分为 1–5 整数，按违规程度判定（negate 条目，Reward Kit 归一化后自动翻转计分）：5=绝大多数结论无任何证据或条文支撑；4=超过半数结论缺少支撑；3=约半数结论缺少支撑；2=仅个别结论缺少支撑；1=所有结论均有证据或条文支撑。 Deliverables to inspect: `output/LAW1-001_法律意见书.docx`."
type = "likert"
points = 5
negate = true
weight = 7.0
```

### 负向：致命错误（weight 10.0，negate，binary）

```toml
[[criterion]]
id = "R15"
name = "R15"
description = "交付物存在致命问题：必交文件缺失、为空或完全不可用；虚构判例案号或裁判理由；或输出未脱敏的身份证号、手机号等敏感个人信息。仅当发现明确证据证明问题存在时判定成立。 Deliverables to inspect: `output/LAW1-001_法律意见书.docx`, `output/LAW1-001_金额测算表.xlsx`."
type = "binary"
negate = true
weight = 10.0
```

### 正向：数值准确性（weight 3.0，binary）

```toml
[[criterion]]
id = "R17"
name = "R17"
description = "民事起诉状载明的诉讼请求金额与合同约定的违约金基数一致，均为人民币 120 万元。 Deliverables to inspect: `output/LAW1-001_起诉状.docx`."
type = "binary"
weight = 3.0
```

## 4. 分布自查清单（法律题）

| 检查项 | 要求 |
|---|---|
| `Critically Important（+10）` 条数 | **≥2** |
| 内容质量维度正分占比 | **≥30%**（全部正分之和为分母） |
| weight 取值 | 仅 `3.0` / `7.0` / `10.0` |
| 负向写法 | `negate = true` + **正** weight（禁止负 weight） |
| likert 条目 | 均写 `points = 5` 且 description 含 5/4/3/2/1 锚点 |
| 每条 criterion | `name == id` 且含 `Deliverables to inspect:` 路径清单 |
| 双重计分 | 同一角度**不得**既有得分点又有失分点 |
| 领域锚点 | 至少若干条明确考察法律专业性（法条时效/条文定位/请求权基础） |

## 5. 参考文件与打分项的对齐检查

每条 **Explicit** 打分项都应能在 `instruction.md` 找到出处；任务书中的**硬性要求**也应有对应 criterion 覆盖。

```
instruction.md 的显式要求  →  criterion（Explicit）
criterion（Implicit）      →  从任务目标与场景可合理推导
无出处的 criterion         →  删除（属"伪需求"）
无 criterion 覆盖的硬约束  →  补 criterion
```

## 6. 与"是否 hack"相关的判分设计

人工质检重点查 hack。以下设计可在 rubric 层面对作弊形成约束：

| 作弊形态 | 对应负向项设计 |
|---|---|
| 编造判例/案号 | 致命负向项：虚构案号或裁判理由（−10） |
| 编造事实/数据 | 事实忠实性负向项：产出表述在源材料中不可溯源（−7） |
| 输出空壳/占位符 | 致命负向项：必交文件缺失、为空或完全不可用（−10） |
| 未脱敏直接落盘 | 致命负向项：含身份证号/手机号（−10） |
| 破坏源文件 | 操作与交付安全负向项（−7） |
| 只完成部分要件却宣称完成 | 指令遵循"数量/覆盖"类负向项（−3 ~ −7） |
