# Skill Dependency 专项（200 条）

## Skill Dependency 类出题（Skill 不可省略）

**目标**：构造**没有 Skill 中的特殊知识 / 行为规则，模型很难正确完成任务**的场景。
Skill 必须包含**特有信息或行为规则**，避免沦为可有可无的 contextual document。

**交付实现见 `../delivery/`**；技能包封装规范见 `../delivery/08-skill-packaging.md`。

### 用途与触发条件

触发词：Skill 依赖题 / Skill 强制题 / SOP 强制 / expected_skill_dependencies / 冲突暂停 / 特化流程 / 阈值映射 / fallback 顺序。

### 判据（一句话判定是否是 Skill Dependency 题）

> **把 `environment/skills/` 整个删掉，任务是否仍然能稳定做对？**
> - 能 → **不是** Skill Dependency 题（skill 只是装饰）
> - 不能 / 极易走错 → 是

配套的 `metadata` 断言：`expected_skill_dependencies` **必须是 `skill_set` 的非空子集**，且该子集中的 skill **确实是失败的必要原因**。

### 三类构造范式

#### 类型一 · 特殊业务规则（冲突暂停）

**Skill 明确规定**：当两个 authoritative source 的关键字段**冲突**时，**禁止自行选择，必须暂停并向用户确认**。

**Task 中主动埋入这种冲突**。模型如果没有真正遵循 Skill → **最终一定会进入错误 branch**。

| 设计要素 | 要求 |
|---|---|
| 冲突位置 | 同一事实分散在 **≥2 个 authoritative source**（Excel / PDF / 邮件 / Markdown / 数据库结果） |
| 冲突性质 | 两个值**对应完全不同的最终答案**（不是无关痛痒的差异） |
| 正解 | 停下 → 明确指出冲突 → 向用户确认（或按 Skill 规定的裁决规则处置） |
| 错解 | 自行选边继续；或"修正"输入；或静默取其一 |

> 关联弱点：**W2 关键冲突下自行选边 / 修改输入**、**W9 Skill 被形式化调用但没有真正改变关键判断**。

**与常规题的边界（重要）**：常规题必须**在任务书中显式给出冲突裁决规则**；本题型相反——**裁决规则只写在 Skill 里**，任务书不提示冲突的存在。

#### 类型二 · 环境特化 SOP

**Skill 定义某个内部流程**，例：

```
Draft → Compliance Review → Manager Approval → Publish
```

**Task 要求完成发布**。如果模型直接 `Draft → Publish`（跳过中间状态），**最终 Workflow State 必须失败**。

| 设计要素 | 要求 |
|---|---|
| 流程状态 | 每一步有**可观察的落盘痕迹**（生成审批记录文件、写入状态字段、产出签核件） |
| 强制点 | 中间步骤产出**后续步骤必需的输入**（不产出则无法继续） |
| 正解 | 严格按 SOP 逐步执行，每步留下落盘证据 |
| 错解 | 跳步直达终态；或声称"已完成审批"但无中间产物 |

> 判分抓手：**终态产物是否存在且内部自洽**（如发布件上带有审批单号、签核日期，且审批记录文件存在）。**不得对"流程顺序"做过程评分**——只判终态产物是否满足 SOP 所要求的可观察结果。

#### 类型三 · 特殊计算 / 判定规则

**Skill 中包含**：**特殊阈值；内部映射规则；自定义字段定义；业务优先级；fallback 顺序**。
要求这些内容**直接影响 final answer**。

| 设计要素 | 要求 |
|---|---|
| 特有规则 | 规则**不能从常识或公开知识推出**（否则 skill 可省略） |
| 影响面 | 规则必须以可核验的方式改变最终交付物中的**具体数值 / 分类 / 排序 / 建议** |
| 正解 | 使用 Skill 给定的阈值/映射/优先级/fallback |
| 错解 | 套用行业惯例阈值、自行外推、沿用旧版方案 |

> 关联弱点：**W11 无据自造数据与口径**。

### 端到端流程

```
① 选定范式（一/二/三，可组合） → ② 设计 skill 特有规则（不可从常识推出）
→ ③ 构造任务与环境（埋冲突 / 设 SOP / 设阈值） → ④ 写 SKILL.md（frontmatter + SOP + 硬规则）
→ ⑤ 写 instruction.md（技能入口 + 显式强调必须走 skill） → ⑥ 产出 golden（严格遵循 skill）
→ ⑦ 设计 rubric（终态产物为判分对象） → ⑧ 交付自检（delivery）
```

#### ①–② 选定范式、设计特有规则

**自检问题**：
1. 规则是否**不能**从常识、公开资料或行业惯例推出？
2. 不遵守规则是否会导致**可核验的错误结果**（而不是"不够好"）？
3. 规则是否**只**写在 SKILL.md 里，任务书不泄露？

#### ③ 构造任务与环境

- 环境：`environment/skills/<skill-name>/`（SKILL.md + scripts/ + references/）+ `environment/input_files/`。
- 冲突类：把同一事实的两个版本分置于不同材料，且**两版都能被读到**。
- SOP 类：设计**终态可观察**的中间产物（审批单、状态文件、签核记录）。
- 阈值类：在源材料里提供**需要按 skill 规则加工的原始数据**（不要直接给出答案值）。

#### ④ 写 SKILL.md

frontmatter（`name` / `description` / `compatibility`）+ 正文 SOP + **硬规则**（"绝不能用别的方式做 X"）。
写法细节 → `../delivery/08-skill-packaging.md`。

**关键**：把"特有行为规则 / 阈值 / 映射 / 冲突处置要求"写进 SKILL.md —— 这就是让 Skill 不可省略的东西。

#### ⑤ 写 instruction.md

- 按 `../delivery/08-skill-packaging.md` §3 列出**全部**可用技能的名称、适用描述、`SKILL.md` 绝对路径、脚本基准目录。
- **显式强调必须走该 skill**（示例见 08 号文档 §3）。
- **不得**泄露哪个技能是必需的、哪个是干扰项。
- **不得**提示冲突的存在、SOP 的中间状态、或阈值规则的内容。

#### ⑥ 产出 golden

golden 必须**严格遵循 skill 的全部特有规则**：
- 冲突类：golden 应体现"指出冲突 + 按 skill 规定的处置方式处理"的终态产物；
- SOP 类：golden 含全部中间产物（审批记录、状态文件）与终态产物；
- 阈值类：golden 使用 skill 给定阈值计算，且过程可追溯。

#### ⑦ 设计 rubric

**只对终态产物判分**，不得对"是否按顺序调用 skill"做过程评分。

| 检查点类型 | 建议写法 |
|---|---|
| 特有规则被应用（阈值/映射/优先级） | binary：交付物中的 X 值等于按 skill 规则计算的 Y（±容差） |
| 冲突被正确处理 | likert 或 binary：产出中明确指出冲突来源，且未自行选边 |
| SOP 中间产物齐备 | binary：中间产物文件存在且内部字段与终态一致 |
| 形式化调用（负向） | negate likert：走了一遍 skill 清单但结论未按 skill 修正，按程度扣分 |
| 自行选边（负向） | negate binary：直接采用冲突双方之一而未说明冲突（−7） |

rubric 通用规则 → `../delivery/03-rubrics-and-prompt.md`；
本题型详细设计与示例 → `本文`。

#### ⑧ 交付自检

跑 `../delivery/` G1–G6 与 17 项自检，外加技能包 9 项自检（08 号文档 §6）。

### metadata 关键字段

```toml
category = "skill-dependency"
skill_set = ["<skill-name>", "<可能的干扰技能>"]
expected_skill_dependencies = ["<skill-name>"]     # 必须是 skill_set 的非空子集
expected_tool_dependencies = ["filesystem", "shell", "python"]
tool_set = ["filesystem", "shell", "python"]
task_complexity = "C2"                              # C1-C5
weakness_tag = ["W09-Skill形式化调用", "W02-关键冲突自行选边"]
```

### 反模式（禁止）

1. **skill 可删除而无影响**（规则能从常识推出 / 规则未被最终产物使用）。
2. **任务书泄露**：提示冲突存在、写明 SOP 中间步骤、写出阈值规则、暗示哪个技能必需。
3. **对流程顺序做过程评分**（"是否按 SOP 顺序调用"）——只判终态产物。
4. 冲突埋得**不影响最终结论**（两个值导致同样答案 → 无法判定）。
5. 冲突类题目在**任务书中给出裁决规则**（那就退化成常规题）。
6. SOP 类**无可观察的中间产物**（无法判定是否跳步）。
7. 阈值类把**答案值直接写在源材料**里（模型无需 skill 即可完成）。
8. `expected_skill_dependencies` 不是 `skill_set` 子集，或与 `skill_set` 完全相等却无任何真实依赖。
9. 技能目录名 / `skill_set` 条目 / `SKILL.md` 的 `name` 三者不一致。
10. Dockerfile 未 `COPY skills/`，或任务书路径与镜像实际路径不一致。
11. 违反 `../delivery/` 的任一硬约束（负 weight、likert 无锚点、criteria 无 name 等）。

## 三类构造范式详解

### 类型一 · 特殊业务规则（冲突暂停）

#### 构造目标

让"遵守 Skill 的冲突处置规则"成为**唯一正确路径**。模型若忽略 Skill，必然进入错误 branch。

#### Skill 侧写法（SKILL.md 正文片段）

```markdown
## 数据冲突处置（硬规则）

本流程涉及两个权威数据源：`ledger.xlsx`（财务登记台账）与 `confirmations/`（对方确认函）。
- 当两者的**关键字段**（金额、日期、数量、比例）不一致时，**禁止自行选择其一**。
- 必须：① 在输出中**明确列出冲突项及两个来源的取值**；② **暂停并向用户提出确认请求**；
  ③ 未经确认不得继续生成依赖该字段的结论。
- 违反本规则产生的任何结论均视为无效。
```

#### Task 侧埋点

| 埋点 | 做法 |
|---|---|
| 冲突分散 | 同一事实在 ≥2 个 source 中取值不同（如台账 120 万 vs 确认函 100 万） |
| 影响面 | 两个取值导致**完全不同的最终答案**（不同的违约金、不同的评级、不同的建议） |
| 可发现性 | 两个 source 都**必须被读到**才能完成任务（否则模型天然只看到一个） |
| 无裁决线索 | 任务书**不提示**存在冲突，也不给出"以哪个为准" |

#### 三种错解（对应判分点）

| 错解 | 表现 | 判分 |
|---|---|---|
| 自行选边 | 直接采用其中一个值继续 | negate binary：−7 |
| 静默补全 | 取平均、取最新、取"更合理"的，不说明 | negate binary：−7 |
| "修正"输入 | 直接改动源材料使之自洽 | negate binary（致命）：−10 |

#### 正解表现

输出中明确列出冲突项与两个取值，说明"因来源冲突需用户确认"，并将依赖该字段的结论**标注为待确认**或按 Skill 规定的处置方式处理。

> **注意**：若任务是**多轮对话**场景，静态 user 多轮数据可作为"用户确认"的载体。

### 类型二 · 环境特化 SOP

#### 构造目标

流程中**缺少任一中间状态则终态失败**。模型若跳过中间步骤走捷径，终态产物必然不满足要求。

#### Skill 侧写法

```markdown
## 发布流程（环境特化 SOP）

本环境的发布流程固定为四态，**不可跳步**：

1. `Draft`    — 起草件，写入 `work/draft.md`
2. `Compliance Review` — 合规复核，产出 `work/compliance_review.md`，须包含复核人、复核日期、结论
3. `Manager Approval`  — 经理签核，产出 `work/approval.json`，须包含审批单号、签核人、签核时间
4. `Publish`  — 发布件，输出至 `/app/output/`，**并在文件内注明审批单号与签核日期**

硬规则：未取得 `approval.json` 中的审批单号，**不得进入 `Publish`**；发布件若不含审批单号视为无效交付。
```

#### Task 侧要求

- 终态产物上**必须携带中间状态的可核验痕迹**（审批单号、签核人、签核日期）。
- 中间产物**本身就是交付物的一部分**（或必须在 `/app/output/` 可见）。
- 逃逸路径必须被堵死：中间字段**无法凭空编造**（单号需与 `approval.json` 一致）。

#### 正解 / 错解

| | 表现 |
|---|---|
| 正解 | 严格四态推进；终态产物含与 `approval.json` 一致的审批单号与签核日期 |
| 错解 A | `Draft → Publish`，发布件无审批单号 |
| 错解 B | 伪造审批单号（与 `approval.json` 不一致或该文件不存在） |
| 错解 C | 声称"已完成复核"，但 `compliance_review.md` 缺失或为空 |

#### 判分抓手

| 判分点 | 写法 |
|---|---|
| 终态含审批信息 | binary：发布件内含审批单号与签核日期，且与 `approval.json` 逐字一致 |
| 中间产物齐备 | binary：`compliance_review.md` 与 `approval.json` 均存在且字段完整 |
| 伪造痕迹 | negate binary：单号与 `approval.json` 不一致或审批文件不存在却声称已批准（−10） |

> **只判终态**：不判"是否按顺序调用了某工具"。过程不可观测，也不应评分。

### 类型三 · 特殊计算 / 判定规则

#### 构造目标

Skill 提供**无法从常识推出**的阈值 / 映射 / 优先级 / fallback，且这些规则**必须改变最终产物**。

#### 四类特有规则

| 类型 | 示例（须与真实业务一致） |
|---|---|
| 特殊阈值 | 风险等级划分不使用行业通行的 90 天，而采用本机构内部口径（如 75 天）；或成本核算采用特定分摊系数 |
| 内部映射 | 内部产品代码 → 会计科目；客户等级 → 审批权限；物料编码 → 成本中心 |
| 自定义字段定义 | "有效口径"定义为剔除冲销与内部往来后的净额，与整池口径不同 |
| 业务优先级 | 同一客户多合同冲突时，按"签署日期 + 金额"的固定优先顺序裁定 |
| fallback 顺序 | 主数据源不可用时，依次回退到 A → B → C，且每次回退需标注口径 |

#### Skill 侧写法（示例）

```markdown
## 内部口径（本环境专用，不得套用行业惯例）

1. 逾期天数 = max(0, 结算日 − 约定付款日)，**不扣除**节假日。
2. 风险分级（内部口径，非行业 90/180 天口径）：
   - ≤75 天：正常
   - 76–120 天：关注
   - >120 天：预警
3. 数据源 fallback 顺序：`core_billing.csv` → `branch_report.xlsx` → `manual_ledger.md`。
   使用非首选项时，**必须在输出中标注所用口径与来源**。
```

#### 判分抓手

| 判分点 | 写法 |
|---|---|
| 阈值正确应用 | binary：分级结果与按内部阈值计算的结果**逐行一致** |
| 映射正确 | binary：科目/权限字段全部按映射表转换，无一行套用通用规则 |
| 重要性权衡正确 | binary：多合同冲突裁定结果与 skill 规定的优先顺序一致 |
| fallback 标注 | binary：使用非首选数据源时已标注来源与口径 |
| 套用惯例（负向） | negate binary：使用行业通行阈值/惯例公式而未按 skill 口径（−7） |

> 关联弱点 **W11 无据自造数据与口径**：正解是**按 skill 口径**，而非"看起来更合理"的自拟口径。

### 组合与选型建议

| 场景 | 推荐范式 | 理由 |
|---|---|---|
| 数据密集 + 多来源 | 类型一（冲突暂停） | 天然存在多源不一致 |
| 有明确业务流程的行业（审批、发文、发布） | 类型二（特化 SOP） | 流程状态可落盘观察 |
| 强计算/分级/映射的领域 | 类型三（阈值映射） | 规则可直接改变数值结果 |
| 高难（A3） | 类型一 + 类型三 组合 | 冲突 + 特有口径双重依赖 |

**复杂度建议**：单题一般 C2–C4；组合范式可到 C4。C5 需配合大 workspace 与多产物（应结合 `05-workflow.md` / `06-weakness-catalog.md` 设计）。

## 设计要点、golden 要求与 rubric 判定

### 1. 设计前自检（三条否决式问题）

| # | 问题 | 不合格表现 |
|---|---|---|
| 1 | 删掉 `environment/skills/` 后，任务是否仍能稳定做对？ | 仍能做对 → 不是 Skill Dependency 题 |
| 2 | 特有规则是否**不能**从常识 / 公开资料 / 行业惯例推出？ | 能推出 → Skill 可省略 |
| 3 | 不遵守规则是否导致**可核验的错误结果**（而非"不够好"）？ | 只影响"质量好坏" → 改造成硬性可核验差异 |

三条全过才算合格题目。

### 2. 强弱依赖分级（用于难度与 weight 设计）

| 级别 | 特征 | 建议 weight |
|---|---|---|
| **强依赖** | 不遵守 → 终态产物**必然错误**（数值错、分级错、缺必需字段） | 特有规则项 +10 或 +7 |
| **中依赖** | 不遵守 → 终态产物**部分错误或不可核验**（缺标注、缺中间证据） | +7 |
| **弱依赖** | 不遵守 → 仅影响完整性或可追溯性 | +3 |

> 只有**强依赖**才能支撑"Skill Dependency 题"的命名；若全为弱依赖，应考虑降级为 Skill Discovery 题。

### 3. 环境与技能包要求

- 技能目录、`metadata.skill_set` 条目、`SKILL.md` frontmatter `name` **三者一致**。
- Dockerfile `COPY skills/ /skills/`，路径与任务书一致；技能依赖写入 `requirements.txt`。
- 以**实际 Agent 用户**验证：技能可读、脚本可执行。

细节见 `../delivery/08-skill-packaging.md`。

### 4. golden 要求

| 项 | 要求 |
|---|---|
| 完整性 | 覆盖 skill 全部特有规则，严格按规则产出 |
| 冲突类 | 明确列出冲突项与两个来源取值，按 skill 规定处置 |
| SOP 类 | 含全部中间产物 + 终态产物，字段互相自洽（单号/日期一致） |
| 阈值类 | 使用 skill 给定阈值/映射，计算过程可追溯（保留中间列） |
| 自检 | 主分 **> 0.85**，且**不得命中任何 negate 条目** |

### 5. rubric 设计

#### 5.1 判分对象

**只对终态产物判分**。不得对"是否按顺序调用 skill""是否读了 SKILL.md"做过程评分。

#### 5.2 推荐条目结构（8–14 条）

| 类别 | 条数建议 | 说明 |
|---|---|---|
| 指令遵循（文件名/路径/格式） | 2–3 | weight 3 |
| **特有规则被正确应用** | 3–5 | weight 7 或 10（本题型核心） |
| 结论正确性 | 1–2 | weight 10 |
| 数值/计算准确 | 1–2 | weight 7 |
| 结构与组织 | 1 | weight 3 |
| 负向：形式化调用 / 自行选边 / 伪造痕迹 / 套用惯例 | 2–3 | negate + weight 7 或 10 |

> 必须满足：`Critically Important（+10）≥2`；内容质量维度正分 ≥30%。

#### 5.3 关键判定句写法

**正向（特有规则被应用）**：

```toml
[[criterion]]
id = "R04"
name = "R04"
description = "风险分级结果全部采用内部口径（≤75 天正常、76–120 天关注、>120 天预警），逐行与内部阈值计算结果一致，未套用行业 90/180 天口径。 Deliverables to inspect: `output/FIN-SKD-001_风险分级表.xlsx`."
type = "binary"
weight = 10.0
```

**正向（冲突被正确处理）**：

```toml
[[criterion]]
id = "R06"
name = "R06"
description = "产出中明确指出 `ledger.xlsx` 与 `confirmations/` 在交易金额上的冲突（120 万元 vs 100 万元），并列明两个来源；未自行选定任一取值。 Deliverables to inspect: `output/FIN-SKD-001_对账说明.docx`."
type = "binary"
weight = 10.0
```

**负向（自行选边）**：

```toml
[[criterion]]
id = "R12"
name = "R12"
description = "直接采用冲突双方之一的取值形成最终结论，而未在产出中说明存在来源冲突。仅当发现明确证据证明该情形存在时判定成立。 Deliverables to inspect: `output/FIN-SKD-001_对账说明.docx`, `output/FIN-SKD-001_金额测算表.xlsx`."
type = "binary"
negate = true
weight = 7.0
```

**负向（SOP 跳步 / 伪造痕迹）**：

```toml
[[criterion]]
id = "R13"
name = "R13"
description = "发布件未包含审批单号，或所含审批单号与 `work/approval.json` 不一致，或 `approval.json` 不存在却声称已获批准。仅当发现明确证据证明该情形存在时判定成立。 Deliverables to inspect: `output/FIN-SKD-001_发布件.docx`."
type = "binary"
negate = true
weight = 10.0
```

**负向（Skill 被形式化调用，按程度扣分 —— 对应 W9）**：

```toml
[[criterion]]
id = "R14"
name = "R14"
description = "产出走了一遍 skill 清单但结论未按 skill 规则修正（如列出冲突后仍按单一口径给出最终结论）。 评分为 1–5 整数，按违规程度判定（negate 条目，Reward Kit 归一化后自动翻转计分）：5=全部结论均未按 skill 规则修正；4=多数结论未修正；3=约半数未修正；2=仅个别未修正；1=所有结论均按 skill 规则修正。 Deliverables to inspect: `output/FIN-SKD-001_对账说明.docx`."
type = "likert"
points = 5
negate = true
weight = 7.0
```

### 6. 定向弱点对照（`weakness_tag` 参考）

| weakness | 本题型中的体现 | 对应 rubric 设计 |
|---|---|---|
| **W2** 关键冲突下自行选边 / 修改输入 | 冲突类题的核心 | 正向"指出冲突且未选边" + 负向"自行选边" |
| **W9** Skill 被形式化调用但没有真正改变关键判断 | 读了一遍 skill 却未按规则修正结论 | 负向 likert"未按 skill 规则修正" |
| **W11** 无据自造数据与口径 | 阈值类题：套用惯例而非 skill 口径 | 负向"套用行业惯例口径" |
| **W13** 规划与策略调整失当 | SOP 类题：跳步直达终态 | 负向"缺中间状态产物" |

### 7. 常见设计陷阱

| # | 陷阱 | 修正 |
|---|---|---|
| 1 | 任务书里顺手写了"注意两份材料可能不一致" | 删除——冲突的存在必须由模型从 skill + 材料自行发现 |
| 2 | 冲突的两个值最终得出相同结论 | 重新设计，使两个值导致不同答案 |
| 3 | SOP 中间步骤无落盘痕迹 | 为每步设计可核验产物（文件/字段） |
| 4 | 阈值写得太"合理"，模型用常识也能撞对 | 采用**反直觉但真实**的内部口径（须有业务依据） |
| 5 | 对流程顺序做过程评分 | 改为只判终态产物 |
| 6 | 干扰技能与必需技能难以区分 | 干扰技能应在**其他能力方向**上"看起来适用"，但不含本题特有的规则 |
| 7 | golden 未按 skill 规则做 | golden 必须与 skill 规则逐条对齐，否则预检不过 |
| 8 | 任务书暗示"必须使用 X 技能" | 只列清单，让模型自行判断（除非题型要求强制，此时应在硬约束段落统一表述，不点名必要性） |
