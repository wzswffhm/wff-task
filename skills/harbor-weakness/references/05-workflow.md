# Workflow Execution 专项（200 + 200 条）

## Workflow Execution 类出题

**目标**：构造**真实存在**的长链路任务——多步骤依赖、多工具协同、branch、async、blocking state、subagent。
数据建设目标是从扩充 **Task Distribution** 转向扩充 **Environment Distribution**。

**交付实现见 `../delivery/`**；技能包（若涉及）封装见 `../delivery/08-skill-packaging.md`。

### 用途与触发条件

触发词：workflow 题 / 依赖链题 / 长链路任务 / subagent 题 / 异步子代理 / dependency-aware / blocking state 恢复。

### 两种形态

| 形态 | 核心 | 判定式 |
|---|---|---|
| **W-A · Dependency-aware Workflow** | 依赖图正确拆解 + 完成状态维护 | 若依赖未满足即执行下游 → 结果必错 |
| **W-B · Subagent Workflow** | 必须回收**多个异步子代理结果**才能完成 Final | 若在主任务结束前不等结果回收 → Final 缺失不可替代信息 |

#### W-A 依赖结构（规范给定）

```
A → B
A → C
B + C → D
D → Final
```

要求模型：
1. 正确拆解 dependency；
2. **维护哪些任务已完成**；
3. **避免提前执行依赖未满足的步骤**；
4. **Final 前确认 dependency 已全部完成**。

#### W-B 设计要求

- 各子 Agent 分别掌握**不可替代**的一部分信息（缺任一条 Final 不可能正确）；
- 子任务结果**必须延迟可得**（不是同步即返）；
- 最终交付必须整合全部子结果（无法用局部结果凑出）。

### 端到端流程

```
① 选定形态（W-A / W-B） → ② 画依赖图或子任务信息切分 → ③ 设计可观察的中间状态与交付物
→ ④ 构造环境与源文件 → ⑤ 写 instruction.md（含长链路要求与状态表要求）
→ ⑥ 产出 golden（含中间状态表与终态产物） → ⑦ 设计 rubric → ⑧ 交付自检（delivery）
```

#### ①–② 选定形态、设计依赖结构

**W-A**：设计 3–5 层的依赖链，其中至少一处为**汇聚点**（`B + C → D`）。
关键要求：**上游缺失则下游不可判定**（不是"可选优化"，而是硬依赖）。

**W-B**：把完成任务所需信息**切分成 k 份**（k = 3–5），每份由一个子任务负责，
且每份**都不可替代**；Final 必须整合全部 k 份。

#### ③ 设计可观察的中间状态与交付物

| 设计点 | 要求 |
|---|---|
| **状态表** | 交付物之一为"任务拆解与完成状态表"（.xlsx/.md）：子任务、依赖、状态、产出路径 |
| **中间产物落盘** | 每个已完成子任务都产出**可核验的文件**（不是仅仅"在回答里说完成了"） |
| **终态可核验** | Final 产物须引用/整合全部中间产物（如汇总表包含每个子任务的字段） |
| **断点与恢复** | 至少埋一处**必须换策略而非重试**的阻塞（可选，见 `06-weakness-catalog.md` W3） |

> 判分靠**可观察状态**：不能对"思考顺序"评分，只能对"落盘状态与终态产物"评分。

#### ④ 构造环境与源文件

- 文件数量按复杂度要求（C1 2 个 → C5 50+；见 `../delivery/` 对应的 C 级表，完整表在 `07-complexity-scales.md`）。
- 各子任务的输入材料**尽量隔离**（不同文件簇），使"只读一部分就出结论"必然出错。
- 若涉及 subagent，在环境与任务书中**明确声明**可用的子代理能力与调用方式。

#### ⑤ 写 instruction.md

除 `../delivery/` 的通用要求外，本型必须写明：

1. **任务拆解要求**：要求交付"任务拆解与完成状态表"（含子任务、依赖关系、完成状态）。
2. **依赖约束**：显式说明"某些步骤必须在其他步骤完成后才能开始"（但**不给出解法路径**）。
3. **Final 要求**：明确 Final 必须整合哪些部分（不说明如何整合）。
4. **（W-B）子任务要求**：若涉及子代理，说明"部分信息需通过独立子任务分别获取"。

⚠️ **不得**给出：依赖图的现成答案、子任务应如何切分的答案、Final 的组装方式。

#### ⑥ 产出 golden

- 交付物包含：① **任务拆解与完成状态表**；② 各中间产物；③ Final 产物。
- 状态表中每个"已完成"的子任务都必须能在 `/app/output/` 找到对应产物。
- 主分 **> 0.85**，不命中任何 negate 条目。

#### ⑦ 设计 rubric

| 判分维度 | 抓手 |
|---|---|
| 依赖拆解正确 | 状态表中的依赖关系与正解一致（不多不少） |
| 完成状态维护 | 标记"已完成"的子任务均有对应落盘产物且内容非空 |
| 未提前执行 | 下游产物的内容确实**引用了上游产出**（而非凭空生成） |
| Final 完整性（W-A） | Final 覆盖全部上游结果 |
| **Final 完整性（W-B）** | Final 整合了**全部**子任务结果（缺任一即扣分） |
| 负向：空壳状态表 | 状态表声称完成但无对应产物（−10） |
| 负向：派发即完成（W-B） | Final 未包含子任务结果即宣告完成（−10） |
| 负向：缺 Final | 只交了中间产物（−10） |

详细设计与示例 → `本文`。

#### ⑧ 交付自检

跑 `../delivery/` G1–G6 与 17 项自检。

### 反模式（禁止）

1. **依赖是"假依赖"**：上游缺失时下游仍可独立完成（那就不是依赖链题）。
2. **依赖图写在 instruction 里**（给出答案，考察失效）。
3. **无可观察的中间状态**——只要求"最后交一份报告"，无法判定是否跳步。
4. **对思考顺序评分**（judge 看不到轨迹，也不应判过程）。
5. W-B 中子任务信息**可被单一来源替代**（子代理变得可有可无）。
6. W-B 中子任务结果**同步即得**（不构成异步回收考点）。
7. Final 只需整合部分子结果即可通过（考点落空）。
8. 用"文件多"冒充复杂度（文件多但无需跨文件推理 → 实际是 C1）。
9. 违反 `../delivery/` 的任一硬约束。

## W-A · Dependency-aware Workflow 构造详解

### 1. 依赖结构（规范给定，作为设计蓝本）

```
A → B
A → C
B + C → D
D → Final
```

| 节点 | 含义 | 设计要点 |
|---|---|---|
| **A** | 起点任务（如拉取/清洗基础数据） | 产出被 B、C 共同依赖 |
| **B** | 分支任务 1 | 只依赖 A，可与 C 并行 |
| **C** | 分支任务 2 | 只依赖 A，可与 B 并行 |
| **D** | 汇聚任务 | **同时依赖 B 和 C**；缺一不可 |
| **Final** | 终态交付 | 依赖 D 完成 |

> 实际题目可扩展为 5–7 个节点，但**必须保留至少一个汇聚点（多输入合一）**。

### 2. 依赖必须"真"（核心判据）

> **判据**：若上游产物缺失或错误，下游产物**是否必然错误或无法生成**？
> - 是 → 真依赖
> - 否（下游可独立完成） → 假依赖，需重设计

#### 造成真依赖的三种手法

| 手法 | 做法 |
|---|---|
| **数据依赖** | 下游计算的输入值只存在于上游产物中（源文件里没有） |
| **口径依赖** | 上游产出了下游必须使用的口径/映射（如系数、分类规则），源文件不直接提供 |
| **结构依赖** | 下游的表结构/章节构成由上游结果决定（如上游产出 N 个类别，下游须逐类填充） |

### 3. 状态可观察化（判分的基础）

**交付物之一：任务拆解与完成状态表**

| 子任务 | 依赖 | 状态 | 产出路径 |
|---|---|---|---|
| A | — | 完成 | `output/step_a.csv` |
| B | A | 完成 | `output/step_b.xlsx` |
| C | A | 完成 | `output/step_c.xlsx` |
| D | B, C | 完成 | `output/step_d.xlsx` |
| Final | D | 完成 | `output/<TASKID>_最终报告.docx` |

**要求**（写进 instruction.md）：

1. 状态表须列出**全部子任务**及其依赖关系；
2. 状态列取值受限于 `完成 / 进行中 / 未开始`；
3. 标记为"完成"的子任务，其产出路径**必须真实存在且内容非空**。

> 该表让"是否提前执行""是否漏步骤""是否空壳完成"变成**可核验的事实**，而不是对过程的猜测。

### 4. "未提前执行"的判定

**正解特征**：下游产物中可观察到**上游产出的痕迹**：

| 节点 | 可观察痕迹 |
|---|---|
| D | D 的产物中包含 B 与 C 各自独有的字段/类别/数值 |
| Final | Final 中引用了 D 的汇总值（数值一致，可对账） |

**错解特征**：

- D 的产物**直接由源文件推出**（未使用 B/C 中间结果）——说明跳过了中间步骤，或中间步骤是冗余的；
- Final 的数值与 D 不一致（说明未真正整合）。

> 若 D 可由源文件直接推出，说明**依赖设计不真**，必须重设计（见 §2）。

### 5. 完整设计示例（金融对账场景）

| 节点 | 任务 | 输入 | 产出 |
|---|---|---|---|
| A | 清洗并合并三个分行的流水文件 | `branch1.csv`, `branch2.csv`, `branch3.xlsx` | `step_a_merged.csv`（统一列名、剔除冲销） |
| B | 按客户维度聚合应收 | `step_a_merged.csv` | `step_b_receivable.xlsx` |
| C | 按账龄维度计算逾期天数 | `step_a_merged.csv` | `step_c_aging.xlsx` |
| D | 交叉核对 B 与 C：同客户同账龄段金额须一致，差异写入差异表 | `step_b`, `step_c` | `step_d_reconcile.xlsx` |
| Final | 出具差异分析报告，逐条说明差异原因与处理建议 | `step_d` | `<TASKID>_差异分析报告.docx` |

**真依赖体现**：
- B、C 都只能基于 A 清洗后的统一口径（源文件列名不一致、含冲销行 → 不先做 A 会算错）；
- D 必须**同时**拿到 B 的客户聚合与 C 的账龄分档才能交叉核对；
- Final 的差异条目数必须等于 D 中的差异条数。

### 6. instruction.md 片段示例

```markdown
## 任务说明

你需要基于三个分行的交易流水，完成一次跨维度的应收对账，并出具差异分析报告。
部分步骤之间存在先后依赖：**必须先完成前置步骤、且前置产物内容正确，后续步骤才可能得到正确结果**。
请自行判断依赖关系与执行顺序。

## 交付物要求

交付物必须写入 `/app/output/`，不要把产物写到任何其他绝对路径。

| 交付物 | 是否必交 | 说明 |
| --- | --- | --- |
| `FIN-WF-001_任务拆解与状态表.xlsx` | 必交 | 列出全部子任务、其依赖关系、当前状态与产出路径；状态取值仅限「完成/进行中/未开始」 |
| `FIN-WF-001_差异分析报告.docx` | 必交 | 最终交付物，逐条说明差异原因与处理建议 |

硬约束：

1. 状态表中标记为「完成」的子任务，其产出路径必须真实存在且内容非空。
2. 中间产物须保留在 `/app/output/` 下，不得只保留最终报告。
3. 差异分析报告中的差异条数必须与中间交叉核对结果一致。
```

> **注意**：instruction 说明了"存在依赖""要交状态表""要保留中间产物"，
> 但**没有**给出依赖图、没有给出执行顺序、没有给出差异条数——这些是要考的。

### 7. 复杂度调节

| 旋钮 | 低（C2–C3） | 高（C4–C5） |
|---|---|---|
| 节点数 | 3（A→B→Final） | 6–8，含 2 个汇聚点 |
| 源文件数 | 3–5 | 25–50+ |
| 分支并行度 | 1 条链 | 3–4 条并行分支 |
| 是否含阻塞恢复 | 否 | 是（某步需换策略，见 W3） |
| 是否含冲突 | 否 | 是（上游两源冲突，见 W2） |

> 与 `06-weakness-catalog.md` 组合可同时命中多个弱点（如 W4 需求覆盖 + W13 规划失当），但**每题的 `weakness_tag` 必须与实际埋点一一对应**。

## W-B · Subagent Workflow 构造详解

### 1. 构造目标

**必须依赖多个 Subagent Result 才能完成 Final 的任务。**
各子 Agent 分别掌握**不可替代**的一部分信息。

> 直接对应缺陷 **W8：启动 Subagent 后把"已派发"当成"已完成"**——
> 模型能正确拆任务并启动多个研究 Agent，却在异步结果返回前直接结束主任务，没有等结果回收。
> 该类任务在现有数据中**非常缺少**，是高价值补充方向。

### 2. 三个必要条件（缺一即不成立）

| # | 条件 | 说明 |
|---|---|---|
| 1 | **信息不可替代** | 每个子任务掌握的信息**无法由其他子任务或源文件推导**；缺任一份 → Final 必然不完整/错误 |
| 2 | **结果延迟可得** | 子任务结果**不是同步即返**（体现等待与回收的语义） |
| 3 | **必须整合** | Final 的合格性依赖**全部** k 份结果（不存在"用其中 2 份也能交差"） |

### 3. 信息切分方法

把完成任务所需的**判据**切成 k 份（k = 3–5）：

| 切分维度 | 示例 |
|---|---|
| **按主题** | 分别研究行业政策 / 上游供给 / 下游需求 / 竞争对手 |
| **按数据源** | 分别从年报 / 研报 / 内部纪要 / 公开数据库获取证据 |
| **按地区/事业部** | 分别汇总各区域口径，Final 需合并 |
| **按结论要素** | 分别产出市场规模、增长率、毛利率、风险点四项，缺一不可 |

**反例（不合格）**：把"写报告"切成"写第一章/第二章"——章节之间无不可替代的信息依赖，模型可以只写一半也算有产出。

### 4. 任务书设计

#### 必须写明

1. 本任务的部分信息**需要通过相互独立的子任务分别获取**；
2. 每个子任务的结论**不可由其他来源替代**；
3. Final 必须**整合全部子任务结果**（并逐项注明来源）；
4. 若环境支持子代理：说明可用的子代理能力与调用方式（**不得**说明应如何切分）。

#### 不得写明

- 子任务应如何切分；
- 每个子任务应产出什么；
- Final 的组装方式；
- "记得等待子任务返回"这类提示（那正是考点）。

#### instruction 片段示例

```markdown
## 任务说明

你需要完成一份《白银供给、回收率与回收技术综合研究》。研究中涉及的若干关键信息
**无法在同一份材料中同时获得**，需要通过相互独立的调查分别取得，且各部分结论
**不可相互替代**。最终报告须整合全部调查结果，并逐项标注结论来源与证据强度。

## 交付物要求

| 交付物 | 是否必交 | 说明 |
| --- | --- | --- |
| `FIN-WF-002_综合研究报告.docx` | 必交 | 最终交付物，须覆盖全部调查维度，每条结论标注来源 |
| `FIN-WF-002_调查记录表.xlsx` | 必交 | 逐条记录每项调查的目标、状态、结论摘要与证据出处 |

硬约束：

1. 综合研究报告必须覆盖 `调查记录表` 中登记的全部调查项，不得遗漏任何一项。
2. 调查记录表中标记为「已完成」的调查项，其结论摘要须与该调查的原始材料一致，可核验。
3. 报告中每条关键结论必须标注其证据出处；无出处的结论不计入覆盖度。
```

### 5. 判分抓手（W8 定向）

| 判分点 | 抓手 | 建议写法 |
|---|---|---|
| **Final 覆盖全部子任务** | Final 中的结论条目 ↔ 调查记录表的调查项 | likert：5=全部覆盖且各有出处；… ；1=仅覆盖 ≤1 项 |
| **未"派发即完成"** | Final 中是否包含**每个**子任务的独有结论 | negate likert：按缺失项数分档扣分 |
| **证据可核验** | 每条结论的来源可在源材料或子任务产物中溯源 | binary：存在无出处结论即不合格 |
| **记录表非空壳** | 标记"已完成"的项有对应结论摘要与实际证据 | negate binary：空壳记录（−10） |

### 6. 环境侧支持

| 项 | 做法 |
|---|---|
| 子代理能力声明 | 任务书说明可用子代理，并给出调用方式（若环境提供） |
| 延迟语义 | 若平台支持，子任务结果通过文件/队列延迟落盘，模型需主动回收 |
| 分簇输入 | 各子任务所需的源材料放在**不同的文件簇**中，避免"读一个文件全知道" |
| 记录表模板 | 可选：在 `input_files/` 提供空的调查记录表模板（列名固定，便于判分） |

### 7. 与 W-A 的关系

| | W-A Dependency-aware | W-B Subagent |
|---|---|---|
| 依赖对象 | 上游**步骤**的产物 | 多个**并行子任务**的结果 |
| 关键缺陷 | 跳步 / 提前执行 | **派发即完成 / 不等回收** |
| 典型交付物 | 任务拆解与完成状态表 + Final | 调查记录表 + 综合报告 |
| 可否组合 | 可以：并行分支由子代理承担（A → {B,C,D 并行子任务} → 汇聚 → Final） |

> 组合形态可同时命中 **W8 + W13**，是 C4–C5 高难题的推荐结构。

## Workflow 类 rubric 设计与 golden 要求

### 1. 判分基本原则

| 原则 | 说明 |
|---|---|
| **只判落盘状态与终态产物** | judge 看不到 agent 执行轨迹；**不得**对"思考顺序""是否并发调用"评分 |
| **以状态表为索引** | 状态表是"可核验事实"的入口：标记完成的项必须有对应产物 |
| **依赖关系可核验** | 下游产物中应能观察到上游产出的痕迹（字段/类别/数值） |
| **覆盖度可计数** | Final 覆盖的条目数应与状态表登记数一致 |

### 2. golden 要求

| 形态 | golden 内容 |
|---|---|
| W-A | 任务拆解与状态表 + 全部中间产物（`step_a/b/c/d`）+ Final |
| W-B | 调查记录表 + 各子任务结论摘要 + 综合研究报告 |

共同要求：
- 状态表中"完成"项**都有真实非空产物**；
- Final 覆盖全部上游/子任务结果；
- 主分 **> 0.85**，不命中任何 negate 条目；
- 与 `instruction.md` / `[[metadata.deliverables]]` 的文件名一致，同步复制到 `tests/__golden_output/`。

### 3. 判分抓手矩阵

| # | 判分点 | 形态 | 建议 type | 建议 weight |
|---|---|---|---|---|
| 1 | 状态表存在且列出全部子任务与依赖关系 | 通用 | binary | 7 |
| 2 | 标记"完成"的子任务均有真实非空产物 | 通用 | binary | 7 |
| 3 | 下游产物引用了上游产出（真依赖而非跳步） | W-A | binary | 10 |
| 4 | Final 覆盖全部上游结果 | W-A | likert | 10 |
| 5 | Final 覆盖全部子任务结论（含出处） | W-B | likert | 10 |
| 6 | 结论出处可溯源 | W-B | binary | 7 |
| 7 | 中间产物齐备 | 通用 | binary | 7 |
| 8 | 数值/口径在 Final 与中间产物间一致 | 通用 | binary | 7 |
| 9 | 负向：空壳状态表（声称完成但无产物） | 通用 | negate binary | 10 |
| 10 | 负向：派发即完成（未回收结果即宣告完成） | W-B | negate binary | 10 |
| 11 | 负向：缺 Final（只交中间产物） | 通用 | negate binary | 10 |
| 12 | 负向：跳步（下游未使用上游产出） | W-A | negate likert | 7 |
| 13 | 负向：未按依赖顺序导致结果错（数值/分类错误） | W-A | negate likert | 7 |

> 必须满足 `Critically Important（+10）≥2` 与"内容质量维度正分 ≥30%"。

### 6. 定向弱点对照

| weakness | 本题型中的体现 | 判分设计 |
|---|---|---|
| **W8** 启动 Subagent 后把"已派发"当成"已完成" | W-B 核心 | 负向"派发即完成"（−10）+ Final 覆盖度 likert |
| **W4** 多要求/多交付物下缺少 Requirement Coverage Accounting | 状态表子任务漏项、Final 漏条目 | 状态表完整性 + 覆盖度 likert |
| **W13** 规划与策略调整失当 | 缺少任务拆解；在失败处反复重试 | 状态表存在性 + 依赖拆解正确性 |
| **W3** 阻塞状态识别与恢复差 | 某步资源缺失时强行闭环（伪完成） | 负向"空壳完成"+ 中间产物质量 |

### 7. 常见陷阱

| # | 陷阱 | 修正 |
|---|---|---|
| 1 | 依赖是假的（下游可独立完成） | 用"数据/口径/结构依赖"三种手法重建 |
| 2 | instruction 给了依赖图 | 删除；只说明"存在依赖"，不给图 |
| 3 | 状态表列名过自由，判分困难 | 在 `input_files/` 提供固定列名的空模板 |
| 4 | 判"是否并发调用子代理" | 改为只判终态覆盖度与记录表状态 |
| 5 | W-B 子任务信息可被单一来源替代 | 按 §2 三个必要条件重设计 |
| 6 | Final 只需整合部分子结果即可通过 | 提高覆盖度门槛到"全部" |
| 7 | 用文件数冒充复杂度 | 按 C1–C5 硬指标（文件数 + 约束数 + 证据链 + 步数）分级 |
| 8 | 负向项重叠（空壳 + 缺 Final 实为同一问题） | 拆分为互不重复的判定角度 |

## MCP Scaling（低优，机动配额）

### 1. 目标

扩大模型在 **非原生工具、陌生 Tool Schema、不同 Tool 组合**下的泛化能力。
与 W-A / W-B 的区别：W-A / W-B 考**编排能力**，MCP Scaling 考**工具契约的阅读与适配能力**。

### 2. 硬性要求

| # | 要求 |
|---|---|
| 1 | 每条任务**必须显式提供**当前 Environment 下可用的工具集合 / MCP 清单 |
| 2 | 工具可以是**框架已有能力**，也可以是**动态注入的自定义工具**；注入时须在题面显式说明 |
| 3 | 可用工具集与 `metadata.tool_set` / `expected_tool_dependencies` **逐一对应** |
| 4 | 可执行性：每条任务须在 `environment/` 中提供工具的**真实实现**（MCP server 或脚本），不得只写说明 |

### 3. 三个维度（选其一或组合）

| 维度 | 手法 | 示例 |
|---|---|---|
| **非原生工具** | 完成核心步骤必须用一个非常规工具，而非 `read_file` / `shell` | 必须通过 `fetch_ledger_snapshot` 取数，本地无源文件 |
| **陌生 Schema** | 工具名与参数名**不符合常规直觉**，迫使模型读 schema 而非猜测 | `qp_agg(entity, period_span, basis="accrual")` 而非常见的 `query(table, where)` |
| **工具组合** | 需串联 2–3 个工具，且**中间结果格式不兼容**，必须做一次转换 | `extract_pdf_table` 输出 JSONL → `normalize_fx` 只接受 CSV → 须先转格式 |

### 4. 难度旋钮

| 旋钮 | 低 | 高 |
|---|---|---|
| 工具种类数 | 2 | 5+ |
| Schema 陌生度 | 参数名接近惯例 | 参数名 + 取值语义均需读 schema 才知 |
| 组合链长 | 1 次调用 | 3–4 次串联 + 1 次格式转换 |
| Schema 文档可得性 | 题面附完整参数说明 | 仅提供 schema 名称，说明在 `environment/` 内某文件中 |

### 5. rubric 抓手

| 情形 | 判分设计 |
|---|---|
| 正确使用注入工具 | binary 正向：产物含该工具特有的返回字段（此字段无法由其他途径获得） |
| 绕过工具自行造数 | binary 负向（negate）：产物数值与环境内数据不一致，说明未真实调用工具 |
| Schema 误用 | likert 负向：按参数误用次数分档 |
| 组合链断裂 | likert 负向：按中间格式转换缺失程度分档 |

### 6. 陷阱

| # | 陷阱 | 修正 |
|---|---|---|
| 1 | 只换工具名，语义完全等同原生工具（无泛化价值） | 让 Schema 的**取值语义**也必须读文档才知 |
| 2 | 工具未真实实现，模型只能猜 | 在 `environment/` 装配可执行实现并在镜像自检中验证 |
| 3 | 题面泄漏工具用法（等于把 schema 抄给模型） | 题面只给工具名与用途，参数细节放 `environment/` 内文档 |
| 4 | 用工具数量冒充复杂度 | 按上表四旋钮 + C1–C5 硬指标判定 |
| 5 | `tool_set` 与实际装配不一致 | 打包前用 `../delivery/` 的打包清单复核 |
