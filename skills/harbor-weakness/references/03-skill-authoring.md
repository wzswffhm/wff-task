# Skill Generation / Editing 专项（200 条）

## Skill Generation / Editing 类出题

**目标**：构造要求模型**产出或改造一个 Skill 包**的任务——创建、修改、从 SOP 抽取、迁移、修复。

**交付实现见 `../delivery/`**；技能包的标准结构与写法见 `../delivery/08-skill-packaging.md`。

### 用途与触发条件

触发词：skill 生成题 / skill 编辑题 / SKILL.md 生产 / SOP 抽取 skill / skill 迁移 / skill 修复 / skill package repair。

### 与另两个 Skill 类题型的边界

| 题型 | 环境中 | 模型要做的 |
|---|---|---|
| Skill Discovery | 已装多个技能 | **判断**是否需要 / 用哪个 |
| Skill Dependency | 已装必需技能 | **遵循**技能的特有规则完成任务 |
| **Skill Generation / Editing（本型）** | **不要求**预装相关技能 | **产出/改造技能包本身** |

> 本型的交付物就是 **Skill 包**（`SKILL.md` + `scripts/` + `references/`），不是"用了技能的产物"。

### 五类任务形态

| 代号 | 形态 | 输入 | 交付物 | 核心考点 |
|---|---|---|---|---|
| **S1** | 创建 Skill | 需求描述 / 业务规则材料 | 新技能包目录 | 触发语义、SOP 完整性、特有规则可依赖 |
| **S2** | 修改已有 Skill | 已有技能包 + 变更要求 | 更新后的技能包（+ 变更说明） | 精准改动、不破坏原有约束、兼容性一致 |
| **S3** | 从 SOP 抽取 Skill | 长 SOP 文档 / 制度文件 | 结构化技能包 | 信息浓缩不失真、可执行化、含条件分支 |
| **S4** | Skill migration | 旧格式技能包 | 新格式技能包 | 语义无损迁移、结构合规、行为等价 |
| **S5** | Skill package repair | 损坏的技能包（缺字段/结构错/脚本报错） | 修复后的技能包 + 修复说明 | 定位缺陷、最小修复、不引入新问题 |

### 端到端流程

```
① 选定形态（S1–S5） → ② 准备输入材料 → ③ 明确验收标准（结构 + 内容 + 可执行）
→ ④ 写 instruction.md → ⑤ 产出 golden 技能包 → ⑥ 设计 rubric → ⑦ 交付自检（delivery）
```

#### ① 选定形态

优先选择**真实业务中会发生**的形态：
- 企业把内部 SOP 沉淀为可复用技能（S3）→ 高频且真实；
- 技能格式升级（S4）→ 真实但需注意"新旧格式"要对得上真实版本演进；
- 修复坏包（S5）→ 真实（合入他人提交的技能时常见）。

#### ② 准备输入材料

| 形态 | 输入材料 |
|---|---|
| S1 | 业务规则说明（.md/.docx）、样例数据、期望触发场景描述 |
| S2 | 现有技能包（完整可运行）+ 变更需求单 |
| S3 | 长 SOP / 制度文件（**信息量要足够大，需要取舍与结构化**） |
| S4 | 旧格式技能包 + 新格式规范说明 |
| S5 | 带缺陷的技能包（缺陷须**可复现且可定位**）+ 现象描述（如"执行报错""技能未被识别"） |

放入 `environment/input_files/`。

#### ③ 验收标准（三类）

| 类别 | 检查点 |
|---|---|
| **结构** | 目录结构合规（`<skill-name>/SKILL.md` + 可选 `scripts/`、`references/`）；frontmatter 三字段齐备（`name` / `description` / `compatibility`）；`name` 与目录名一致且符合小写连字符命名 |
| **内容** | `description` 写清"何时该用"（触发语义可辨识）；SOP 分步、含**条件分支**与**完成检查**；含**特有规则**（阈值/映射/优先级/fallback）而非泛泛而谈；失败恢复路径完整 |
| **可执行** | `scripts/` 下脚本语法正确、可运行、参数与 SKILL.md 记载一致；`compatibility` 与依赖实际一致 |

#### ④ 写 instruction.md

- 交付路径固定 `/app/output/`；交付物为该技能包目录（`path` 可写目录层级，如 `<skill-name>/SKILL.md`）。
- 明确写出命名要求（技能名）、格式要求（Anthropic Skill 格式）、必须包含的要素。
- **不得**泄露 golden 内容或"评分将检查……"。
- ⚠️ **不要**在 instruction 中把"该创建什么内容"写成可照抄的成品（要给需求，不给答案）。

#### ⑤ 产出 golden

- golden 为一套**完整可用的技能包**，放入 `solution/golden_output/`。
- 要求：结构合规、frontmatter 完整、SOP 可执行、特有规则明确、脚本可运行。
- S2/S4/S5 的 golden 还应包含**变更/修复说明**（交付物之一）。
- 主分 **> 0.85**，且不命中任何 negate 条目。

#### ⑥ 设计 rubric

判分对象是**产出的技能包**（判官可直接读目录与文件）。

| 判分维度 | 说明 |
|---|---|
| 文件与结构 | 交付物存在、目录层级正确、命名合规 |
| frontmatter | 三字段齐备、`name` 与目录一致、`description` 含触发语义 |
| SOP 质量 | 分步、含条件分支、含完成检查、含失败恢复 |
| 特有规则 | 含可依赖的阈值/映射/优先级/fallback（**不是泛泛描述**） |
| 脚本可用 | 语法正确、能运行、与 SKILL.md 记载一致 |
| 迁移/修复正确性（S4/S5） | 语义无损、缺陷被修复、未引入新问题 |
| 负向 | 照抄输入材料原文（未结构化）、frontmatter 缺失、脚本报错、编造依赖版本 |

详细设计与示例 → `本文`。

#### ⑦ 交付自检

跑 `../delivery/` G1–G6 与 17 项自检。

### metadata 关键字段

```toml
category = "skill-generation"      # 或 skill-editing / skill-migration / skill-repair
skill_set = []                      # 本型通常不预装相关技能；若预装旧版本则如实填写
expected_skill_dependencies = []
tool_set = ["filesystem", "shell", "python"]
expected_tool_dependencies = ["filesystem", "shell"]
task_complexity = "C3"
weakness_tag = ["W04-需求覆盖记账", "W01-长文档硬约束"]
```

### 反模式（禁止）

1. instruction 把答案（成品 SKILL.md 内容）写成可照抄文本。
2. 交付物含糊（不指明技能名、不指明目录结构）。
3. 只用"写一个技能"一句话，**不给验收要素**（frontmatter/结构/SOP/脚本），导致判分不可核验。
4. 环境预装了与本任务相同的技能（应留空或预装**旧版本**作为输入）。
5. S3 的输入 SOP **信息量太小**（不足以考察取舍与结构化能力）。
6. S5 的缺陷**不可定位**（"某处有问题"但没有可观察现象）。
7. rubric 判"文风好坏""是否美观"等主观项。
8. 负向项滥用（把正常差异判为违规）。
9. 与 `../delivery/` 硬约束冲突（负 weight、likert 无锚点、criteria 无 name 等）。

## S1–S5 五类形态构造详解

### 通用：交付物的"及格线"结构

无论哪一类，产出的技能包必须满足（判定基线，见 `../delivery/08-skill-packaging.md`）：

```text
<skill-name>/
├── SKILL.md          # frontmatter(name/description/compatibility) + 正文 SOP
├── scripts/          # 可选：可执行脚本
└── references/       # 可选：被 SKILL.md 引用的补充资料
```

`SKILL.md` frontmatter 三字段：

| 字段 | 要求 |
|---|---|
| `name` | 小写连字符；与目录名一致 |
| `description` | 必须写清"什么时候该用"（触发语义），使不同任务可辨识 |
| `compatibility` | 运行前提：语言/解释器版本、依赖包与版本 |

### S1 · 创建 Skill

#### 输入材料

- 业务规则说明（.md / .docx）：一段真实的内部规则（如审批口径、分级阈值、字段映射）；
- 样例数据（可选）：体现规则作用效果的输入输出样例；
- 期望触发场景描述：在什么情况下这个技能应被使用。

#### 关键设计

| 要素 | 要求 |
|---|---|
| 规则的真实性 | 规则来自真实业务，**不是为出题编造** |
| 规则的特异性 | 含**不能从常识推出**的阈值/映射/优先级/fallback（否则技能无价值） |
| 触发语义 | `description` 需能让下游任务判断"该不该用这个技能" |
| SOP 完整性 | 分步 + 条件分支 + 完成检查 + 失败恢复 |
| 可执行性 | 至少提供一个脚本（如按规则计算/校验/转换），并写明参数 |

#### golden 要求

完整技能包 + 一节 `README.md` 说明设计依据（可作为交付物之一）。

#### 难度调节

| 旋钮 | 高 | 低 |
|---|---|---|
| 规则条数 | 5–10 条，含冲突处置与 fallback | 2–3 条线性规则 |
| 是否要求脚本 | 必须提供可运行脚本 | 仅文档 |
| 是否需要 references/ | 需要拆分子文件 | 单文件 |

### S2 · 修改已有 Skill

#### 输入材料

- **现有技能包**（完整可运行的旧版本，装在 `environment/input_files/` 或 `environment/skills/` 作为输入）；
- **变更需求单**（.md）：列出需要新增/修改/删除的条目。

#### 变更需求设计（关键）

需求单应包含**三类变更**，考察精准改动能力：

| 变更类型 | 示例 | 考察点 |
|---|---|---|
| **新增** | 新增一档风险阈值（>180 天为"严重"） | 插入位置正确、不破坏既有分支 |
| **修改** | 阈值从 90 天改为 75 天 | 全文口径一致（含正文、示例、脚本常量） |
| **删除** | 移除已废止的审批环节 | 不留残留引用、不留悬空引用 |

**隐蔽考点**：同一规则在**多处出现**（正文、脚本常量、references、示例），修改须**全处一致**——这直接对应 **W4 需求覆盖记账** 与 **W1 长文档硬约束**。

#### 交付物

- 更新后的技能包；
- **变更说明**（.xlsx 或 .md）：逐条列出需求 → 改动位置 → 改动内容。

#### golden 要求

新版技能包 + 变更说明；且**旧版中未被要求变更的部分必须保持原样**（可用 diff 核验）。

### S3 · 从 SOP 抽取 Skill

#### 输入材料

**长 SOP / 制度文件**（.docx / .md / .pdf），要求：

- 信息量足够大（建议 ≥3000 字，含多条规则、例外、审批链、表单要求）；
- 含**冗余内容与噪声**（背景介绍、免责声明、历史沿革），需要取舍；
- 含**隐含规则**（散落在正文段落而非列表里）。

#### 关键设计

| 要求 | 说明 |
|---|---|
| 结构化 | 把长文档转成分步 SOP（编号步骤 + 条件分支 + 完成检查） |
| 浓缩不失真 | 全部硬性规则必须保留；背景性内容可删 |
| 可执行化 | 把"应当由…审核"转成"检查 X 字段是否存在且非空"这类可操作判据 |
| 抽取阈值 | 把文中散落的数值规则集中为显式的阈值表 |
| 保留出处 | 可选：标出每条规则在原文的出处（便于核验） |

#### 交付物

技能包 + **抽取对照表**（.xlsx）：原文段落 → 抽取后的规则 → 处理方式（保留/合并/删除）。

> 对照表是**可核验的关键**：它让"是否漏抽规则"变成客观可判的事实。

#### 难度调节

| 旋钮 | 高 | 低 |
|---|---|---|
| 原文长度与噪声 | ≥8000 字，噪声占比高 | 2000–3000 字，结构清晰 |
| 隐含规则条数 | ≥5 条散落规则 | ≤2 条 |
| 例外与冲突 | 含"但书""例外情形" | 无例外 |

### S4 · Skill migration

#### 输入材料

- **旧格式技能包**（如：无 frontmatter / 单文件巨长 / 脚本内联在 SKILL.md 中 / 目录层级不同）；
- **新格式规范说明**（.md）：目标结构、必需字段、命名规则。

#### 关键设计

| 要求 | 说明 |
|---|---|
| 语义无损 | 旧版全部规则与阈值必须在迁移后**完整保留** |
| 结构合规 | 按新规范的组织方式重排（frontmatter 补全、脚本外置、references 拆分） |
| 行为等价 | 迁移前后对同一输入的判定结果一致 |
| 兼容性声明 | `compatibility` 须反映真实依赖（含版本） |

#### 交付物

迁移后的技能包 + **迁移对照表**（.xlsx：旧位置 → 新位置 → 是否等价）。

#### 隐蔽考点

- 旧版中**分散在多处的同一阈值**，迁移后容易不一致 → 考察一致性维护；
- 旧版中的**废弃内容**，迁移时应删除而非照搬 → 考察判断力。

### S5 · Skill package repair

#### 输入材料

- **带缺陷的技能包**（缺陷必须**可复现、可定位**）；
- **现象描述**（.md）：如"技能目录名为 `MySkill` 但 SKILL.md 中 `name: my_skill`，导致技能无法被识别""`scripts/calc.py` 执行报 KeyError"。

#### 缺陷类型库（建议每题埋 3–5 个）

| # | 缺陷 | 现象 | 定位难度 |
|---|---|---|---|
| 1 | frontmatter 缺字段 | 技能无法被识别 | 低 |
| 2 | `name` 与目录名不一致 | 技能加载失败 | 低 |
| 3 | `description` 无触发语义 | 技能从不被选中 | 中 |
| 4 | `compatibility` 与实际依赖不符 | 执行时缺包报错 | 中 |
| 5 | 脚本语法错误 | 执行报 SyntaxError | 低 |
| 6 | 脚本逻辑错误（阈值写错） | 结果静默错误（**最难**） | 高 |
| 7 | SKILL.md 引用了不存在的 references 文件 | 路径悬空 | 中 |
| 8 | 正文与脚本常量不一致 | 结果与文档不符 | 高 |
| 9 | 目录层级错误（SKILL.md 位置不对） | 技能不被发现 | 低 |

#### 交付物

修复后的技能包 + **修复说明**（.xlsx：缺陷 → 定位依据 → 修复内容 → 验证方式）。

#### golden 要求

修复后所有缺陷消除，且**未引入新问题**；提供一条可运行的验证命令（如 `python3 scripts/calc.py --selftest`）。

## Skill Generation / Editing rubric 设计

### 1. 验收要素清单（rubric 的原料）

#### 结构类

| 检查点 | 判定方式 |
|---|---|
| 技能目录存在且命名合规（小写连字符） | 目录存在性 + 命名正则 |
| `SKILL.md` 位于技能根目录 | 路径检查 |
| frontmatter 三字段齐备（`name` / `description` / `compatibility`） | YAML 解析 |
| `name` 与目录名一致 | 字符串比对 |
| `scripts/` 下脚本可解析 | `python3 -m py_compile` / `bash -n` |

#### 内容类

| 检查点 | 判定方式 |
|---|---|
| `description` 含触发语义（何时该用） | 判官阅读判断 + 是否含触发词/场景描述 |
| SOP 分步（编号步骤清晰） | 结构检查 |
| 含**条件分支**（if/else、例外情形） | 结构检查 |
| 含**完成检查**（每步的验收判据） | 内容检查 |
| 含**失败恢复**（某步失败怎么办） | 内容检查 |
| 含**特有规则**（阈值/映射/优先级/fallback） | 是否给出**具体数值/映射表**而非泛泛描述 |
| references 引用路径有效 | 引用的文件确实存在 |

#### 可执行类

| 检查点 | 判定方式 |
|---|---|
| 脚本能实际运行 | 真实执行（judge 可用 Bash 跑） |
| 脚本参数与 SKILL.md 记载一致 | 对照 `--help` 与文档 |
| `compatibility` 与实际依赖一致 | 对照 requirements / import |

#### 形态专属

| 形态 | 专属检查点 |
|---|---|
| S2 | 变更需求单每条都被落实；未要求的旧内容保持原样 |
| S3 | 原文硬性规则无遗漏（按对照表核验）；浓缩不失真 |
| S4 | 迁移前后语义等价；废弃内容已删除；一致性未被破坏 |
| S5 | 每个缺陷被修复；未引入新缺陷；验证命令可运行 |

### 2. 示例条目

#### 结构：frontmatter 完整性

```toml
[[criterion]]
id = "R01"
name = "R01"
description = "交付的技能包中 `SKILL.md` 的 YAML frontmatter 同时包含 `name`、`description`、`compatibility` 三个字段，且 `name` 取值与技能目录名逐字一致。 Deliverables to inspect: `output/<skill-name>/SKILL.md`."
type = "binary"
weight = 10.0
```

#### 内容：触发语义可辨识

```toml
[[criterion]]
id = "R02"
name = "R02"
```

### 3. 建议条目结构（9–15 条）

| 类别 | 条数 | weight |
|---|---|---|
| 结构合规（目录、frontmatter、命名） | 3 | 3–10 |
| **内容质量（触发语义、SOP、特有规则）** | 3–5 | 7–10 |
| 可执行性（脚本、依赖） | 1–2 | 7 |
| 形态专属（变更/抽取/迁移/修复） | 2–3 | 7–10 |
| 负向（照抄、编造、结构破损） | 2 | 7 |

> 必须满足 `Critically Important（+10）≥2` 与"内容质量维度正分 ≥30%"。

### 4. 定向弱点对照

| weakness | 本题型中的体现 | 判分设计 |
|---|---|---|
| **W1** 长文档硬约束遵循差 | S3 从长 SOP 抽取：漏掉散落的硬性规则 | 抽取对照表 + 无遗漏判定（+10） |
| **W4** 多要求下缺 Requirement Coverage Accounting | S2 多处口径需同步修改，模型只改一处 | 变更需求逐条落实判定 |
| **W9** Skill 被形式化调用 | 技能写得"像样"但无真实可依赖的特有规则 | 特有规则 likert（本题型核心项） |
| **W13** 规划与策略调整失当 | 修复题中只处理显性缺陷、忽略静默逻辑错误 | 缺陷修复逐项判定 |

### 5. 常见陷阱

| # | 陷阱 | 修正 |
|---|---|---|
| 1 | instruction 给了成品文本，模型照抄即得满分 | instruction 只给需求与验收要素，不给成文内容 |
| 2 | 交付物不指明命名与路径 | 明确写出技能名、目录结构、交付路径 |
| 3 | rubric 判"文风""是否美观" | 改为可核验的结构/内容/执行检查 |
| 4 | 只判"文件存在" | 必须判**内容质量**（特有规则、SOP 分支、脚本可用） |
| 5 | S3 的 SOP 太短、无噪声 | 加长到 ≥3000 字并混入背景性噪声 |
| 6 | S5 缺陷不可定位 | 每题埋 3–5 个**可复现**缺陷，并在现象描述中给出可观察现象 |
| 7 | 环境预装了与任务相同的成品技能 | 留空，或预装**旧版本**作为输入 |
| 8 | 负向项把正常差异判为违规 | 负向项只描述明确错误（照抄、编造、破损） |
