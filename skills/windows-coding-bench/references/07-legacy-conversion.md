# 07 · 旧题转换与整改

来源：规范第九章

---

## 一、参考样本

`outside_harbor-dev_0911.zip` 中的 **6 题**是本轮旧题转换和提交目录的直接参考。

- 当前生产先沿用其 `outside_harbor/` + `outside_harbor-assets/` 提交形态
- 但包内题目**仍须按本规范的新评分和验收口径整改**，不能将历史结果直接视为合格

---

## 二、变更对比（必须先做）

将压缩包中的**修复版本**与供应商**最初提交的原始版本**逐题对比，形成变更清单，说明：

| 项 | 内容 |
|---|---|
| 改了什么 | 文件级变更 |
| 原问题是什么 | 原始缺陷/隐患 |
| 修复是否已动态验证 | 有/无实测证据 |
| 是否应保留到本题新版本 | 保留/撤回及理由 |
| 是否值得沉淀为通用生产规范 | 是/否及理由 |

> **无法取得原始提交或无法确认变更来源时，应明确标为「证据缺口」，不得把现状全部宣称为已验证修复。**

**产出位置**：`delivery-extras/tasks/<task-id>/original_comparison/`
至少保留：原始提交身份及 Hash、当前压缩包版本身份及 Hash、文件级变更清单、变更原因、验证证据、保留/撤回结论、对后续新题的复用建议。

## 三、每题必须重新完成的 12 项

| # | 动作 | 要点 |
|---|---|---|
| 1 | 冻结 Schema 重新校验 | 校验 `task.toml`、目录和入口；**历史文件能运行 ≠ 已符合本次标准 Schema** |
| 2 | 整理为唯一标准 Harbor Task | `instruction.md + task.toml + environment/ + solution/ + tests/`；`source.json`/运行证据/质检材料移入 `delivery-extras/` |
| 3 | 保留平台提交入口 | `outside_harbor/<task-id>.json` 与 `outside_harbor-assets/<task-id>/` 绑定**同一身份三元组** |
| 4 | 统一并修正 ID、版本和 Hash | 消除历史 `task.toml`、`source.json`、平台 JSON、镜像标签和来源包之间的身份冲突 |
| 5 | 重做题面—testcase 双向映射 | 删除越界、相反或绑定内部实现的测试 |
| 6 | 评分统一改为二值 | F2P/P2P 全过得 1，否则得 0；**清除 `judge.toml`、`rubric.json` 及聚合器中的权重与部分分语义** |
| 7 | 重新验证 Golden=1、no-change=0 | 并**逐项解释**所有异常、SKIP 和缺失 |
| 8 | 检查测试是否真触发 Windows 机制 | 避免路径/readiness、依赖、权限、旧产物、Mock 失真和异步提前退出等历史问题 |
| 9 | 核对离线执行资产 | 保留离线依赖、fixture、baseline repo；核对**来源、Hash、体积、隐藏边界和实际加载路径** |
| 10 | 盘点 `.ap-tools` | 标明有效版本；删除/隔离过期、重复、仅服务历史版本的工具；最终位置待联调确认 |
| 11 | 重新执行多模型检查 | Qwen/Opus 各 3 次 + GLM/Kimi 可运行性检查 |
| 12 | 与新题同标准交付 | 使用**相同版本库、批次流程和验收标准** |

> 历史「已修」「已通过」或旧分数**仅作为风险线索**，不替代本次实测。
> 若转换后仍不能满足 Windows 价值、二值判分、稳定性或模型区分度要求，应**淘汰并用新题替换**。

## 四、值得沉淀为通用检查的历史修复（9 类）

判断以下历史修复是否应转为后续题目的**通用检查**（而不是直接复制实现）：

| # | 检查方向 |
|---|---|
| 1 | Windows 根目录、工作目录、`WINDIR/SystemRoot`、Shell 和路径解析是否与**真实 Runner** 一致 |
| 2 | Node/.NET/NuGet 等工具链和离线依赖是否预装、锁版本并在**断网条件**下真实可用 |
| 3 | prepare、Agent 修改、patch capture 和 verifier 是否操作**同一个实际工作区** |
| 4 | 构建失败是否**立即停止**，是否清理旧二进制和旧结果，避免历史产物伪通过 |
| 5 | required testcase 是否完整执行；缺失、重复、SKIP、ERROR 和解析失败是否**正确标为 INVALID** |
| 6 | 环境/fixture/权限异常是否与候选功能失败**分开**，不能用大 try/catch 静默变成模型 0 |
| 7 | Mock、跨进程、异步回执和负观察是否保真，不能只凭退出码、文件存在或固定等待判定 |
| 8 | 网络访问、外部源码下载、本地答案搜索、评分目录读写和轨迹完整性是否**可审计** |
| 9 | Golden 是否真实应用参考解、no-change 是否稳定为 0、每项结果是否可由**同版本日志和 Hash** 复核 |

> **「值得后续题目参考」应沉淀为「风险、检查方法、正反控制和结果字段」，不要求后续题机械复用旧脚本、旧 Mock、旧阈值或旧目录。**

## 五、转换工作流

```
1. 取得两版（原始提交 + 修复版）
   → 2. 逐题文件级 diff，形成变更清单
   → 3. 判定每项变更的去留 + 是否沉淀
   → 4. 无法确认来源 → 标记证据缺口
   → 5. 按 12 项重做（Schema 校验 → 结构整理 → 身份统一 → 双向映射 → 二值评分 → 对照重验）
   → 6. 重跑多模型
   → 7. 与新题同标准交付
   → 8. 淘汰不达标项并用新题替换
```

### 转换自检

- [ ] 两版身份与 Hash 均已记录
- [ ] 文件级变更清单完整
- [ ] 每项变更标注「保留/撤回」+ 理由
- [ ] 无法确认来源的已明确标为证据缺口
- [ ] 12 项重做逐项完成并留痕
- [ ] `judge.toml` / `rubric.json` 权重语义已清除
- [ ] 身份冲突已修正（非备注兼容）
- [ ] `original_comparison/` 材料齐全
- [ ] 多模型检查重跑完成
- [ ] 不达标项已淘汰
