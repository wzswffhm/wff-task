# 《外发版-基于 weakness 和 skill 的数据构造方案（金融）》解析笔记

> 原文抽取见同目录 `原文抽取.txt`（14 页）。
> **组合使用要求**：须与《外发版-评测题包交付规范（rewardkit）20260913》组合使用。
> 本文件回答**出哪几类题、每类怎么构造**；交付规范回答**怎么打包、怎么判分、怎么验收**。

## 0. 一句话结论

本批次聚焦**金融（FIN）**领域，总量 **2000 条**，分两大块：
- **专项数据 1000 条**：基于 skill / tool / workflow 的能力专项（5 个二级类型，各 200 条）；
- **Weakness-driven 数据 1000 条**：针对已观测模型缺陷的定向构造（覆盖 W1–W14 共 14 种，复杂度分 C1–C5）。

---

## 1. 项目背景与使用范围

- 定义 RL 从 0 到 1 标注生产下数据的规格、格式、质量标准与验收流程。
- 面向对象：供应商、内外部专家、标注质检平台。
- **写给领域专家**：根据自己的擅长领域选择合适难度的任务，给出 ① 任务描述（对应办公场景、具备真实业务价值）② 参考文件 ③ 参考答案 ④ 打分项。
- **验收依据**：① 用打分项给参考答案打分 → 正确率 > 0.85；② 用 3 个模型执行并打分 → 看难度是否足够高；③ **人工质检**重点考察题目真实性、参考答案合理性、打分项设计合理性、是否 hack 等异常作弊，一经发现**直接打回**。

## 2. 难度分级

按**三模型平均正确率**划分：只要平均分低于 **70%** 即算难度达标；达标后再按区间归入 A1/A2/A3（**区间不重叠**）。

| 级别 | 产量占比 | 数量（单领域） | 平均正确率 |
|---|---|---|---|
| A1 基础 | 20% | 200（单个领域 50 题） | 60% ≤ 得分 < 70% |
| A2 进阶 | 60% | 600（单个领域 150 题） | 50% ≤ 得分 < 60% |
| A3 高难 | 20% | 200（单个领域 50 题） | 得分 < 50% |

**跑分口径（单条）**：Claude code 框架下跑 `gpt-5.6-sol`、`claude-opus-4-8`、`qwen3.8-max0902`；满分归一化为 1.0；**裁判模型 `qwen3.7-plus`**；每模型跑 1 次求平均分，均分 **< 0.7**；且**至少有一个模型有得分**（避免全 0 的"死题"）。

**跑分产物及轨迹要求**：提交题目文件时须**同步提供模型产物和跑分轨迹**。

### 首批构造需覆盖两个方面

- **领域覆盖**：金融 FIN。本批次仅聚焦金融领域，金融领域下的数据应**均匀分布**，**不接受一个知识点/workflow 出题 ≥3 道**；且数据分布符合专项数据与 weakness 数据的要求。
- **数据总量**：**2000 条**（基于 skill/tool/workflow 等内容专项数据 **1000 条** + weakness 数据 **1000 条**）。

## 3. 类型一：专项数据（skill / tool / workflow，1000 条）

> 更关注某一能力方向的**系统性和完整覆盖**：从能力维度出发，尽可能全面覆盖不同场景、难度、环境和任务形态，目标是整体提升该能力。

| 一级 | 二级 | 数量 |
|---|---|---|
| Skills 数据 | Skill Discovery | 200 |
| Skills 数据 | Skill Generation / Editing | 200 |
| Skills 数据 | Skill Dependency | 200 |
| Workflow Execution | Dependency-aware Workflow | 200 |
| Workflow Execution | Subagent Workflow | 200 |

（另有 **MCP Scaling（低优）**：扩大模型在非原生工具、陌生 Tool Schema 和不同 Tool 组合下的泛化能力；可主要通过 MCP 数据构造，须在每条任务中**明确提供当前 Environment 下模型可使用的工具集合 / MCP**，工具可以是框架已有能力，也可以是动态注入的自定义工具（在题目里显式说明）。）

### 3.1 基于 skills/workflow 的 scaling 专项——背景与出发点

目前 Cowork RL 数据中，大部分任务仍运行在相对简单的环境里：
- 以 filesystem / shell / 少量原生工具为主；
- Tool schema、可用能力和调用方式相对固定；
- **Skill 即使存在，也经常只是辅助信息，并非完成任务所必需**；
- Workflow 多数是线性的「读取 → 处理 → 输出」，较少包含真实业务中的状态变化、异步依赖、异常恢复、跨工具协同等复杂过程。

**下一阶段目标**：数据建设从单纯扩充 **Task Distribution**，进一步转向扩充 **Environment Distribution**。

### 3.2 Skills 数据需求

#### (1) Skill Discovery（200 条）
**提供多个 Skill，要求模型自行判断：是否需要 Skill，以及应该使用哪个 Skill。**
→ 关键设计：环境中同时安装**相关 skill 与干扰 skill**，任务本身不一定需要 skill（考察"不使用"也是正确决策）。

#### (2) Skill Dependency（200 条）
**构造：没有 Skill 中的特殊知识 / 行为规则，模型很难正确完成任务。**

三种推荐构造方式：

| 类型 | 构造要点 |
|---|---|
| **类型一：特殊业务规则** | Skill 明确规定：当两个 authoritative source 的关键字段**冲突**时，**禁止自行选择，必须暂停并向用户确认**。Task 中**主动埋入这种冲突**。模型如果没有真正遵循 Skill：最终一定会进入错误 branch |
| **类型二：环境特化 SOP** | 例如 Skill 定义某企业内部审批流程：`Draft → Compliance Review → Manager Approval → Publish`。Task 要求完成发布。如果模型直接 `Draft → Publish`，最终 **Workflow State 必须失败** |
| **类型三：特殊计算 / 判定规则** | Skill 中包含：**特殊阈值；内部映射规则；自定义字段定义；业务优先级；fallback 顺序**。要求这些内容**直接影响 final answer** |

#### (3) Skill Generation / Editing（200 条）
增加一批：**创建 Skill；修改已有 Skill；从 SOP 抽取 Skill；Skill migration；Skill package repair** 之类的任务。

### 3.3 Workflow 数据需求

#### (1) Dependency-aware Workflow（200 条）
任务中存在明确 dependency：

```
A → B
A → C
B + C → D
D → Final
```

要求模型：① 正确拆解 dependency；② 维护哪些任务已完成；③ 避免提前执行依赖未满足的步骤；④ Final 前确认 dependency 已全部完成。

#### (2) Subagent Workflow（200 条）
**构造必须依赖多个 Subagent Result 才能完成 Final 的任务。**
（最好是有涉及 subagent 的，例如在 codex 下运行该任务会触发 subagent。）

### 3.4 Skill 形态说明

当前可主要通过**写入 skills 文件夹**的形式实现。功能型 Skill 的标准目录结构：

```
AQ-002/
├── task.toml                      # 任务声明
├── instruction.md                 # 显式说明"通过 contract-redliner skill 完成，禁止其它方式改文档"
├── environment/
│   ├── Dockerfile                 # COPY skills/ /skills/  ← skill 在这里被装进环境
│   ├── skills/
│   │   └── contract-redliner/
│   │       ├── SKILL.md           # Anthropic Skill 格式：frontmatter(name/description/compatibility) + 正文 SOP
│   │       ├── scripts/           # read_document.py / propose_edits.py / add_comment.py …
│   │       └── references/        # anchors.md 等被 SKILL.md 引用的补充规则
│   └── app/                       # 任务输入：contract.docx + grounding 材料
├── tests/
│   ├── test.sh → run_verifier.py  # 判分入口
│   └── rubrics.json               # 判据
└── solution/
    ├── solve.sh
    └── ground_truth.docx          # ground_truth
```

**SKILL.md 写法参考**：

```markdown
---
name: contract-redliner
description: Redline Word (.docx) contracts with native tracked changes and margin comments …
    Use when asked to redline, mark up, revise a .docx legal document — every edit must be a
    real tracked change applied via the bundled scripts, never by rewriting the file.
compatibility: Requires Python 3.10+ with python-docx==1.2.0, docx-revisions, lxml.
---
# Contract Redliner
（正文：分步 SOP、脚本用法、失败恢复、"绝不能用别的方式改文档"的硬规则
这些"特有行为规则/阈值/映射"就是让 Skill 不可省略的关键）
```

**关键要求**：`instruction.md` 里需**显式强调要使用该 skill**：

> Every edit and every comment goes through the contract-redliner skill installed in this environment — never write `[ADD:…]` / `[DELETE:…]` markup, and never modify the document by any other means.

### 3.5 专项数据交付 Metadata

建议每条数据额外维护：

```toml
skill_set                   = ["approval-workflow"]   # 环境内安装的功能型 skill（= environment/skills/ 下的目录名）
task_complexity             = "C3"                    # C1–C5，取值口径见正文分级表
expected_skill_dependencies = ["approval-workflow"]   # 完成任务真正必须依赖的 skill（子集，可为空表示 Skill Discovery 干扰项）
weakness_tag                = ["W07-流程跳步", "W12-约束遵循"]   # ≥覆盖 1 个
```

| 字段 | 类型 | 取值写法 / 约束 |
|---|---|---|
| `skill_set` | array | 环境内安装的功能型 skill 目录名，须与 `environment/skills/<name>/` 逐一对应；**可含干扰项**（Skill Discovery 场景） |
| `task_complexity` | enum | C1–C5，按正文分级表的文件数 / requirement / evidence-hop 等硬指标判定 |
| `expected_skill_dependencies` | array | `skill_set` 的**子集**：不依赖它任务必失败的 skill。Skill Discovery 任务里这一项应**严格小于** `skill_set`（存在故意的无关 skill） |
| `weakness_tag` | array | 覆盖 ≥1 个，按算法词表填写，至少一项 |

## 4. 类型二：Weakness-driven 数据（1000 条）

> 更聚焦**已经观察到的具体模型缺陷**，从明确的 **Bad Pattern / Trigger** 出发，针对性构造能够**稳定复现**并训练该问题的场景。

**覆盖要求**：
- 数量 **1000 条**，要求覆盖 **14 种 weakness**，以及数据复杂性覆盖 **C1–C5**。
- 数据须在元数据中标注**主要作用于哪个 weakness，必须覆盖 1 个以上**。
- 计数规则：每条数据在 `weakness_tag` 中标注 ≥1 个；一条数据标注多个时，对其标注的每一种各计 1 次覆盖。**每种 weakness 至少被 50 条数据覆盖，且不超过 250 条**。
- **标注须与题目实际埋入的 trigger 一一对应**：标了某个 weakness，**题面和 environment 中必须存在能稳定诱发该 weakness 的设计点**。

### 4.1 C1–C5 分级表

| 指标 | C1 | C2 | C3 | C4 | C5 |
|---|---|---|---|---|---|
| 文件数 | 2 | 5 | 10 | 25 | 50+ |
| Requirement 数/约束 | 3 | 6 | 10 | 15 | 20 |
| 输出产物数 | 1-2 | 2-3 | 3-4 | 4-6 | 4-8 |
| Evidence Chain | 1-hop | 2-hop | 3-hop | 4-hop | 5-hop |
| 执行步数 / 子任务数 | 1–3 / 1 | 4–7 / 2–3 | 8–15 / 4–6 | 16–30 / 7–10 | 30+ / 10+ |
| 工具种类数 | 1 | 2 | 3 | 4 | 5+ |
| 领域专业深度（参考） | 通用常识 | 基础专业 | 中级业务 | 高级专业 | 专家级 |
| **题量** | **120** | **250** | **350** | **180** | **100** |
| **占比** | **12%** | **25%** | **35%** | **18%** | **10%** |

> 注：C5 的输出产物数为 4-8；如果是一个大型项目（如做整个并购尽调），产出物可以为 1 份。

**各等级画像与典型真实生产力场景**：

| 等级 | 画像 | 典型场景 |
|---|---|---|
| C1 | 单文件、单输出、单步完成，无需专业知识 | 从一份 Excel 中统计销售额并生成一句话结论 |
| C2 | 多文件简单对照，2 种工具，基础专业门槛 | 对比两份报价单，输出差异表 + 推荐方案 |
| C3 | 标准项目规模，中等推理链，3 种能力组合 | 根据销售数据、客户反馈、产品资料生成分析报告 + 图表 + 建议清单 |
| C4 | 复杂项目级任务，长依赖链，需要高级领域知识 | 基于季度财报、行业研报、内部纪要撰写投资 memo + 财务模型 + 风险清单 |
| C5 | 大型项目/知识库，多产物完整交付，专家级判断 | 完成并购项目的 CIM 分析、估值模型、尽调问题清单 |

**指标说明**：

| 维度 | 含义 | 计量方式 |
|---|---|---|
| 文件数 | 模型可读取/处理的输入文件数量 | 不含重复文件、临时文件 |
| Requirement 数 | 显式或隐式需满足的条件/约束条数 | 含功能、格式、引用、质量约束 |
| 输出产物数 | 最终需交付的文件/片段/结果数量 | 如代码文件、表格、报告段落、邮件等 |
| Evidence chain 深度 | 完成答案所需的**最长跨文件推理步数** | 1-hop = 单文件直接可得 |
| 执行步数 | 模型需调用的原子操作/工具调用次数 | 工具调用次数 |
| 工具种类数 | 不同类型的能力/工具（文本阅读、搜索、代码执行、计算、写作、绘图、表格处理等）。同一类工具的多次调用只算 1 种 | 工具种类数量 |

### 4.2 W1–W14 全量弱点表

> `weakness_tag` 为 b 列（按算法词表填写）。

| # | Weakness | 典型行为 | 具体 case | 推荐的数据构造方式 |
|---|---|---|---|---|
| **W1** | 长文档下的硬约束遵循较差 | 模型不是完全没看到要求，而是随着内容生成变长，部分 hard constraint 从 working state 中丢失；尤其是需要**真实 artifact operation** 才能满足的约束（section break、页码域、字数上限、公式保留），而不是在正文中"写到了"就算完成 | PA-T1-001 无人驾驶航空器管理办法起草：明确要求正文 4000–8000 字，Qwen 最终约 14825 字（接近上限两倍）；同时页码域、单双页等要求并未真正写入 Word XML | 构造 **long-form + 5–15 个 artifact-level hard constraints** 的任务。重点混合三类约束：**内容约束、数量约束、真实文件结构约束** |
| **W2** | 关键冲突下自行选边 / 修改输入，而不是模糊澄清或是说明具体冲突情况 | Workspace/Context 中存在互相矛盾的关键信息，模型甚至已经发现冲突，但会自行选择其中一个版本继续，极端情况下直接"修正"输入 | 报告中血钾 8.2 mmol/L vs "持续低钾"；材料用量 100ml vs 120ml 都稳定复现了该问题。医疗冲突 Case：病例文字明确描述"持续低钾"，但化验结果显示 K⁺=6.2 mmol/L。高钾和低钾对应完全不同的诊断和治疗策略，模型不能自行决定哪一条是真的 | 构造**含冲突 Workspace** 的任务。同一事实分别出现在 Excel / PDF / 邮件 / Markdown / 数据库结果中，两个值对应完全不同的最终答案；真正值只能通过**询问用户**或额外可信工具确认，或是有其他证据（这里可以是静态 user 多轮数据） |
| **W3** | 阻塞状态的识别与恢复能力较差 | 遇到关键资源缺失、权限受限、外部依赖失败、输入损坏或必要信息不足等 **Blocking State** 时无法稳定判断。典型错误两类：**过早放弃/不懂变通**（原路径失败后直接停下或把任务推回用户，明明存在 retry、替代工具、备用数据源等可恢复路径）；**强行闭环/伪完成**（关键阻塞尚未解除，却使用假数据、placeholder、自行估值、未经授权的替代方案继续执行，并最终宣称任务完成） | case1：image 工具不可用，但模型一直仍在反复调用；case2：某相关文件不存在，模型一直在反复寻找该文件直到超长 | 主要是教会模型 **Blocking State → Recovery**。可涵盖多种类型：某数据不可用（目标文件名不可用，但 Workspace 中存在合理替代文件）；某服务不可用（需要模型自行先修复服务）；原路径不可行，但环境里有另一种工具可以完成；缺少关键信息（需要 ask_user） |
| **W4** | 多要求 / 多交付物下缺少 Requirement Coverage Accounting | 简单任务基本能完成，但当显式要求项、文件数、sheet/section/field/edit item 增多时，模型容易"完成大方向但漏细项"，缺少一套持续维护的 requirement checklist | hard_194：PPT 要求完成 10 项修改，Qwen 约只完成 4/10；hard_008：要求同时交付完整 Excel 审计表和 Word 摘要但缺少必需工作表/章节；hard_180：7 页脚本 PPT 漏掉每日时段和逐镜来源 | 构造**要求有多个产物要求**的复杂任务 |
| **W5** | 关键信息缺失时"该问不问" | 模型能够意识到部分信息缺失，却没有稳定转化成真正的"提问—等待"。漏问 case 中既有"声明关键假设但继续做"，也有直接静默补全 | 通用-003｜9 天差旅穿搭：用户列出了衣物、帽子、围巾，却没有提供任何鞋款；任务又明确要求每天必须搭配一双鞋，且连衣裙必须配皮鞋。Qwen 没有询问可用鞋款，直接继续生成，最终鞋子部分缺失结果 | 刻意删除一个**决定最终结果的 blocking variable**。例如穿搭缺鞋款、金融测算缺收购比例、分析任务缺时间范围、PPT 缺目标受众等 |
| **W6** | 用户补充信息后只局部更新，没有 Global Re-planning | 模型"问到了、听懂了、写进答案了"，但依赖这一事实的其他规则、计算、排序、结论仍沿用旧值。Qwen 在完整利用澄清信息的 case 中，仍有 59% 内容未满分、33% 有严重错误 | 并购 Earn-out Case：模型能够主动追问并获得"首期收购 60%、剩余 40% 按业绩分期收购"等关键信息，但最终一方面把剩余 40% 当作购买日或有对价计入合并成本，相当于按 100% 收购 | 一个新增事实**同时影响 3–5 个 downstream fields**。例如主体从 A 改成 B，同时改变税率、适用法规、现金流计算、风险评级和最终建议 |
| **W7** | 长表格 / 多 Sheet 下的数据覆盖与抗干扰能力弱 | 阅读长 Excel、多子表或重复实体时容易漏行漏对象、错误聚合、把 inactive/非目标对象混入统计；模型有时已经注意到"同名多记录"等异常，但仍快速选择一个未经验证的处理口径 | hard_155：没有提取 60 个子表数据；medium_050：源表存在同名学生多条考试记录，Qwen 将记录直接求和排名，得到无法回源的分数与前三名；另有 case 出现 inactive 对象、冲突项覆盖不足 | 构造 **row / sheet scaling + distractor injection**：增加 sheet 数、行数、重复 key、inactive 记录、跨期记录、相似实体、隐藏列、异常值；让 gold **明确依赖正确的 grouping / filtering / dedup 规则** |
| **W8** | 启动 Subagent 后把"已派发"当成"已完成" | Qwen 可以正确拆任务并启动多个研究 Agent，但多次在异步结果返回前直接结束主任务，没有等结果回收动作 | H-104967｜白银供给、回收率与回收技术综合研究：3 次 rollout 均启动 5 个研究 Agent，但全部停在"等待返回" | 构造需要依赖**多个 delayed subagent result** 才能完成 final 的任务。各子 Agent 分别掌握**不可替代**的一部分信息。（该类任务也是目前非常缺少的） |
| **W9** | Skill 被形式化调用，但没有真正改变关键判断 | 报告发现"使用了匹配且关键的 Skill"并不等于结果改善。模型可能完整走了一遍 Skill checklist，却没有根据检查结果修正原结论 | Clinical Skill Case：Qwen 先搜索 Skill，再激活 clinical-diagnostic-reasoning 并读取 clinical-reports；Skill 确实使输出结构更完整，也加入了偏差检查，但模型随后仍自行加入固定冰冻分流、固定切缘、固定药物线序等过度具体建议，说明 Skill 被"读了"，却没有真正约束每条建议的证据强度 | 构造一批**必须依赖 Skill 中特有信息或行为规则**才能正确完成的任务，避免 Skill 只是"可有可无"的辅助材料。例如 Skill 明确要求发现数据冲突必须暂停，task 中刚好埋冲突 |

### 4.3 通用 difficulty-control 维度（重要）

> **Qwen 在要求项更多、交付物更多、跨应用更多的 hard query 上，思考和工具调用没有随难度增加，甚至有所下降，明显弱于其他模型；而 Opus 会相应增加执行与验收投入。这个现象更适合作为所有定向 weakness 数据的 difficulty-control 维度。**

→ 出题时可把"要求项数 / 交付物数 / 跨应用数"作为难度旋钮，并据此预期模型表现分化。
