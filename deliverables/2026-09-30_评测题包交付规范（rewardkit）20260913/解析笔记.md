# 《评测题包交付规范（rewardkit）20260913》解析笔记

> 原文抽取见同目录 `原文抽取.txt`（67 页）。
> 本规范是**题包格式与评分器写法**的唯一权威；题量配比、难度、通过率等验收标准见其第 7 章。

## 0. 一句话结论

这是 **外发供应商题包第三代交付规范**：由「Judge 一次性读文件 + gating.toml 一票否决」（旧版 v4 / 20260808）
升级为「**claude-code agent judge 逐条独立会话评分**（`mode = "individual"`）+ **单份 rubrics.toml 池化计分**」。
供应商的产出边界是：`instruction.md` / `task.toml` / `rubrics.json` / `environment/` / `solution/` / `tests/rubrics.toml` / `tests/prompt.md`；其余基础设施（镜像、判官、聚合）由平台固定。

## 2. instruction.md（任务书）

Harbor 不提供模板，供应商自撰，但硬性要求：

1. **源文件路径固定 `/app/input_files/`，交付路径固定 `/app/output/`**。
2. **自包含**：Agent 只能看到 instruction.md、`/app/input_files/` 与镜像内预装工具/技能 → 任务书须写全所需信息，或给出镜像内可读取的技能与资料入口；**不得引用外部链接**或"见附件说明"之外的隐藏语境。
3. **技能入口（有 Skill 时）**：列出全部可用技能的名称、适用描述、容器内 `SKILL.md` 的**绝对路径**，并说明脚本相对路径的基准目录；**不得只写技能名让 Agent 猜路径**。技能方法与 Workflow/SOP 保留在技能文档中，无需全文复制到任务书。
   **不得泄露**：`expected_skill_dependencies` 中的必要技能身份、干扰项身份。
4. **列明源文件**：逐个列出 `/app/input_files/` 下文件及其字段/口径说明（表格式）。
5. **交付物精确命名**：逐个给出精确文件名，与 `[[metadata.deliverables]]`、`artifacts`、两份 `golden_output/`、criterion description **逐字节一致**。
6. **与 Rubric 对齐**：Rubric 每条显式要求都应能在任务书中找到出处；任务书中的硬性要求也应有对应 criterion 覆盖。
7. **不得泄露评分信息**：不出现 rubric 条目、golden 内容或"评分将检查……"式提示。
8. **硬约束独立成段**：禁止项、文件名要求必须独立段落显式写出，不得藏在括号内。

## 3. task.toml（schema 1.4）

### 3.1 书写顺序（强制）

`schema_version` → `artifacts` → `[task]` → `[metadata]` → `[[metadata.deliverables]]` → `[agent]` → `[verifier]` → `[verifier.env]` → `[environment]`。

### 3.2 字段说明

| 字段 | 说明 | 必填 | 约束 |
|---|---|---|---|
| `schema_version` | 版本 | 是 | 固定 `"1.4"` |
| `artifacts` | 交付物绝对路径 | 是 | 由 `required = true` 的 `deliverables.path` 前加 `/app/output/` 机械展开，另固定含 `/logs/artifacts/output` |
| `[task].name` | 任务名 | 是 | `work/<task_id 小写连字符>`，如 `work/fin1-001` |
| `[task].version` | 版本 | 是 | `"1.0.0"`，返修补丁号递增 |
| `[task].description` | 一句话说明 | 是 | 可直接用 instruction.md 标题 |
| `[task].keywords` | 关键词 | 是 | `[领域英文名, "office", 难度等级]`，如 `["finance","office","A2"]` |
| `[metadata].task_id` | 题目编号 | 是 | 格式 `领域缩写-任务类型-序号`，如 `FIN1-skill-DEP-001` |
| `[metadata].author_organization` | 供应商名 | 是 | — |
| `[metadata].category` | 题目类型 | 是 | 如 `skill-dependency` |
| `[metadata].domain` | 一级标签 | 是 | `通用办公` / `金融` / `医疗` / `法律` |
| `[metadata].domain_l2` | 二级标签 | 是 | 对齐知识体系表 |
| `[metadata].domain_l3` / `domain_l4` | 三/四级标签 | 是 | 对齐知识体系表 |
| `[metadata].capabilities` | 评测的能力 | 是 | 该任务能评测的具体专业能力 |
| `[metadata].difficulty` | 难度等级 | 是 | A1 <70% / A2 <60% / A3 <50% |
| `[metadata].vl_dependency` | 是否依赖 VL | 是 | 是 / 否 |
| `[metadata].source_note` | 任务说明 | 是 | 为什么选这个任务、真实性保障、真实场景交付物是什么 |
| `[metadata].tools` | 所需工具 | 是 | Word/Excel/PPT 等 |
| `[metadata].domain_knowledge` | 领域知识依赖 | 否 | — |
| `[metadata].task_complexity` | 任务复杂度 | 本专项必填 | C1–C5，**不从 difficulty 换算** |
| `[metadata].weakness_tag` | 弱点标签 | 本专项必填 | 数组，≥1 项，用正式词表 |
| `[metadata].environment_template` | 环境模板名 | 本专项必填 | 平台已确认模板名，与实际镜像依赖一致，不替代 Dockerfile |
| `[metadata].tool_set` | 工具能力集合 | 本专项必填 | 如 `["filesystem","shell","python"]` |
| `[metadata].skill_set` | 环境内可用技能 | 本专项必填 | 与 `environment/skills/<name>/` 逐一对应，名称与 SKILL.md 的 name 一致；可含干扰技能；无技能写 `[]` |
| `[metadata].expected_tool_dependencies` | 真正必要的工具 | 本专项必填 | 必须是 `tool_set` 的子集 |
| `[metadata].expected_skill_dependencies` | 真正必要的技能 | 本专项必填 | 必须是 `skill_set` 的子集；发现类任务应为**真子集** |
| `[metadata].expected_pass_rate` | 目标通过率预估 | 否 | 0~1 |
| `[[metadata.deliverables]]` | 交付物清单 | 是 | path / required / desc |
| `[environment].network_mode` | — | 是 | **固定 `public`**；claude-code 框架下**禁止写 no-network**（agent setup 阶段要联网装 claude CLI，断网直接 AgentSetupTimeoutError） |
| `[environment]` 允许键 | — | — | 仅 `os / network_mode / allowed_hosts / build_timeout_sec / docker_image / cpus / memory_mb / storage_mb / env / healthcheck`；**禁止写 workdir**（工作目录由 Dockerfile 的 `WORKDIR /app` 决定） |
| `[environment].env` | agent 侧环境变量 | — | 最小必要原则；**`JUDGE_*` 严禁写入**（等于把评分通道泄漏给被测模型） |
| `[verifier].timeout_sec` | — | 是 | `18000.0` |
| `[verifier].user` | — | 是 | `"root"` |
| `[verifier.env]` | judge 凭据 | 是 | 逐字照抄：`JUDGE_API_KEY` / `JUDGE_BASE_URL` 必选（运行环境注入，不替换真实值）；`JUDGE_MODEL` 等可选项必须用 `${VAR:-默认值}` 语法 |

### 3.3 `[[metadata.deliverables]]` 命名与结构规则（5 条）

| # | 规则 | 原因 |
|---|---|---|
| 1 | `required = true` 必须写**精确文件名**，禁止 glob / 通配 / "或等价命名" | glob 只允许用于 `required = false` 的过程性产物 |
| 2 | 文件名不得含日期、时间戳、版本号等动态成分 | Agent 每次生成名字不同，criterion 里的名字永远对不上；业务需含日期的把具体字符串写死 |
| 3 | **大小写敏感**；清单、instruction.md、artifacts、`solution/golden_output/`、`tests/__golden_output/`、criterion description 中引用的交付物路径**六处逐字节一致**（含全角/半角、空格、下划线/连字符） | Linux 容器内 `Report.docx ≠ report.docx` |
| 4 | 需目录层级时在 `path` 中写出；criterion description 引用交付物时**逐个写完整文件路径**（如 `output/<文件名>`），不要只写目录 | agent judge 靠 description 里的路径线索找文件，只给目录容易漏查文件却照 criteria 判"没写" |
| 5 | UTF-8，单个文件名 ≤200 字节，无控制字符；建议以题目编号为前缀 | 避免与 Agent 中间产物混淆 |

## 4. environment/

### 4.1 Dockerfile 硬性要求（每题一个）

- 公共依赖直接写全，**全部走官方源**（Debian / registry.npmjs.org / pypi.org）。**禁止使用任何国内镜像源**（npmmirror、aliyun pypi、docker registry mirror）——AP 平台部署在境外，官方源直连。
- 固定模板（照抄改写）：

```dockerfile
FROM python:3.12-slim
RUN useradd -m -u 1000 agent
# ① node/npm 是 claude CLI 的运行依赖；中文字体 + libreoffice 供交付物渲染/校验
RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates curl git bash jq ripgrep unzip nodejs npm \
        libreoffice-calc libreoffice-writer fonts-noto-cjk \
    && rm -rf /var/lib/apt/lists/*
# ② 预装 claude-code（钉死版本 2.1.114）——judge 在 verifier 判分容器内运行，harbor 安装器不负责该容器
RUN command -v claude >/dev/null 2>&1 \
      || npm install -g @anthropic-ai/claude-code@2.1.114; \
    command -v claude >/dev/null 2>&1 \
    && mkdir -p /root/.local/bin \
    && ln -sf "$(which claude)" /root/.local/bin/claude \
    && claude --version
# ③ pip 依赖：rewardkit + 基本解析库（官方 pypi.org）
RUN pip install --no-cache-dir \
        "harbor-rewardkit[all]==0.1.7" markitdown \
        openpyxl pandas python-docx pypdf python-pptx PyYAML chardet matplotlib
# ④ 本题执行侧依赖（无依赖交空 requirements.txt）
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt
COPY input_files/ /app/input_files/
RUN chown -R root:root /app/input_files && chmod -R a-w /app/input_files
RUN mkdir -p /app/output && chown -R agent:agent /app/output
WORKDIR /app
COPY skills/ /skills/          # 有 skill 时
```

- **有 skill 的题**：镜像构建须 `COPY skills/ /skills/`；技能所需依赖仍写入 `environment/requirements.txt`，构建期安装；确保**实际 Agent 用户**能读取技能及引用资料、执行脚本。

### 4.2 镜像硬性要求与自检

| 要求 | 安装自检 |
|---|---|
| Python ≥ 3.12，且有 `python3` | `python3 -V` |
| 有 bash | `bash --version` |
| 有 nodejs / npm（claude CLI 运行依赖） | `node -v` |
| 有 claude 可执行，**版本含 2.1.114**（judge 用，verifier 容器平台不代装） | `claude --version \| grep -q 2.1.114` |
| `harbor-rewardkit[all]==0.1.7` 且在 root 的 PATH 上 | `rewardkit --version` |
| pip 已装文档解析库（markitdown / openpyxl / python-docx / python-pptx / pypdf）——judge 读交付物依赖它们，缺装会大面积判负 | `markitdown --help` / `python3 -c "import openpyxl,docx,pptx,pypdf"` |
| 存在 agent 用户且对 `/app/output` 可写 | `su agent -c "touch /app/output/.w && rm /app/output/.w"` |

## 6. tests/（评分器）

### 6.1 运行链路（固定）

`harness` → `bash /tests/test.sh` → 分数落到 `/logs/verifier/reward.json` 与 `reward.txt`（单一数值）；
逐条明细由 `finalize.py` 复制一份到 `reward-details.json`（审计用，缺失不影响主分）；
评分不可用时按 AP 规范写 `reward_exit_message.json`（枚举 `judge:timeout` / `judge:api_error` / `judge:parse_error` / `judge:scorer_error` / `judge:invalid_output` / `judge:unknown`）。

- `test.sh` 与 `finalize.py` 是**平台固定模板，逐字复制、含注释一并保留、不得改动**。
- **判官是 claude-code agent judge**：以 CLI 进程跑在 verifier 容器内，自己用 Bash 工具读交付物（不再由 Reward Kit 预读塞 prompt）。每条 criterion **单独起 1 个 judge 会话独立评分**（`mode = "individual"`，逐条串行）。
- 供应商只负责 `rubrics.toml` 与 `prompt.md` 的内容。

### 6.2 rubrics.toml

```toml
[judge]
judge = "claude-code"          # 固定值
prompt_template = "prompt.md"  # 固定值
model = "qwen3.7-plus"         # 裁判模型，照抄
timeout = 7200                 # 单个 judge 会话超时（individual 模式下 = 每条一个会话）
mode = "individual"            # 每条评分点独立评分
weight = 1.0                   # 固定值，照抄

[[criterion]]
id = "R1"
name = "R1"                    # 恒等于 id（硬性要求，见 §6.5）
description = "…… Deliverables to inspect: `output/FIN-T2-001_财务分析报告.xlsx`."
type = "binary"                # binary | likert
weight = 10.0                  # 只允许 3.0 / 7.0 / 10.0
```

### 6.3 prompt.md

模板（可直接复制，把交付物格式按题目实际情况调整），六条规则：

1. `{criteria}` 占位符**必须保留**（Reward Kit 把 criterion 列表渲染进去，删掉 judge 收不到评分项）。
2. `Fairness anchor` 段**不要删**、也不要加任何评分宽严表述（工具提示被误读成"放宽判分"会使严格度漂移）。
3. `Material map` 段**不要删**——须显式写明三区语义：`/app/output/`（唯一评分对象）、`/app/input_files/`（只读证据）、`/tests/__golden_output/`（参考解）。
4. `Reference-solution policy` 段**不要删、不得弱化**——尤其"不得因参考答案满足就给分"与"不得逐值比对"两条。
5. 工具提示段保持"提示"而非"强制"——列出容器内可用解析途径供 judge 选用。
6. 总量上限：`prompt.md` 模板 + 全部 criterion description 之和 **< 100 KB**（prompt 经命令行参数传给 judge，超长会 E2BIG 直接起不来）。

### 6.4 criterion 字段约束

| 字段 | 约束 |
|---|---|
| `[judge].judge` | 固定 `"claude-code"` |
| `[judge].model` | 合法 LiteLLM 模型串，按示例照抄（`"qwen3.7-plus"`）；运行时被 `REWARDKIT_MODEL`（test.sh 由 `JUDGE_MODEL` 派生）覆盖，toml 值是兜底 |
| `[judge].prompt_template` | 固定 `"prompt.md"` |
| `[judge].timeout` | 缺省仅 300，**必须显式写 7200**；会话超时不写 reward.json，整题无分。且须 < `[verifier].timeout_sec`（18000） |
| `[judge].weight` | 固定 `1.0` 照抄，不参与主分，只影响审计值 |
| `[judge].mode` | 必写 `"individual"` |
| `[scoring].aggregation` | 固定 `"weighted_mean"` |
| `[[criterion]].id` | 必填，题内唯一，与 `rubrics.json` 对应条目编号保持一致 |
| `[[criterion]].name` | **必填，恒等于 id** |
| `[[criterion]].description` | 单条可独立判定的标准 + 待查交付物路径清单；likert 条目还须含各档位锚点 |
| `[[criterion]].type` | 只允许 `binary` 与 `likert`；likert 时 judge 输出 1–5 整数 |
| `[[criterion]].points` | likert 必填，固定写 `5` |
| `[[criterion]].weight` | 只允许 `3.0` / `7.0` / `10.0` |
| `[[criterion]].negate` | `true` = 该条描述"候选犯了什么错"；判官判"存在"得 0、"不存在"得 1 |

### 6.5 权重档位 ↔ 重要级别

| 级别 | 原分数 | 写法 |
|---|---|---|
| Critically Important | +10 | `weight = 10.0` |
| Important | +7 | `weight = 7.0` |
| Slightly Important | +3 | `weight = 3.0` |
| Slightly Detrimental | −3 | `weight = 3.0 + negate = true` |
| Detrimental | −7 | `weight = 7.0 + negate = true` |
| Critically Detrimental | −10 | `weight = 10.0 + negate = true` |

> **扣分只能 `negate = true` + 正 weight，绝不能写负数 weight**——负 weight 条目会被平台聚合脚本判为异常剔除并记 `verifier_error = 1`，扣分静默失效、整次评分作废重评。

### 6.6 三条硬性写法（缺一即整题判分崩溃 / 静默 0 分 / 档位漂移）

1. 每条 criterion **必须写 `name = "<id>"`**（与 id 相同）。不写时 name 由 description 自动 slugify，**纯中文 description 会生成空串**，全部条目键塌缩 → Reward Kit 解析崩溃。
2. `description` 里**必须写明待查交付物的完整路径**（`Deliverables to inspect:` 清单，路径形如 `output/<文件名>`）。
3. `type = "likert"` 的条目，**必须显式写 `points = 5`** 且在 description 里写明档位锚点——锚点按 **5/4/3/2/1** 逐档写明可独立核验的具体情形。不给锚点则中间档位不可复现、不可审计；锚点写成 0–1 小数会被输出 schema（integer）拒掉。

### 6.7 评分机制（供应商不自行聚合，由 finalize.py 全题池化）

```
S_max（满分基准） = Σ 全部正向条目的 weight        ← 负向条目不进分母
分子             = Σ 正向 weight × value − Σ 负向 weight × (1 − value)
主分 reward      = clip(分子 / S_max, 0, 1)
```

value 取值：`binary` → 0 或 1；`likert` → judge 输出 1–5 整数，Reward Kit 归一化为 `(raw−1)/4`（1→0、2→0.25、3→0.5、4→0.75、5→1）；`negate = true` 的条目自动翻转（"完全没违规" = 1.0）。

数值算例（points = 5、weight = 7.0）：正向条 raw 5/4/3/2/1 → 计入 +7 / +5.25 / +3.5 / +1.75 / +0；negate 条按违规程度 raw 5/4/3/2/1 → 扣 7 / 5.25 / 3.5 / 1.75 / 0。

> **负向条目优先用 binary**：违规通常"成立/不成立"没有中间态，且负向多档在现网无生产先例、判官一致性缺少验证；确需按违规程度分档扣分时才用 likert，并把每一档写到可独立核验。

### 6.8 Rubric 细则要求（五项准则，每条先过五关）

| 检查项 | 标准 |
|---|---|
| 原子性 | 每条判据仅检查一个方面（避免捆绑多个独立事实/多个可接受值） |
| 客观性 | 判据为可客观验证的事实性陈述，不含"风格/美观"等过于主观表述 |
| 区分度 | 正负样本明显区分；正分判据能区分"部分正确"与"完全正确" |
| 完整性 | 覆盖多个维度 |
| 鲁棒性 | 多次 judge 判断基本稳定 |

单条打分项要求：原子性、准确无歧义（不推荐"收入实现了明显增长"，推荐"收入同比增长了 65%"）、可独立判断、来源合理（项目描述明确要求 / 参考文件明确要求 / 可合理推导的隐含要求）、有明确判定锚点（不推荐"PPT 排版美观"，推荐"单页正文不超过 150 字，文本无明显遮挡、重叠或溢出"）、客观可验证、粒度合理、明确打分对象。

打分项之间：互不重复互不冲突、具有区分度、整体覆盖完整、权重体现重要性、允许合理亮点项、判断结果稳定（鲁棒性）。

补充字段语义：
- `criterion_type ∈ {Objective, Subjective}`（Objective = 可度量可验证；Subjective = 需判断与语境解读）
- `criterion_necessity ∈ {Explicit, Implicit}`（Explicit = prompt 中逐字明文给出；Implicit = 必然推导）
- `type ∈ {Binary, Gradient}`（Gradient 对应 harbor 的 likert；存在程度差异且对质量有意义时用）

### 6.9 评价维度 dimension

| 一级维度 | 二级标签 | 主要检查什么 |
|---|---|---|
| **指令遵循【必须】** | — | instruction 中显式要求的内容与交付约束是否被完整执行（范围限定、数量、命名、路径、格式、单位、精度、明确要求包含或禁止的内容）。**只检查 instruction 明确提出的要求**；内容本身是否正确/专业/深入归入内容质量维度 |
| **内容质量【必须】** | 结论正确性 | 基于已有事实/数据/分析形成的最终判断、结论、推荐或决策是否正确，是否与证据一致 |
| | 数值与计算准确性 | 数值提取、公式计算、统计口径、单位换算、聚合方式、分母选择、时间范围、精度及容差 |
| | 专业规范 | 是否符合任务所属行业/领域的专业知识、规则、标准、通行实践（会计准则/法律规则/医学规范/行业标准/术语/业务口径） |
| | 分析与论证质量 | 事实、数据、引用是否忠实于输入材料及可验证客观事实；引用来源是否真实可追溯；跨文件处理是否正确区分主体/版本/时间/口径 |
| | 事实忠实性 | 同上（溯源不到即视为编造，违反事实性） |
| | 内容逻辑性与分析深度 | 分析到位、论证充分、有没有回答真问题、洞察深度；论点有准确论据支撑 |
| | 结构与组织 | 信息架构与组织方式是否合理（章节/页面结构完整、层级清晰、顺序合理、关键模块不缺失） |
| 操作与交付安全 | — | 是否安全处理用户已有文件与 workspace；不得误删/覆盖/破坏无关源文件，不得因编辑或格式转换造成数据/公式/页面丢失 |
| 安全合规 | — | 隐私、数据安全、版权、法律法规及业务合规；避免泄露敏感信息、违规使用内容或产生误导、偏见 |
| 超预期贡献 | — | 其他要求都满足后进一步提升交付价值的部分（事实二次核对、产物兼容性与易用性、防呆设计、指出 instruction 疏漏） |
| 视觉美感 | — | 排版、配色等（**仅针对交付物有美观度要求时配置，普通任务不建议包含**） |

**不同维度的权重设置要求**：内容质量、操作与交付安全**总是较高 weight**；PPT 等设计类交付物视觉美感与格式规范维度应较高 weight；行业性突出的交付物专业规范维度应较高 weight；写作类交付物结构与组织维度应较高 weight；数学计算要求较高（如金融场景）数值与计算准确性维度应较高 weight。

### 6.10 打分项分布要求

- **领域锚点占比**：交付物内容质量维度（其下所有二级标签）锚点正分，占全部正分的 **30% 以上**。
- **关键项占比**：每题**至少包含 2 条 Critically Important（+10）**评分项。
- **−10 分项**：仅用于重大专业错误、幻觉、业务安全、合规风险等真正影响答案可信度的情形，**不得滥用**。
- 一般来说，**指令遵循、结论正确性、分析与论证质量、事实忠实性这些维度总是需要的**；行业性突出的交付物覆盖专业规范维度；PPT 等设计类覆盖视觉美感与格式规范维度；写作类覆盖结构与组织维度；数值计算要求较高的（如金融）覆盖数值与计算准确性维度。

### 关键设计契约（判分可靠性）

| 契约 | 语义 |
|---|---|
| `reward.json.reward` | 主分；评分不可用时刻意记 0 |
| `reward.json.verifier_error` | **1 = 本次评分不可信**（判官限额/超时/评分器异常），须**重评**而非记零分 |
| `reward.txt` | 单一数值，与 reward.json 的 reward 一致 |
| `reward-details.json` | 逐条明细（审计件），缺失不影响主分 |
| `reward_exit_message.json` | **仅评分不可用时存在**；成功则删除 fail-closed 占位 |
