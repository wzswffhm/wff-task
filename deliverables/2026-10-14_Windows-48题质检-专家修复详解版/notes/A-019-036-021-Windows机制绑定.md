## 0. 总结论

这三道题把"Windows 价值"注入在**三个互不重叠的层次**上，而且每一层都有一条"非 Windows 上必然失败"的硬闸门：

| 层次 | 019（NTFS 文件） | 036（注册表） | 021（命名管道） |
| --- | --- | --- | --- |
| 题面显式声明 Windows 专属 | 明确写"目标是真实的 Windows NTFS 语义，**不需要实现其他操作系统版本**"（L5），并逐条点名 `FILE_SHARE_*`、硬链接、DACL/继承保护、命名数据流（L31–L64） | 指定"Windows Server 2022 x64、PowerShell 7.4.18"（L3），逐条点名 REG_DWORD/REG_QWORD/REG_BINARY/REG_MULTI_SZ/REG_EXPAND_SZ 的原生语义（L7） | 指定"Windows NamedPipe + Message transmission mode"（L5），"验收使用真实 Windows 管道和外部独立服务进程"（L11） |
| 环境构造 Windows 唯一前置条件 | Windows 容器 + `net user BenchAgent /add` + `icacls 'BenchAgent:(OI)(CI)M'`（Dockerfile L8–L16）；真实验证 `csc.exe`（validate_environment.ps1 L3–L4） | `validate_environment.ps1` 硬校验 `PSVersion 7.4.18` + `Build 20348`，并在 `HKCU\Software` 真实建/删子键探测（L2–L5） | `validate_environment.ps1` 校验 `$IsWindows` 且 `[IO.Pipes.PipeTransmissionMode]::Message` 可用（L2–L3）；adapter 为 `native-windows`（adapter.toml L1） |
| 验证层用原生 API 观测，而非跨平台等价 | C# 真实验证器 P/Invoke `FindFirstStreamW`/`CreateHardLinkW`/`CreateFileW`（Verifier.cs L202–L210），比对 SDDL 字符串与创建时间（L253–L264），进程级 `FileShare` 占用（L413–L420、L480–L532） | 真实 `RegistryAclGuard.cs`：P/Invoke `RegSetKeySecurity` 注入 Deny ACE（L31–L37）、`RegNotifyChangeKeyValue` 在候选首写后撤销写权限制造真实回滚失败（L38–L42）；测试用 `GetValueKind`/`DoNotExpandEnvironmentNames` 读原生类型（run_tests.ps1 L22、L71） | 独立服务进程使用 `NamedPipeServerStream(..., PipeTransmissionMode.Message, Asynchronous)`，用 `IsMessageComplete` 做真实消息边界（server.ps1 L6–L7）；用外部健康证明与总期限约束候选（run_tests.ps1 L11–L17） |
| 非 Windows 必然失败点 | `Environment.OSVersion.Platform != PlatformID.Win32NT` → 抛异常；`DriveInfo(...).DriveFormat != "NTFS"` → 抛异常，两者都使全部用例进入 preflight_error（Verifier.cs L601–L602、L611–L617） | `[Environment]::OSVersion.Version.Build -ne 20348` → throw（validate_environment.ps1 L3）；ACL 故障注入依赖 advapi32 原生 ACE | `$IsWindows` 为假直接 `exit 1`（validate_environment.ps1 L2）；`Message` 传输模式是 Windows 命名管道独有 |
| 反作弊强度 | 强（ExecGuard：独立账号登录 + Job Object + 私有 window station/desktop + 受保护 receipt + 守卫探针自检） | 中强（真实键状态双向对照；ACL/原生通知注入无法被内存模拟绕过；31 用例齐全性硬校验） | 中（真实管道 + 独立服务端审计字段 + stall/disconnect 反 sleep 短路用例） |

**给返修的直接结论**：这道题的甲方判词"没有依赖 Windows 专属机制"并非要求"必须出现某个 API 名字"，而是要求在**题面（点名机制与共享/ACL/原生类型语义）+ 环境（真实 Windows 前置条件与硬校验）+ 验证（用原生 API 观测真实现象，跨平台等价实现必然失败）**三处同时闭合。019 的"共享模式读句柄 + 硬链接身份 + SDDL 对比 + ADS 枚举"、036 的"注册表原生类型位模式 + Deny ACE 故障注入"、021 的"Message 模式分帧 + 外部服务进程审计"是三套可独立照搬的模板。

## 1. 样本 A：`extracted/019` — `win-fs-001`（NTFS ACL / ADS / 元数据 / 原子替换）

### A.1 题面层（`instruction.md`）

**是否显式声明"不依赖其他操作系统"：是。** 这是三题中唯一一句明写的。

关键原文抄录与解释：

1. L5：
   > 请修复工程，使下面的公开行为成立。目标是真实的 Windows NTFS 语义，不需要实现其他操作系统版本。

   —— 直接声明验收锚定在 NTFS 语义，且**主动豁免**"其他操作系统版本"，等于告诉候选：跨平台等价写法不算达标。

2. L11：
   > `build.ps1` 使用 Windows 内置的 .NET Framework 4.x C# 编译器，语言级别 C# 5，递归编译 `src/*.cs`，生成 `bin/WinPublish.exe`。可使用 .NET Framework 4.8 标准库以及 Windows API，不联网下载依赖。

   —— 允许并暗示使用 Windows API；构建链本身绑定 `%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe`。

3. L25：
   > 源和目标都已存在且是普通文件，位于本机同一个 NTFS 卷；本题不涉及跨卷发布、UNC、超过 240 字符的路径、重解析点、只读/加密/压缩文件或系统崩溃恢复。源文件可以位于不同目录。

   —— 显式圈定 NTFS 卷与路径长度上限，并把重解析点排除出题（避免歧义），但把"同一 NTFS 卷"变成前置条件。

4. L35（R2）：
   > 若旧目标已被读取进程打开，且它授予 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`，发布应成功；该旧句柄仍必须完整读到旧内容，重新打开目标必须读到完整新内容。不能先删除目标再创建，也不能原地截断/写入目标。同步好的持续读取进程只能看到完整旧内容或完整新内容，不能看到目标消失、空窗或半写数据。

   —— 直接写 Windows 共享模式常量名，并规定"不许 Delete+Create、不许原地截断"；这三条只在 Windows 文件共享/替换语义下才有意义。

5. L39（R3）：
   > 成功发布必须保留原目标的创建时间、DACL（包括继承保护状态）、所有已有命名数据流的名称和原始字节。只发布源的默认数据流，不引入源的命名数据流，也不让源的同名流覆盖目标的流。不要用暂存目录的默认权限替代目标的权限。

   —— DACL + 继承保护（`AreAccessRulesProtected`）+ NTFS 备用数据流（ADS）三项机制同时点名。

6. L43（R4）：
   > 对合法批次，如果任一目标的 Windows 共享限制阻止替换（例如另一个健康进程持有未授予 `FILE_SHARE_DELETE` 的读句柄），命令必须有限时间内失败，而不是等对方退出或强行关闭其句柄。

   —— 把"共享冲突"规定为**必须失败且必须回滚**的合法结果，而不是要绕过的障碍；这正是 Windows 独有的行为面。

7. L51（R5）：
   > 不同路径不代表不同文件；硬链接身份验证必须利用真实文件系统。

   —— 点名 NTFS 硬链接身份（同一 FileID），并要求用真实文件系统验证，禁止纯字符串归一化糊过去。

8. L62：
   > 验收时只比较目标原有的 DACL 及其继承保护状态；不要求复制目标的 owner/group 字段，也不得把源文件的安全描述符带到目标。

   —— 把验收口径收窄到 SDDL 的 DACL 部分，消除不可比噪声，同时明确"源安全描述符不得污染目标"。

**机制名清单（题面出现）**：NTFS 卷、`FILE_SHARE_READ/WRITE/DELETE`、硬链接、DACL、继承保护状态、命名数据流（ADS）、原子可见性、批次回滚。

关键原文抄录与解释：

1. L3：

2. L5：
   > UTF-8 JSON 补丁包含字符串 `Root`（`HKCU:\` 下的非空路径）和数组 `Operations`。……键和值名忽略大小写，字符按字面处理；不接受 `.`、`..`、绝对 Path、冒号或 NUL。目标键必须已经存在，工具不创建或删除键。

4. L9：
   > 原子模式先检查整批目标键是否存在且可写，任何一项不合格都不落盘：问题项 Failed，其余 Skipped。检查通过后按顺序执行；操作失败就把本批已改变的值恢复到执行前的存在性、类型和完整内容，成功恢复的项记为 RolledBack，失败项 Failed，后续项 Skipped，原来未改变的项仍是 Unchanged/AssertPassed。……回滚也失败时，该项记 RollbackFailed 并提供 Error，退出码仍为 2。

5. L11：
   > Preview 根据每个目标在调用开始时的状态报告 WouldSet、WouldDelete、Unchanged 或 AssertPassed/Failed，Applied 和所有 Changed 都是 0/false，不允许注册表发生变化。

6. L13：
   > 全部操作成功退出 0，操作或回滚失败退出 2。参数、JSON 结构、值类型/范围、路径语法、原子重复目标或报告路径不可用退出 3，这类输入错误必须在任何注册表变更前被发现。

**是否显式声明"不依赖其他操作系统"：没有这句原话**，但把"真实 Windows 管道 + 外部独立服务进程 + Message 模式"写进验收定义。

关键原文抄录与解释：

1. L1：
   > 我们有个 Windows 本地命名管道服务，客户端遇到长消息和中文时会把一条报文读坏。请修好 workspace/candidate.ps1。它连接外部已启动的服务端，不自己启动服务。

   —— 明确"外部已启动的服务端"，候选不能自造服务端自测。

2. L3：
   > 入口参数是 -PipeName（不带 \\.\pipe\ 前缀的唯一管道名）、-Messages（string[]，每个元素是一段合法 JSON 文本，默认空数组）、-TimeoutMs（100 到 15000 的整数，默认 5000）。……

   —— 参数面直接暴露 Windows 命名管道命名空间 `\\.\pipe\`。

3. L5：
   > 服务端是本机当前用户可访问的双向 Windows NamedPipe，使用 Message transmission mode。每次发送调用对应一个完整 UTF-8 JSON 报文，没有 BOM、长度头、分隔换行或额外终止字节；一条报文可能超过一次读取的缓冲区。

   —— 点名 **Message transmission mode**（Windows 命名管道独有：字节模式/消息模式之分）；"一条报文可能超过一次读取的缓冲区"意味着必须靠消息边界而不是"读到 JSON 解析成功为止"。

4. L7：
   > 连接后先接收服务端的 {"kind":"ready"}。然后按 Messages 顺序发送 {"kind":"data","seq":i,"payload":原文本}，每发送一条都等服务端对应的 {"kind":"ack","seq":i,"payload":原文本}，确认后才发下一条。……空数组也必须完成 ready/complete/done 握手。

   —— 逐条 ACK 的请求/应答握手，天然要求"一次写=一条消息"。

5. L9：
   > 返回且只返回一个对象：Status="completed" 或 "timeout"；Acks 是 string[]，包含已收到正确 ACK 的原文本，顺序不变。TimeoutMs 是从调用开始计量的整体通信期限，涵盖连接、ready、消息传输、ACK 和 done；服务端不出现、停在任一步或者在 done 前断开时返回 timeout，保留之前已确认的 Acks，结束并关闭管道。不能靠固定等待时间推断服务已健康或消息已结束，不输出日志，不访问网络或改动工作区其他文件。

   —— "总期限 + 前缀保留"+"不能靠固定等待时间推断"是明确的反 sleep/反轮询短路条款；"不改动工作区其他文件"是防污染条款。

6. L11：
   > 服务端使用上述协议且输入可信；不要求处理畸形协议、超过 1MB 的单条报文或其他用户的服务。验收使用真实 Windows 管道和外部独立服务进程。环境是 Windows Server 2022 x64 build 20348、PowerShell 7.5.10、NTFS，离线运行。只修改 candidate.ps1；保持这个参数入口。

   —— **"验收使用真实 Windows 管道和外部独立服务进程"** 是这一题的题面级 Windows 绑定声明，等价于 019 的 L5。

**机制名清单（题面出现）**：Windows 本地命名管道、`\\.\pipe\` 前缀、双向管道、Message transmission mode、UTF-8 无 BOM 报文、逐条 ACK 握手、总超时（含连接阶段）、NTFS、Windows Server 2022 build 20348、PowerShell 7.5.10。

### C.4 反作弊 / 反短路

- **服务端是外部独立进程**，候选只能通过命名管道协议说话；无共享内存、无文件哨兵可伪造。
- **健康与否由服务端证明，不由候选声明**：`constructed / message_mode / connected`（run_tests.ps1 L17）；`completed` 还要求 `done_sent && complete_received && !error`。
- **反 sleep 短路**：`stall_ready` / `stall_ack` / `stall_done` 三个模式让服务端在关键步骤故意不回包；候选若用固定 `Start-Sleep` 猜"完成了"，返回 `completed` 会与期望 `timeout` 不符；若把总超时实现成"每条消息各自计时"，`ack_deadline_preserves_prefix` 要求已确认前缀 `@('first')` 仍被保留，也会暴露。
- **反"协议外探测"**：`no_server_timeout` 在没有服务端时必须 `timeout`，禁止"探测到没有服务端就当成功"。
- **反缓冲区取巧**：`long_message` 12KB + 服务端 211 字节缓冲 + `IsMessageComplete` 三件套强制真正的消息分帧实现。
- **反污染**：`unrelated-keep.txt` 与题面"不访问网络或改动工作区其他文件"呼应。
- 用例分组语义清晰：`long_message`/`unicode_roundtrip`/`multiple_message_boundaries` 为 F2P（修复前必失败），其余为 P2P。

### 4.4 反作弊 / 反短路必做项

1. **"真的调用了机制"要可观测**，而不是靠候选自述：
   - 019：候选必须让共享句柄仍能读到旧内容、让硬链接身份被发现、让 SDDL 逐字符保留；
   - 036：`Demand ($guard.Applied)` —— 候选若不真写注册表，内核通知不触发，用例必失败（run_tests.ps1 L237）；
   - 021：`message_mode/connected/done_sent/complete_received` 由**服务端**给出（L17）。
2. **双向对照**：候选报告 vs 测试进程直接读真实对象（036 `Check-Report` + `Read-Val` + `Snapshot`；019 stdout JSON + `Snap`）。
3. **故障注入用原生手段**：DACL Deny ACE（036 L34）、注册表通知（L39）、共享模式占位（019 L417/L451）、服务端 stall/disconnect（021 L25–L32）。
4. **注入前先断言"候选确实产生了预期副作用"**，否则失败原因会指向错误的地方（036 L237）。
5. **防"先改后回滚"**：`FileSystemWatcher` 监听 `NotifyFilters.Security` 的零变更断言（019 L159–L184）；`Snapshot -ceq $before` 的精确 before-image 断言（036 L139、L143、L147、L151）。
6. **防探测测试资产**：候选账号对 `C:\tests`、验证器日志目录无读/写权限，并用探针自检该事实（019 test.ps1 L37–L63、L80–L82；GuardProbe.cs L19–L24）。
7. **防残留与防伪造回执**：Job Object + `KillOnJobClose` + `TerminateJobObject`（ExecGuard.cs L276、L303）；回执文件用显式 DACL `CreateNew`（L326–L341）；验证器强校验回执字段（Verifier.cs L93–L99）。
8. **防"靠睡眠猜状态"**：题面明写禁止（019 L59、021 L9），并用 stall/missing 用例令其暴露（021 L25–L26、L30–L32）。
9. **防污染**：无关文件不变断言（021 L3、L18）；`C:\agenttmp` 清单集合相等（019 Verifier.cs L106）。

### 4.5 常见坑

- **只写"用 Windows API 也可以"，却不写机制语义** → 候选全部用跨平台写法也能过，正是本次返修被质疑的形态。必须像 019 L35–L51、036 L7、021 L5 那样把机制**写进可验收的行为**。
- **验证层只用 .NET 便捷 API**（如 `File.ReadAllBytes`、`Registry.GetValue`）→ 观测不到 ADS/ACL/SDDL/位模式。必须下沉到 P/Invoke 或至少 `GetValueKind`/`DoNotExpandEmptyEnvironmentNames`/`GetSecurityDescriptorSddlForm`。
- **在题面里断言"必须调用某 API"** → 不可验证且限制实现自由。正确做法：像 019/036/021 一样**只描述可观测行为与原生类型结果**，再用故障注入迫使候选必须真正落到机制上。
- **`ExpandString` 用默认 `GetValue` 读** → 会被展开成 `C:\...`，导致"保存原文"契约永远判错（036 用 `DoNotExpandEnvironmentNames`，run_tests.ps1 L22）。
- **ACL 断言包含不可控噪声**（owner/group、SDDL 里 SACL）→ 必须像 019 L62 那样显式限定比较范围。
- **不使用容器/专属账号就做 ACL 注入** → 可能污染宿主。019 用 `WINBENCH_DISPOSABLE_CONTAINER=1` + `-TrustedLocal` 双开关把关（test.ps1 L8–L10）。
- **NamedPipe 用 Byte 模式或按"能解析 JSON"当帧结束** → 长报文必错。必须 Message 模式 + `IsMessageComplete`（021 server.ps1 L6–L7）。
- **超时按单条消息计时** → 与"总期限 + 前缀保留"契约不符（021 rubric L46–L54 的三个 `R3` 用例）。
- **评分清单允许缺失/多余用例** → 必须像 036 aggregate L6、019 test.ps1 L94–L96 一样硬校验数量与集合，否则删掉难题即可拿分。
- **镜像不钉 sha256 / 不校验 build 号** → 换环境后"Windows 价值"悄然消失，且不可复现。
