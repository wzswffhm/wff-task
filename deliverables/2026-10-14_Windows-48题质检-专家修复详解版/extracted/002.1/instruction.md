# LiteMonitor：状态镜像的变更检测从定时轮询改为注册表事件驱动

## 背景

LiteMonitor 会把一份机器可读的运行状态镜像发布到当前用户的注册表键下（见 `src/Core/StatusMirror.cs`），
供插件宿主、内置网页服务这类外部消费方在应用完整启动之前就读到上次的运行状态。

消费方需要「镜像一变就立刻知道」。现在的做法是 `StatusMirror.StartRefresher` 内部挂一个周期性定时器，
每 200 毫秒打开一次注册表键、比较发布代号（Generation）的数值，变了才回调：

* 空闲时也在反复开键读值，白烧 CPU；
* 最坏有 200 毫秒的延迟；
* 只有代号的**数值**变化才算「变了」——消费方改写镜像里的其它字段（例如主题名），
  或者把代号重写成同样的数值，订阅方都收不到通知。

仓库里已经为这件事准备了一个辅助类型 `src/Core/RegistryNotify.cs`：它对外声明了「订阅镜像键的值变更」
和「读取镜像键的最后写入时间」两个公开方法，但两个方法目前都只是 `throw new NotImplementedException()` 的空壳，
也从来没有被接进 `StartRefresher`。

## 本轮迭代目标

1. 实现 `RegistryNotify` 的两个公开方法：对状态镜像注册表键的**值变更**做事件驱动的订阅通知，
   以及读取该键的最后写入时间（以 UTC 表示）。
2. 把 `StatusMirror.StartRefresher` 从「定时轮询比较代号」改造成基于上述订阅的事件驱动实现，
   并清掉不再需要的遗留轮询代码。

## 验收标准写在哪里

`src/Core/RegistryNotify.cs` 与 `src/Core/StatusMirror.cs` 里冻结的契约文档，逐条写明了本题**全部**
可观测验收要求：时延上限、空闲时的 CPU 开销上限、通知的触发范围与过滤语义、连续变更与密集突发写入下的
自动重新挂接、多个订阅共存与退订语义、回调自身抛异常时的行为、目标键被删除重建（含整棵镜像树被彻底清理后
重新发布）时的自愈、最后写入时间的时间刻度与 `DateTimeKind`、键缺失时的返回值与「不得代为创建」、
以及任何情况下都不得抛异常。

这些约定会被一个独立评测器在真实 Windows 上逐条执行验证（跨进程写注册表、删除并重建键、量测空闲 CPU、
强制结束进程等等）。**文档没有写明的行为一律不作要求。** 动手之前请把这两份契约完整读一遍。

这里的“值写入/同数值重写”指 Windows 实际产生值变更通知的操作，例如保留逻辑数值但改变注册表值类型。
类型与字节内容均完全相同的幂等写入可能被 Windows 合并，不要求为系统未产生的通知补发回调。
最后写入时间是操作系统记录的键元数据：没有写入时，多次读取必须保持不变，不能用读取时的当前时间代替。

## 硬性约束

* 公开契约冻结：`RegistryNotify` 与 `StatusMirror` 的公开成员名称、签名、常量值，以及 `StatusSnapshot`
  的形状和 `Publish` / `TryRead` / `ReadGeneration` / `Purge` 的既有行为，都不得修改；只能补实现。
* `LiteMonitor.csproj` 与 `LiteMonitor.sln` 冻结；**不得新增任何 NuGet 包引用**（判分环境全程断网，
  只有已 vendored 的离线包可用）。只能用 net8.0-windows 自带的 BCL 与操作系统原生能力。
* 不得保留、也不得改回任何形式的周期性轮询来判断「有没有变化」。
* 工程必须在 `dotnet build LiteMonitor.csproj -c Release` 下 0 error，既有功能行为不得回归。
* 判分前后被测工作树必须干净：临时验证用的小工程、脚本、日志或构建产物都不要留在仓库里
  （构建输出的 `obj/`、`bin/` 已被重定向到仓库之外）。
* 本次只做标准的 Harbor E1 试标范围内的这一轮迭代，不要顺手扩展其它需求。
