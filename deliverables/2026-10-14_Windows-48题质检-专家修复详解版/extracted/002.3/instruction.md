# Repair the NTFS deployment approval workflow

PathAclTool now supports a deployment approval workflow: an operator reviews an offline plan, then another process applies it later. The current implementation eagerly changes ACLs during planning and blindly repairs a saved pathname during application. A deployment can therefore modify a different NTFS object, overwrite intervening policy, or partly grant access before discovering an unwritable descendant. Repair the complete workflow, not just the original recursive ACL grant.

## R1. ACL reconciliation and compatibility

PathAclTool recovers shared staging trees after a Windows deployment. A staging root can already contain ordinary legacy work directories, protected private files and directories, directory junctions, and file symbolic links. The current tool still prints `acl-ready`, but ordinary legacy files and new descendants do not reliably receive the Builtin\Users Modify grant. Re-running it also leaves duplicate or stale grants on the root.

Make the tool reconcile a staging root so Builtin\Users has one usable, inheritable Modify grant on the root, and so ordinary existing as well as subsequently created descendants receive that inherited access. Ordinary legacy content can carry a stale explicit Builtin\Users Modify entry from an earlier deployment; replace that managed entry with inheritance. Preserve everything that is not the managed Modify grant: unrelated allow entries, deny entries, owners, inherit-only identities, non-ACL file attributes, and alternate data streams. A Builtin\Users ACE that is not the managed Modify grant must stay. The tree can contain non-ASCII names.

Do not weaken, traverse, or rewrite protected-DACL files or directories, and do not follow a reparse point or change its target. Report how many protected objects and reparse points were skipped. Repeated runs must converge without accumulating managed root ACEs. Keep the existing `net8.0-windows` entry point: `dotnet run --project src/PathAclTool -- <staging-root>`. Invalid invocation must retain its existing usage behavior. Do not solve this by granting Administrators access, replacing a whole DACL, or changing protected private content.

The root itself is the explicitly requested reconciliation target, even when its DACL is protected. The protected-DACL exclusion applies to descendants. Keep the existing success report fields `protected=<decimal count>` and `reparse=<decimal count>` (counts have complete decimal boundaries). A new staging root may be created. Managed Modify means Modify, optionally with Synchronize, not broader FullControl.

The managed family consists of explicit Allow ACEs for Builtin\Users with exactly that mask, regardless of their old inheritance or propagation flags. Old deployments can leave duplicate entries, object-only or container-only inheritance, NoPropagateInherit, or InheritOnly entries. Normalize these managed root entries to one effective grant applying to the root and all descendant levels; remove managed explicit entries from ordinary descendants. Inherit-only entries for other identities and Users entries with other masks remain foreign policy and must be preserved. In particular, foreign explicit entries retain their SID, Allow/Deny type, mask and flags even if the managed grant makes their access redundant; harmless reordering within an equivalent Allow block is permitted. The preservation rule does not require keeping a stale managed InheritOnly entry. Validate the actual persisted ACL, not only a view that might coalesce duplicate entries.

Modify only C# source files under `src/PathAclTool/`; new source files are allowed. Preserve the public entry point and report contract. Project files, dependency configuration and target framework are frozen; no additional packages or external downloads are available. The supplied root is an ordinary directory (or a new directory path); descendant reparse points are boundaries, not reconciliation targets.

## R2. Read-only durable planning

`PathAclTool --plan <existing-root> <new-plan.json>` must capture an approval snapshot without changing the root or any existing object's security, data, streams or attributes. It exits 0 and prints `acl-planned`. The plan is a UTF-8 JSON file outside the staging tree, created without overwriting an existing file. Do not create a missing root in plan mode. The file must be sufficient for a later fresh process: no process-local state, companion files or fixed-location cache. Copying/renaming the plan outside the tree must not invalidate it. The original one-argument command remains available, including creation of a new root.

The public envelope is `{"formatVersion":1,"rootPath":"<absolute root>","entries":[...]}`. Each entry has a canonical `relativePath` (`.` for the root; otherwise a nonempty relative path without empty, dot, parent, rooted or alternate-stream components). Include the root, ordinary descendants and encountered protected/reparse boundaries; do not inventory children below either boundary. Other entry fields and their representation are your choice; retain sufficient information for R3. JSON property order and entry array order are not significant. Reject malformed envelopes, unsupported versions, missing root entries, duplicate paths (case-insensitive), and escaping paths with exit 2 before touching the tree. Plans are operator-owned, not cryptographically authenticated; no signature or hostile concurrent plan-writer defense is required.

## R3. Apply a reviewed snapshot, not a pathname

`PathAclTool --apply <plan.json>` must check the entire reachable inventory before any ACL mutation. Compare NTFS object identity (volume and file ID), ordinary/directory/reparse kind, protection state, and owner/group/DACL, including inheritance flags. Detect root or descendant replacement even when pathname, bytes, length, timestamps and ACL are copied exactly. Additions, removals and renames in the inventoried scope invalidate approval. Reparse points are inventoried as link objects, never as targets. A changed boundary itself is a conflict; changes below a protected directory or in an external link target are out of scope and must not invalidate approval.

On any snapshot conflict, exit 3, print `acl-conflict`, and leave all objects at their immediately-before-apply state (including earlier siblings and the root). Do not repair any object before discovering a late conflict. File contents, ADS, non-type file attributes and timestamps are not approval keys: such changes alone must be accepted and preserved. A plan is an approval of a pre-state, not a command to restore old data or replay saved DACLs. Successful application performs R1, exits 0 and reports `acl-ready` with the existing skip counts. Applying the same old plan after an ACL-changing successful application is a conflict, not implicit permission to apply again. A fresh plan of the reconciled tree can be applied successfully without security drift.

## R4. NTFS aliases and all-object access preflight

Ordinary unprotected files with more than one NTFS hard-link name are unsafe reconciliation targets: changing their DACL affects every name, including names outside the approved root. Refuse the entire operation with exit 4 and `acl-unsafe`, before any ACL write, whether the other name is inside or outside the root. Detect a hard link added after planning as unsafe as well. Do not follow/search external names or break links. Protected files and reparse boundaries remain excluded; do not reject merely because a skipped protected file has aliases.

Before changing any ACL, establish that every to-be-reconciled object can actually be opened with READ_CONTROL and WRITE_DAC under the current Windows token. A readable but non-writable late descendant must cause exit 1 and `acl-failed` with the entire tree unchanged, not partial repair or a swallowed error. Apply this preflight and alias policy to the one-argument command as well. Do not take ownership, enable extra privileges, strip foreign deny ACEs or loosen protection to bypass an access failure. Close all handles on every outcome so an operator can rename/delete the tree immediately afterward.

## R5. Execution boundaries

Use native Windows/NTFS behavior, not path/size/mtime guesses. The caller excludes concurrent namespace/security mutation during an individual command; changes between separate plan/apply processes are in scope. Crash recovery, power-loss atomicity and concurrent writers during the write phase are not required. Test roots have concrete DACLs; their directory ancestry is ordinary and accessible, and ordinary tree objects are readable. The runner is elevated and supports creation of junctions, symlinks and hard links. Preserve existing offline SDK/project constraints.

The visible `tools/public_smoke.ps1` provides small runtime examples of both the original CLI and the plan/apply lifecycle, not the hidden acceptance suite. `run_smoke` compiles and executes these examples on fresh NTFS objects. `edit_file` replaces an exact source fragment and `write_file` can replace a source file. All models receive the same tools. New workflow code must be connected to the public CLI.

Public debugging examples: run_smoke reports expected CLI codes alongside actual NTFS ACL observations. It includes new descendants at two levels, stale managed InheritOnly flags, and both internal and external hard links. R4 applies in planning as well as direct/apply modes: an unsafe unprotected file must make --plan exit 4 without creating an approval. Use these observations to validate your implementation; the hidden acceptance suite is unavailable.
