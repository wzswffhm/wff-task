# 《RL0-1-数据生产规范 Guideline for 外部供应商（法律）》解析笔记

> 原文抽取见同目录 `原文抽取.txt`（10 页）。
> **组合使用要求**：本文件须与《外发版-评测题包交付规范（rewardkit）20260913》**组合使用**——本文件定义**出什么题、怎么设计打分项**，交付规范定义**怎么打包、怎么判分、怎么验收**。

## 1. 项目背景与使用范围

- 定义 RL 从 0 到 1 标注生产下数据的**规格、格式、质量标准与验收流程**。
- 适用对象：提供标注数据的所有数据生产流程。面向对象：供应商、高校、内外部专家、标注质检平台。
- **写给专家的职责**：作为对应办公场景的专家，根据自己的擅长领域选择合适难度的任务，给出
  ① 能对应办公场景、具备**真实业务价值**的任务描述；
  ② 恰当的**参考文件**；
  ③ 对应该任务的**参考答案**；
  ④ 一套能衡量任务做得好坏的**打分项**。
- **验收依据（专家自检口径）**：
  - ① 用打分项给自己提交的参考答案打分 → **正确率 > 0.85**；
  - ② 用 3 个模型执行该任务并用打分项打分 → **三模型平均正确率 < 0.7**（难度达标）。
  - ③ **人工质检**重点考察：题目真实性、参考答案合理性、打分项设计合理性、**是否 hack 等异常作弊**——一经发现**直接打回**。
- **格式要求**：供应商的题目需提供 **Harbor 格式**；高校根据能力酌情提供 Harbor 或非 Harbor 的原始文件。

- **三级标签目前为空，出题时须补足**；四级标签自行填写，描述细分场景。
- 题目分布均匀，**不接受 2 道以上（2 道本身可以）的题目属于同一个三级标签**。

## 3. 难度分级

按**三模型平均正确率**划分易、中、难。

| 级别 | 产量占比 | 平均正确率 | 备注（据 §8） |
|---|---|---|---|
| A1 易 | 20% | < 70% | 实际验收区间 0.6 ~ 0.7 |
| A2 中 | 60% | < 60% | 实际验收区间 0.5 ~ 0.6 |
| A3 难 | 20% | < 50% | 实际验收区间 < 0.5 |

**跑分口径（单条）**：Claude code 框架下跑 `gpt-5.6-sol`、`claude-opus-4-8`、`qwen3.8-max0902` 三个模型。
所有题目满分归一化为 1.0，**裁判模型为 `qwen3.7-plus`**，每种模型都跑 **1 次**求平均分：
- 均分需要 **< 0.7**；
- 且**至少有一个模型有得分**（避免全 0 的"死题"）。

**跑分产物及轨迹要求**：提交题目文件时，须**同步提供模型产物和跑分轨迹**，用于验证难度要求。

## 4. 三个核心组成

### 4.1 任务描述

- 自然语言描述**任务场景、需要用到的材料、交付物要求**。
- 包括任务说明、产出要求、硬约束（禁止项、文件名要求）——**必须用独立段落显式写出，不得隐藏在括号内**。

### 4.2 参考文件

- 完成该任务/作业所需的**真实输入**（如 CSV、PDF、合同、日志）。
- **该任务场景下真实的交付物是什么，就用什么源文件。**
- **必须为真实数据**；不得要求模型凭空猜测法规条款、政策口径、职责分工或统计数据。
- 数量没有限制，总大小在 20 GB 以内。

### 4.3 参考答案

- 由领域专家产出的标准答案，作为**打分项自检基准**。
- 与题目标注中规定的**交付物类型、文件名、数量严格一致**。
- 参考答案中的文件经过打分项判分后须满足 **`score_final ≥ 0.85`**；若 < 0.85 则不符合要求，**需修正**。

## 5. 打分项（本规范的评分设计部分）

**定义**：打分项 = 一个得分点/扣分点，即考察交付物——符合某一条在实际生产中被要求或有正向收益的 → 得分；符合某一条实际生产中应该杜绝或避免的 → 扣分。

> **注意**：**不能**在同一个打分角度上既写得分点又写失分点，造成双重得分或双重扣分。

### 5.1 任务描述 description（单条打分项要求）

| 要求 | 说明 |
|---|---|
| 原子性 | 每条描述一个独立、明确、可验证的评分点，仅检查一个方面（避免捆绑多个独立事实/多个可接受值） |
| 准确无歧义 | 表述完整、事实正确、依据可靠，使不同评分者能够形成一致理解 |
| 可独立判断 | 应包含作出判断所需的关键信息，不要求评分者额外推导、补充标准或二次判断<br>✗ 不推荐："收入实现了明显增长。" ✓ 推荐："收入同比增长了 65%。" |
| 来源合理 | 必须来自：① 项目描述中的明确要求；② 参考文件中的明确要求；③ 根据任务目标和使用场景可以合理推导出的隐含要求。**不能凭空增加"伪需求"** |
| 有明确判定锚点 | 禁止"语言流畅""结构清晰""内容专业"等空洞描述<br>✗ 不推荐："PPT 排版美观。" ✓ 推荐："单页正文不超过 150 字，文本无明显遮挡、重叠或溢出。" |
| 客观可验证 | 优先评价能直接核查的事实、数据、结构和结果；确需评价主观质量时必须转化为具体的可观察标准 |
| 粒度合理 | 既不把多个独立要求合并为一项，也不把完整动作拆成大量无实际意义的小项 |
| 打分对象 | 输出文件有多个时，在打分项中**明确给出本条的打分对象** |

**打分项之间的要求**：
- **互不重复、互不冲突**。例："公文是否专业、有条理且合规"应拆分为：文种选择是否正确 / 格式要素是否齐全（标题、主送机关、正文、落款、发文字号等）/ 请求事项是否明确、是否符合"一文一事"。
- **具有区分度**：正分项与负分项的判定边界应明确；`type` 为 gradient 的正分项要求能区分"部分满足"与"完全满足"。
- **整体覆盖完整**：所有打分项合起来覆盖任务主要目标与关键能力，从不同维度评价交付物质量，不遗漏关键要求。
- **权重体现重要性**：按对任务结果的影响程度设置不同 weight，避免机械地全部同权。
- **允许设置合理亮点项**：可评价项目要求之外、但基于常识会影响用户判断或交付质量的内容；应有明确价值和合理依据，不能无限扩展任务范围。
- **判断结果稳定（鲁棒性）**：同一套打分项由不同 Judge 或不同时间多次评分时结果应基本一致；波动较大时应进一步明确描述、判定边界和示例。

### 5.2 主客观类型 `criterion_type`

- `Objective` = 可度量、可验证，仅凭回答本身即可作出明确判定；
- `Subjective` = 需要打分员的判断与语境解读（语气/质量/风格，或对某理由、断言、示例是否成立的判断）。

### 5.3 显隐式类型 `criterion_necessity`

- `Explicit` = 在 prompt 中逐字明文给出的要求；
- `Implicit` = 没有明说但从语境中必然推导出的要求。

### 5.4 权重 weight

分值（正分表示奖励，负分表示扣分/惩罚）。**不接受恶意负分、故意增加题目难度/降低分数的行为。**
字段约束：**weight ∈ {+10、+7、+3、−3、−7、−10}**，不能取任何其他值。

| 级别 | 分数 | 含义 |
|---|---|---|
| Critically Important | +10 | 不满足就是"答错大题"，核心要素 |
| Important | +7 | 明显增色，但不一定是最低标准 |
| Slightly Important | +3 | 细节/锦上添花 |
| Slightly Detrimental | −3 | 小错误、小跑题 |
| Detrimental | −7 | 重要错误，但整体还能用 |
| Critically Detrimental | −10 | 致命错误，直接毁掉答案本身，一票否决项 |

### 5.5 类型 type

字段约束：`type ∈ {Binary, Gradient}`。

| Binary（二元判定） | Gradient（分档位给分，接受中间状态） |
|---|---|
| 答案要么满足、要么不满足；中间状态无意义 | 存在程度差异，且这种差异对最终质量有意义 |
| 主观但可明确 yes/no（如"是否有提及不确定性"） | 连续指标可以量化（数量、比例、偏离度） |

> 注：在 rewardkit 交付规范中，`Gradient` 对应 `rubrics.toml` 的 `type = "likert"`（points = 5）；
> `Binary` 对应 `type = "binary"`。

**五档 gradient 示例**：

```json
{
  "id": "R06",
  "description": "法律意见引用的核心法条应现行有效且与争点契合，越准确得分越高",
  "dimension": "内容质量-专业规范",
  "criterion_type": "Objective",
  "criterion_necessity": "Explicit",
  "type": "gradient",
  "weight": 7.0,
  "levels": {
    "1":    "全部核心法条现行有效、版本正确且与争点契合",
    "0.75": "核心法条有效，个别次要法条存在效力或适用瑕疵（不超过 1 处）",
    "0.5":  "核心法条有效，但存在 2-3 处效力或适用瑕疵",
    "0.25": "引用了已失效或明显不适用的法条，但主体结论未被推翻",
    "0":    "引用已失效法条或适用错误，直接支撑了错误结论"
  }
}
```

**二档 binary 示例**：

```json

  "description": "民事起诉状载明的诉讼请求金额与合同约定的违约金基数一致，均为人民币 120 万元。",
  "dimension": "内容质量-数值与计算准确性",
  "criterion_type": "Objective",
  "criterion_necessity": "Explicit",
```

### 5.6 评价维度 dimension

每条打分项需要有其所属评分维度（一级 + 二级，二级可为空）。维度根据任务要求**动态调整**，不同任务需要有区分度。

**不同维度的权重设置要求**：
- 内容质量、操作与交付安全应**总是较高 weight**；
- PPT 等设计类交付物：**视觉美感与格式规范**维度应较高 weight；
- 行业性比较突出的交付物：**专业规范**维度应较高 weight；
- 写作类交付物：**结构与组织**维度应较高 weight；
- 数值与计算要求较高的交付物（如金融场景）：**数值与计算准确性**维度应较高 weight。

| 一级维度 | 二级标签 | 主要检查什么 | 法律领域典型条目 |
|---|---|---|---|
| **指令遵循【必须】** | — | instruction 中显式要求的任务内容与交付约束是否被完整执行（范围限定、数量、命名、路径、格式、单位、精度、明确要求包含或禁止的内容）。**只检查 instruction 明确提出的要求** | 「结果文件名为 `lawsuit_memo.docx`」「存放在 output/」「金额以万元为单位保留两位小数」→ 拆成 3 条 |
| | 结论正确性 | 基于已有事实、数据、分析形成的最终判断、结论、推荐或决策是否正确，是否与证据一致 | 证据显示合同第 7 条已明确约定逾期违约金比例，最终结论应为支持违约金主张，而不能错误主张不承担违约责任 |
| | 数值与计算准确性 | 数值提取、公式计算、统计口径、单位换算、聚合方式、分母选择、时间范围、精度及容差 | 赔偿金额合计 = 各项分项之和（±0.01）；万元与元换算正确 |
| | 专业规范 | 是否符合任务所属行业/领域的专业知识、规则、标准和通行实践 | 法律分析使用**现行有效**的法律规则而非已失效规定；援引条文时**条、款、项定位准确**；**请求权基础与争议焦点匹配** |
| **内容质量【必须】** | 分析与论证质量 | 事实、数据、引用是否忠实于输入材料及可验证的客观事实，不无依据地编造、篡改或混淆信息；引用和来源是否真实可追溯；跨文件处理时是否正确区分主体、版本、时间、统计口径 | 「A 公司于 2016 年成立」能在工商档案材料中溯源；溯源不到即视为编造，违反事实性 |
| | 事实忠实性 | 同上 | 案例分析中引用的判例、案号与裁判要旨均可核对，不存在虚构案号或伪造裁判理由 |
| | 内容逻辑性与分析深度 | 分析到位、论证充分、有没有回答真问题、洞察深度。在指令遵循之外单独考察深度、逻辑、思想内涵。**论点有准确论据支撑** | 对争议焦点给出 ≥2 条有证据支撑的论证路径，而不是复述"存在争议" |
| | 结构与组织 | 信息架构和组织方式是否合理（章节/页面结构完整、内容层级清晰、顺序符合逻辑、信息分组合理、关键模块不缺失、文字/表格/图表放置合理） | 法律意见书按「事项概述—事实与证据—法律分析—结论与建议」形成清晰结构 |
| 操作与交付安全 | — | Agent 执行过程中是否安全处理用户已有文件和 workspace；不得误删、覆盖、破坏无关源文件，不得因编辑或格式转换造成数据、公式、页面或其他原有内容意外丢失 | 处理完成后案卷清单仍完整可打开；被覆盖或删除则命中扣分项 |
| 安全合规 | — | 产出内容及执行行为是否满足隐私、数据安全、版权、法律法规及业务合规要求 | **对外文书不得直接暴露输入材料中的身份证号、手机号等敏感个人信息** |
| 超预期贡献 | — | 其他要求都满足后进一步提升交付价值的部分 | 事实二次核对、产物兼容性与易用性、防呆设计、指出 instruction 本身的疏漏以及更完善的交付物 |
| 视觉美感 | — | 交付物是否足够美观（排版、配色等），**比较偏主观**。仅针对交付物有美观度要求的情况配置得分点，普通任务不建议包含 | 法律意见书的排版与层级是否清晰美观 |

### 5.7 打分项分布要求

- **领域锚点占比**：交付物内容质量维度（其下所有二级标签）锚点正分，**占全部正分的 30% 以上**——表示本题对专业性有很高要求，非简单指令遵循就可满分。
- **关键项占比**：每题**至少包含 2 条 Critically Important（+10）**评分项，模拟用户真实期望。
- **−10 分项**：仅用于重大专业错误、幻觉、业务安全、合规风险等真正影响答案可信度的情形，**不得滥用**。
- **一般来说，指令遵循、结论正确性、分析与论证质量与事实忠实性这些维度总是需要的**；行业性突出的交付物应覆盖专业规范维度；PPT 等设计类应覆盖视觉美感与格式规范维度；写作类应覆盖结构与组织维度；数值与计算要求较高的应覆盖数值与计算准确性维度。

## 7. 得分计算

```
Score = ( Σ_{i∈P} s_i·w_i  +  Σ_{j∈N} h_j·w_j ) / Σ_{i∈P} w_i
```

- `w_i > 0 (i∈P)`，P = 正打分项；`w_j < 0 (j∈N)`，N = 负打分项。
- `s_正i` = 1（binary 正打分项命中）；或 {0, 0.25, 0.5, 0.75, 1}（gradient 正打分项实际档位）。
- `h_负j` = 1（binary 负打分项命中）；或 {0, 0.25, 0.5, 0.75, 1}（gradient 负打分项实际档位）。
- 三模型平均分 = (score1 + score2 + score3) / 3。

> 与 rewardkit 交付规范的池化公式一致（负向不进分母）。

- AI 质检题目质量
- 人工质检题目质量 SOP
