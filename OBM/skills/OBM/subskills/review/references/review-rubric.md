# 内容判断标准（v6）

规则来自同目录《OBM Source 收集说明书》及用户本次指定的相关度阈值。每次审查
记录说明书 SHA-256。不同证据冲突时呈现冲突并给出补查动作，不能取最有利的说法。
程序负责定位/比对/约束结果；Agent 负责理解题面、源数据、任务增量和证据含义。

## 顺序与结果

先审 Source 复用，确认任务特有内容复用为 H02，拒收并停止该题。
其余依次做相关度、公开历史、内容质量。结论按 REJECT > FAIL > REVIEW > ACCEPT 合并。
FAIL 与旧表“需重做”对应；REVIEW 既包含相关度 warning，也包含需补证据，不是通过。
各项已知结果独立保留；一个明确不通过不会因其他项缺证据而降成待定。

## 垂直领域相关度

只比较 proposal.C_agent_task 与真实 related_question 题面：
业务/科学对象是什么、问题属于哪类专业活动、使用哪些领域规则、产物服务什么目标。
不要因为都用 Python、JSON、命令行、Docker 就认为领域相同。

| 分数区间 | 判断锚点 |
|---|---|
| 0–19 | 领域对象和问题目的基本无关，仅共享通用编程/数据处理形式 |
| 20–49 | 邻近大领域或部分业务对象相似，但主要专业问题与规则明显不同 |
| 50–79 | 主要专业问题相关，关键领域知识有实质交集，仍有明显场景/范围差异 |
| 80–100 | 高度相同的领域对象、目的和专业约束；100 只表示领域等价，不代表题目可复制 |

分数是有证据的评审判断，不是统计置信度。解释为什么落在此区间，不伪装为精密测量。
必须引用 C 与对照题各至少一处原文，列相同点与差异；仅引用相同文件格式不足以评分。

## 核心能力相关度

先从真实题面提取 2–5 个决定成败的能力，并区分核心机制与附带工程步骤。
再看 C 是否确实要求这些能力：黑盒行为推断、程序复刻、约束求解、跨模块调试、
性能优化、科学分析、训练评估等。A/B 和 D 可用于查矛盾，但不替 C 增添不存在的要求。

| 分数区间 | 判断锚点 |
|---|---|
| 0–19 | 缺失对照题的主要能力，仅共享工具操作或一般代码编写 |
| 20–49 | 共享一部分次要能力/输出流程，但核心难点不成立或明显被简化 |
| 50–79 | 至少一个主导能力及相应约束实质相同，但能力组合、难度或覆盖不同 |
| 80–100 | 主导能力组合与决定成败的机制高度相关，能解释迁移价值 |

两个分数互不平均。19.9 不通过；20 和 49.9 是 REVIEW；50 通过该维度。
引用不足/真实题面拿不到时 null + REVIEW，不得按任务名猜。
高相关度不抵消改名改数、内容复制或现成公开答案。

## Source 复用判定

查看整个交付 Source，包括目录、压缩包、数据文件、脚本、初始化内容和答案。
对照 related task 及本次其他 Benchmark 语料。确认复用至少给：

1. 交付文件路径及哈希、Benchmark task 文件路径及哈希。
2. 相同数据记录/代码/答案片段（部分复用标识具体位置）。
3. 为什么这是评测任务特有内容，排除共同公共上游、许可证、通用空文件或来源引用。

命中 H02 为 REJECT，即使专家声称其他部分原创也停止本题。扫描 candidate 不是定罪。
只有 URL、标题、任务名相同：`provenance_only` 或无候选，不当作 Hack。
共同 jq 源码等可为 `common_upstream`，但要核实来历，不凭文件名认定。
改了数字/实体名称仍保留同一题结构、答案机制可触发 R04，需要语义证据，不能只靠哈希。
二进制、远程下载或未读的大文件用相应工具补查并保存证据；没有能力检查则 REVIEW。

## A 的公开 commit / PR 来源

所有造题方式只要 A 提出仓库增量都检查；不能仅因 type=B/C 免查。
先列“来源已经有的功能”和“A 新增功能”；然后检索后一组特征，读相应 diff 和 PR。
检索至少覆盖功能语义、接口/模块、关键约束/边界；中英文同义词按仓库语言选用。
记录仓库、baseline（若有）、refs/shallow 状态、查询、分页/数量限制、检索时间。
PR 的标题相似不够，commit message 命中也不够；应能指出新增行为已由某个公开变更实现。

- `base_functionality`：只是使用公开 baseline，增量不同，不能定罪。
- `unrelated`：词命中但目标/行为不同，解释差异。
- `unresolved`：可能匹配但 diff/时间/语义证据不足，REVIEW。
- `derived_from_public_change`：公开不可变 SHA + URL + 与 A/B 对应的实际变更证据，R02 拒收。

时间未知时只能表述“审查时已存在公开实现”，不能声称已证明专家抄袭或提交前公开。
声称提交前公开，须有提交时间与公开事件时间的外部证据；Git commit author/committer date
可重写，不独立证明首次公开时间。对已公开答案同样可按当前质量要求拒收，但说明准确。
未搜索的仓库、空查询、截断、API 限流或私有历史不可访问均 REVIEW。
“本次检索未发现相同增量”可在充分限定覆盖范围后作为 PASS；绝不宣称全球绝对原创。
没有任何 Git 来源时，引用 proposal_sources 与资产事实解释 NOT_APPLICABLE；
这不豁免原创任务和现成 solution 检查。

## 剩余初验内容

| 检查键 | 必须理解和记录的内容 |
|---|---|
| source_assets | 用了什么资产、在哪里、是否可读/可获得、是否支持任务。A 需要真实仓库基线与新增行为；B 需可观察参考与原创目标/约束/工作负载/指标；C 需真实工作资产、环境（说明书要求 Docker）和复现路径。不能把未知可用性写成 PASS |
| feasibility | C 与 B/Verify 有无自相矛盾、资源/权限/网络限制是否允许完成；至少一条可信实现路线；检查是否有合法简单解，不把未运行误写为“不可能解” |
| original_task | 任务的新要求/真实用途/训练价值是什么，是否只改原题名字数字，或现成搜索可直接得到完整答案 |
| verifier | 以什么为准、怎么判完成、为什么测这些、哪些错误应失败、哪些不同合法解应通过、独立 oracle 如何来、专家说明是否可信。校验必须行为级、不可只比日志/文件存在/固定答案；性能目标有基线、单位、阈值；隐藏样本不引入未公开业务规则 |
| skill_alignment | D 每个难点对应哪条实际专家经验、为什么有用；内容应具体且正确，不能只是通用 coding 流程；不声称静态阅读已证明增益 |
| skill_leakage | 经验是否从问题机制推导，而非依赖 hidden test ID、固定答案、verifier 私有数据或通过测试的捷径；共享公开算法原则本身不等于泄漏 |

所有明确可修复缺陷为 FAIL，材料不足为 REVIEW，直接证据满足说明书拒收条款则 REJECT。
R01 矛盾/不可能解需要具体反例或逻辑证明；静态未知可解性不是 R01。
R03 patch 高度相似、R05 verifier 复制 tests、R07 Skill 泄漏、R08 公开完整 solution
必须附具体两侧证据。不要从写作风格断言 AI 生成或专家不理解，需要真实外部证据。
说明书“Skill 只是通用 coding 流程，未起到帮助”中的实际无帮助需 rollout 实证；
初验通用 Skill 可先判 skill_alignment FAIL。

## 后置实证

初验不要求已经证明 Seed 失败/超长或 Skill 增益。明确做后续 rollout 时核对：
Seed 无 Skill 不能做对或成功但 >100 轮；with-skill 成功，且实现失败转成功，
或相对无 Skill 成功基线，轮次减少 ≥30% 且时长减少 ≥30%。
任务、模型、环境、输入与 verifier 一致，容器/工作区/会话/缓存隔离，保留真实轨迹。
基础设施失败不能当模型能力失败，轮次/时长不可复算则 REVIEW。
