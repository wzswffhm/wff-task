# marshmallow 结构化 diff 专家经验

本任务要在 marshmallow 的 `Schema` 上新增一个公开方法 `document_diff`，对两份文档做字段级比较，返回有序的 `{op, path, left, right}` 记录。难点不在于“写个比较函数”，而在于让比较**绑定 schema 的声明结构**，而不是退化成脱离类型的通用字典比较。下面按四条真正需要推理的难点展开。

## 共享方法

先确立一个总原则：**比较的权威来源是 `schema.fields`，不是输入字典**。每一次向下走一层，都用“当前这一层该用什么 schema 决定下一步”来指导递归。也就是说，遇到 `Nested` 就切换到它的子 `Schema` 继续按字段比较；遇到 `List` 就先按位置对齐，再问“这个列表元素本身是不是又一层结构”。路径只是这条递归路线的字符串投影：嵌套字段用点号连接，列表或 many 元素用方括号下标。

凡是走到“某字段只在一侧出现”或“两侧元素个数不同”的分支，都要先想清楚它应该成为 `add`/`remove`，还是被误判成 `change`。凡是遇到“schema 不认识的键”，都要先想清楚它默认应不应该出现在结果里。

---

## 难点一：把 diff 建成 schema 驱动而非值驱动

### 契约模型
需要持久化（或至少稳定推导）的事实只有一件：`schema.fields` 的**声明顺序**和它每个字段的**类型**。顺序决定输出记录的顺序，类型决定下一步是标量比较还是结构递归。输入字典的插入顺序、是否含有 schema 不知道的键，都不应进入主路径。

### 冲突关系
最大的冲突是“按声明遍历”与“按输入遍历”的取向之争。若直接遍历输入字典，会得到随输入变化的顺序、会漏掉只在一侧声明但为空的字段、会把未知键当成真实差异。必须明确：字段集合与顺序来自 schema，输入只提供值。

### 决策方法
逐字段处理时，先取 `schema.fields` 中声明的字段名，再去左右文档里取对应值。某个字段在 schema 里有、但文档里没有，就按“单侧缺失”处理（见难点三），而不是跳过。判断“下一步怎么比”只看字段类型：`Nested` 进递归，普通标量做相等比较，`List` 进位置对齐。

### 反例历史
一个常见错误是维护一个“两边同时遍历的键集合”，结果顺序跟着第一个文档走，第二个文档多出来的字段被遗漏，或者未知键混进来。另一个错误是把整个文档当成无类型的值一次性比较，于是 `Nested` 内部的子字段被拍平、路径丢失。

### 验证思路
构造两份字段顺序不一致但内容一致的文档，确认返回空列表；构造 schema 声明了但文档缺省的字段，确认它被当作缺失而非忽略；构造含未知键的文档，确认默认不出现在结果里。关键是看“结果的字段顺序是否等于 schema 声明顺序”。

## 难点二：正确处理 Nested(many=True)

### 契约模型
`Nested(many=True)` 的每一侧都是一个**元素列表**，每个元素都是一份受同一子 schema 约束的文档。可推导的事实是：元素之间按下标对应，单个元素内部仍由子 schema 的字段集合与顺序主导。

### 冲突关系
这里最容易和“单值 Nested”混淆。单值 Nested 比较的是“一个对象对另一个对象”，路径追加子字段名即可；`many=True` 比较的是“列表对列表”，必须先在元素层级做对齐，再对每个元素做对象级比较。把 many 的元素当成单值去取值，会拿整型下标去查一份并不是字典的东西，路径与值都会错位。

### 决策方法
两侧元素个数相同时，按下标 `i` 一一对应，对每个元素用子 schema 递归比较，路径前缀为 `字段名[i]`。某一侧多出元素时，多出来的下标成为 `add` 或 `remove`。递归时务必使用子 schema 自己的 `fields`，而不是把元素当原始值处理。

### 反例历史
典型故障是：`many=True` 的元素被当作“字段值”，于是对整型下标做字典取值触发 `KeyError`；或者元素个数不同却被逐字段比较，把“多出一个元素”误报成“某个字段 change”。

### 验证思路
构造左右元素个数相同的列表，确认内部子字段差异出现在 `字段名[i].子字段` 路径上；构造右侧多一个元素的列表，确认多出来的下标是 `add`；构造一个子字段在元素间不同的例子，确认路径精确指向 `字段名[i].子字段` 而不是笼统地报整个列表变化。

## 难点三：为缺失键与列表位置定义无歧义的 add/remove/change

### 契约模型
三类记录的语义必须固定：`change` 表示同名字段两侧都有且不等；`add` 表示只出现在右侧（左侧视角为 `None`）；`remove` 表示只出现在左侧（右侧视角为 `None`）。相同文档必须产出空列表——这条是契约的零值不变式。

### 冲突关系
冲突集中在“列表按位置比较”与“列表当作集合”之间。按位置比较时，元素个数不同必须产生 `add`/`remove`，而不能把错位后的元素当成 `change`。另一个冲突是“字段只在单侧出现”到底算 `add`/`remove` 还是算 `change`：只有当两侧都有该字段且不等时才是 `change`。

### 决策方法
先处理字段存在性：两侧都有则比较值，不等即 `change`；只在右侧有则 `add`，只在左侧有则 `remove`。再处理 `List`：逐个下标比较，某一下标只在单侧存在时就成为该下标的 `add`/`remove`，两侧都有则比较该位置上的值（若值是结构则继续递归）。路径格式全程统一：嵌套用点号，位置用 `[i]`，二者可叠加。

### 反例历史
一个隐蔽错误是列表元素个数不同却按最短长度比较，把“缺失的元素”吞掉，只报了前几个；另一个是把左侧缺失的字段记成 `change` 并带上一个假“左侧值”。

### 验证思路
构造一个列表右侧比左侧多两个元素的例子，确认这两个新增下标都出现为 `add`；构造同字段只在右侧出现的例子，确认是 `add` 且左侧值为 `None`；构造完全相同的文档，确认结果为空列表。重点检查路径里 `[i]` 的下标是否和真实位置一致。

## 难点四：守住选项契约与既有 API

### 契约模型
`include_unknown` 与 `ignore_fields` 只是**本次比较的视图开关**，不应写进 schema 的任何持久状态。`include_unknown=True` 才把文档里 schema 不认识的键纳入比较；`ignore_fields` 里的字段名在整个比较中跳过。两者都不影响 `dump`/`load`/`validate`。

### 冲突关系
冲突来自“视图开关”与“schema 状态”的边界。`include_unknown` 如果改了 schema 的字段集合或缓存，就会污染后续调用；`ignore_fields` 如果只跳过顶层而漏掉嵌套层，就会在递归里重新出现。另一个边界是新增方法必须是纯函数：不能改 schema、不能改文档。

### 决策方法
把“是否比较未知键”和“跳过哪些字段”都作为参数在递归过程中向下传递，而不是改任何全局或实例状态。跳过字段时，要在每一层递归入口都尊重同一个忽略集合，包括嵌套层。最后明确：`dump`/`load`/`validate` 的行为、签名与异常都不在本任务改动范围内，新增方法不应引入新的公开类型或破坏既有 API。

### 反例历史
曾出现过 `include_unknown` 被记成 schema 的永久属性，导致下一次不带该选项的调用仍然比较未知键；也出现过 `ignore_fields` 只过滤了顶层，嵌套里的同名字段又被比较出来。

### 验证思路
构造含未知键的文档，先确认默认不出现、再确认 `include_unknown=True` 时出现；构造在嵌套层也存在的忽略字段，确认它在顶层与嵌套层都被跳过；最后单独跑序列化/反序列化/校验的既有用例，确认它们没有回归。

---

## 收尾检查

实现完成后，至少确认四件事：结果是按 `schema.fields` 声明顺序输出的；`Nested`（单值与 `many=True`）都走子 schema 递归且路径正确；缺失键、列表位置与忽略字段的语义无歧义；`dump`/`load`/`validate` 的既有行为完全不变。只要这四点守住，新增行为就能被正确观测，且不会把原题改坏。
