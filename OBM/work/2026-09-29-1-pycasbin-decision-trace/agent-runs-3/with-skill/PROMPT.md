## 题目

Task overview:
给 `Casbin` 授权引擎补上一组公开的「决策可解释 + 变更影响分析」入口。一个是 `enforce_traced(*rvals)`：它在给出布尔结论的同时，交代这次求值到底匹配了哪些策略规则、其中哪一条规则让引擎停了下来，以及引擎当时是否被禁用。另一个是 `would_change(*rvals, mutations=...)`：它在一份一次性沙箱副本上试算「增删若干条策略规则或角色链接之后，同一个请求的结论会不会翻转」，并返回变更前后的结论。两块能力都要在允许覆盖、拒绝覆盖、允许且拒绝、优先级、主体优先级这五种策略效果下给出正确结果，还要覆盖角色多级继承、域隔离、条件角色管理器与 `EnforceContext` 打头这些真实用法，并且不得改变 `enforce()` 的任何既有行为。
改动集中在新增模块 `casbin/trace.py`，并从包顶层导出，同时在 `CoreEnforcer` 上挂两个方法，这样 `Enforcer`、`SyncedEnforcer` 等子类自动获得能力。

公开命名是契约的一部分，实现必须使用下列名称与字段顺序，不得自创替代名。模块 `casbin/trace.py` 定义四个不可变公开类型，并经 `casbin/__init__.py` 从包顶层导出：`PolicyMatch(ptype, rule, index, effect)` 表示一条匹配记录，四个字段按此顺序；`TraceResult(allowed, matched, decisive, disabled)` 是追踪结果，四个字段按此顺序，其中 `matched` 与 `decisive` 的元素都是 `PolicyMatch`；`PolicyMutation(op, sec, ptype, rule)` 描述一条策略或角色变更，四个字段按此顺序，`op` 只接受 `add` 与 `remove`，其他取值抛 `ValueError`；`ChangeImpact(changed, before, after)` 是变更影响结果，三个字段按此顺序，`changed` 是布尔，`before` 与 `after` 是变更前后的结论。

第一块是决策追踪。入口 `enforce_traced(self, *rvals)`，参数与 `enforce()` 完全同构：可以带一个 `EnforceContext` 打头，其后是请求值。它返回一个不可变结果对象，含四个字段。`allowed` 是布尔结论，必须恒等于同参数下 `enforce()` 的返回值。`matched` 是按求值顺序排列的匹配记录元组，每条记录含四个字段：规则类型 `ptype`（例如 `p` 或 `p2`，带 `EnforceContext` 时取上下文里的类型）、规则内容 `rule`、该规则在对应策略列表中的下标 `index`，以及这条规则的效果取值 `effect`。求值顺序与上游 `enforce_ex` 的循环逐步一致，也就是按策略载入后的优先级顺序逐条取值。`decisive` 是引擎因它而中断的那条规则，长度只能是零或一。`disabled` 表示引擎是否被 `enable_enforce(False)` 关掉。

第二块是变更影响分析。入口 `would_change(self, *rvals, mutations)`，`mutations` 可以是一条变更描述，也可以是一串按顺序施加的变更描述，每条描述由操作、区段、规则类型和规则内容四项组成，操作取 `add` 或 `remove`，区段取 `p` 或 `g`。它返回变更前结论、变更后结论、以及两者是否不同三个值。语义要求：`add` 落在策略区段时，与既有 `add_policy` 行为逐字一致，规则已存在则不动作，否则追加，并且在该规则类型带优先级字段时按上游同样的规则做优先级插入；`remove` 落在策略区段时与 `remove_policy` 一致，规则不存在则不动作；落在角色区段时，必须与 `add_grouping_policy` 和 `remove_grouping_policy` 的全部副作用一致，也就是不仅改策略，还要真的为角色管理器增量建立或删除角色链接，否则后续角色继承的求值不会变。规则比较按元素逐一相等。变更序列为空时前后结论必然相同。整个试算过程只回答「会不会变」，不落盘、不通知监听者、不调用适配器。

非侵入性要求：`enforce_traced` 与 `would_change` 都不得修改引擎自身状态。调用前后，`enforce()` 的结论、`get_policy()` 与 `get_grouping_policy()` 的内容与顺序、`get_roles_for_user` 与 `get_users_for_role` 与 `has_role_for_user` 的结果、域模型下的 `get_roles_for_user_in_domain` 结果，以及条件角色管理器上已注册的链接条件，都必须与调用前逐字相同。

退化情形也要定义清楚：策略列表为空时，上游会用空值求值一次匹配式，这个效果来自引擎而非任何一条规则，所以追踪结果不能凭空造出规则；匹配式引用了不存在的策略类型、或请求值个数不符时，抛与 `enforce()` 相同的异常，不做包装；匹配式用 `eval()` 且策略为空时，原样透传上游的 `RuntimeError`。

在 `casbin` 这个 `Python` 授权库里实现两组新的公开能力，并保证既有行为不变。

新增模块 `casbin/trace.py`，并在包顶层 `casbin/__init__.py` 导出四个公开类型，名称与字段顺序如下，不得自创替代名：
- `PolicyMatch(ptype, rule, index, effect)`：一条匹配记录。
- `TraceResult(allowed, matched, decisive, disabled)`：追踪结果；`matched` 与 `decisive` 的元素都是 `PolicyMatch`。
- `PolicyMutation(op, sec, ptype, rule)`：一条变更；`op` 只接受 `add` 与 `remove`，其他取值抛 `ValueError`。
- `ChangeImpact(changed, before, after)`：变更影响结果；`changed` 是布尔，`before` 与 `after` 是变更前后的结论。
同时给 `CoreEnforcer` 增加两个方法，使所有具体引擎子类都能用。

第一部分：`enforce_traced(*rvals)`。参数与 `enforce()` 完全同构，可选的 `EnforceContext` 打头，其后是请求值。返回一个结果对象，包含四个字段：
1) `allowed`：布尔结论，必须恒等于同参数下 `enforce()` 的返回值。
2) `matched`：按求值顺序排列的匹配记录序列。每条记录含规则类型、规则内容、该规则在其策略列表中的下标、以及该规则的效果取值。只有「被求值且匹配式为真」的规则才计入；最近不匹配的规则不计入。
3) `decisive`：让引擎停下来的那条规则，长度为零或一。
4) `disabled`：引擎是否处于 `enforce` 被禁用状态；禁用时结论恒为放行，`matched` 与 `decisive` 均为空。

效果取值 `effect` 的规则：策略定义里存在该规则类型的效果字段时取其值，取值等于 `allow` 时记作允许，等于 `deny` 时记作拒绝，其余任何取值记作不确定（`indeterminate`）；策略定义里没有该规则类型的效果字段时，一律记作允许。效果为不确定的匹配规则不触发中断，也不影响最终结论。

求值与中断必须与上游 `enforce_ex` 的循环一致，而四种策略效果族的中断条件不相同：允许覆盖族（`some(where (p_eft == allow))`）在第一条匹配且效果为允许的规则处停下，首条匹配的拒绝规则只记入 `matched`，不中断；拒绝覆盖族（`!some(where (p_eft == deny))`）与允许且拒绝族（`some(where (p_eft == allow)) && !some(where (p_eft == deny))`）都在第一条匹配且效果为拒绝的规则处停下；优先级族与主体优先级族在第一条匹配且效果确定的规则处停下。`decisive` 就是中断点那条规则；如果引擎从未因效果中断，`decisive` 为空。由此可推出：拒绝覆盖与允许且拒绝两种效果下，当结论是放行时 `decisive` 必须为空；而优先级与主体优先级下 `decisive` 无论结论如何都非空。

第二部分：`would_change(*rvals, mutations)`。把给出的变更按顺序施加到引擎的一次性沙箱副本上重新求值，返回一个 `ChangeImpact`，其 `changed` 属性为布尔、`before` 与 `after` 属性分别为变更前与变更后的结论。`mutations` 既可以是单个 `PolicyMutation` 对象，也可以是它们的序列，序列按给定顺序逐条施加。变更由操作、区段、规则类型、规则内容四项描述：
1) 策略区段新增：等价于既有的新增策略接口，规则已存在则无动作，否则追加；若该规则类型带优先级字段，按上游同样的方式做优先级插入。
2) 策略区段删除：等价于既有的删除策略接口，规则不存在则无动作。
3) 角色区段新增与删除：必须等价于既有的角色策略接口的全部副作用，即同时维护角色管理器里的角色链接；只改策略列表而不更新角色链接的实现，会导致后续角色继承求值不随之变化。
规则比较按元素逐一相等；变更序列为空时前后结论必然相同。

约束：
- `enforce_traced` 与 `would_change` 都不得修改引擎自身状态。调用前后，既有结论、策略列表与角色策略列表的内容和顺序、用户的角色集合、角色对应的用户集合、域内的角色集合，以及条件角色管理器上注册过的链接条件函数，全部必须逐字不变。
- 不得改变 `enforce()`、`enforce_ex()`、策略管理与角色管理接口的任何既有行为，既有测试必须继续通过。
- 策略列表为空、匹配式引用不存在的策略类型、请求值个数不符、匹配式使用 `eval()` 且策略为空这些情形，要与 `enforce()` 给出相同的返回值或相同的异常。
- 所有新增内容必须能从包顶层导入，且不需要任何新增第三方依赖。

Task difficulties:
- 四种策略效果族的中断条件并不相同。允许覆盖要等到第一条匹配且效果为 `allow` 的规则才停，首条匹配的 `deny` 不会让它停；拒绝覆盖与允许且拒绝都在第一条匹配且效果为 `deny` 的规则上停；优先级与主体优先级在第一条匹配且效果确定的规则上停。把「引擎停下来了」简单等同成「第一条匹配的规则」，在允许覆盖下会直接算错。
- `matched` 的边界是「被求值且匹配式为真」，不是「一路记到中断点为止」。中断点那条规则本身要计入，它之后没被求值的规则不能计入，被求值但匹配式为假的规则也不能计入。这三个集合互不相同，混用会同时污染 `matched` 和 `decisive`。
- `decisive` 的含义随效果族变化。拒绝覆盖与允许且拒绝两种效果下，当结论是放行时 `decisive` 必须为空，因为放行是因为没找到 `deny`，没有哪条规则该为它负责；而优先级与主体优先级下 `decisive` 无论结论如何都非空。要按效果族分别定义，不能用一个统一规则糊过去。
- 效果取值的退化分支必须与上游一致。策略定义里没有该规则类型的效果字段时一律算允许；有效果字段但取值既不是允许也不是拒绝时，算不确定（`indeterminate`），并且既不触发中断也不影响结论。漏掉这两个分支会让匹配矩阵在边界组合上整体错位。
- 沙箱隔离是这块最容易踩的坑。上游 `Assertion` 的深拷贝是刻意按引用共享角色管理器的，所以直接深拷贝整张模型并不会隔离角色图。一旦按这条路实现，对角色区段的试算变更会污染真实引擎的角色继承结果，而这类污染只在角色相关用例上暴露，普通策略用例完全看不出来。
- 条件角色管理器上注册的链接条件必须活到沙箱里。这类模型（例如角色定义带参数形式）的角色关系靠注册进去的函数判定，一旦沙箱重建角色管理器却丢掉这些函数，试算结论就会与实际重新求值不一致。任何走文本往返序列化来复制模型的实现都会在这里失败。
- 空策略路径不归属任何规则。上游在策略列表为空时会用空值求值一次匹配式，这个效果来自引擎本身而不是某条规则，所以追踪结果里不能凭空造出一条规则，而结论仍要按上游的效果语义给出。
- 一致性不变量覆盖整个矩阵。无论策略效果族、角色层级深度、域隔离、`EnforceContext` 打头、禁用引擎怎么组合，`allowed` 都必须与同参数下 `enforce()` 完全相同，`enforce_traced` 也不能改变引擎自身的策略、角色与既有结论。这条不变量必须在每一种组合下单独验证，不能靠抽样。

# 授权决策追踪与变更影响分析 · 经验手册

这套东西要解决两个问题：一次放行或拒绝到底是哪几条规则和角色链接参与决定的，以及把某条规则删掉或加上之后，同一个请求的结论会不会翻过来。我会先花时间把引擎现有的求值循环从头读完，重点看它在什么条件下提前停下。大部分坑都在这个「什么时候停」上。

## 先读求值循环，把「什么时候停」搞清楚

引擎停下来不是看规则匹不匹配，而是看当前已经累积出来的效果。四种效果族停的条件不一样：

- 允许覆盖这一族要等到第一条「匹配且效果是 `allow`」的规则才停。首条匹配的 `deny` 不会让它停，那条规则只会被记下来，循环继续往下走。
- 拒绝覆盖和允许且拒绝这两族，都在第一条「匹配且效果是 `deny`」的规则上停。
- 优先级和主体优先级这两族，在第一条「匹配且效果确定」的规则上停。

我见过最常见的错，就是把它当成「第一条匹配的规则」。这么写的话，在允许覆盖下会少记好几条规则，后面所有断言跟着错。动笔之前先在纸上把一组策略的求值顺序推一遍，比写完再调快得多。

## 该记哪些规则：三个集合别混

要记的是「被求值过、并且匹配式为真」的规则。它不等于「一路记到停下来为止」，也不等于「所有匹配的规则」。三个点要盯住：

1. 中断点那条规则本身要算进去。
2. 中断点之后没被求值的规则不能算。
3. 被求值过但匹配式为假的规则也不能算。

这三个集合互不相同，混用会同时污染「参与了哪些规则」和「哪条规则决定了结论」两个输出。

## 决定结论的那条规则要分效果族定

这个输出的含义不是固定的，它跟着效果族走：

- 拒绝覆盖和允许且拒绝这两族，当结论是放行的时候，它必须是空的。放行是因为压根没找到 `deny`，没有哪条规则该为它负责。
- 优先级和主体优先级这两族不一样，不管结论是什么，它都非空。

如果你用一个统一规则去定义它，一定会在这两族上错一半。我会给这两族单独写断言：前两族在放行时要求为空，后两族要求非空。

## 效果取值有两条退化路径，别漏

策略定义里有这个规则类型的效果字段，就取它的值：等于 `allow` 时记作允许，等于 `deny` 时记作拒绝，其它任何取值都算不确定。策略定义里没有这个字段，一律算允许。不确定这种取值既不触发中断，也不影响最终结论。

这两条分支看着不起眼，漏了会让整个匹配矩阵在边界组合上错位，而且错得很隐蔽——只有那些特意构造的策略才会踩到。

## 试算的沙箱隔离：最容易翻车的地方

想回答「改几条策略会不会翻」，最自然的想法是深拷贝一份模型上去改。我一开始也是这么想的，但这里有个坑：上游那个断言类型的深拷贝是刻意按引用共享角色管理器的，所以深拷贝整张模型并没有隔离角色图。

后果是：你改了沙箱里的角色链接，真引擎的角色继承也跟着变了。而且这种污染只在角色相关的用例上暴露，跑普通策略用例一点都看不出来，很容易以为已经做对了。

我的做法是自己造一份独立的角色管理器，再挂到沙箱模型上，而不是指望深拷贝。改完之后逐项比一遍，下面这些必须和调用前逐字一样：

- 既有入口的结论
- 策略列表和角色策略列表的内容与顺序
- 用户的角色集合、角色对应的用户集合
- 域模型下的域内角色集合

## 条件角色管理器上注册的函数要活下来

有些模型的角色定义是带参数的，角色关系不靠策略行本身，而靠注册进去的函数判定。这类函数必须在沙箱里还在，否则试算出来的结论和「真的改完再算」对不上。

特别提醒一句：不要用文本序列化再读回来的方式复制模型，那样函数会直接丢掉。而且这类问题只在参数化角色模型的用例上出现，用普通模型测是测不出来的。

## 角色区段增删要连着角色链接一起做

只改策略列表是不够的。角色区段的新增和删除，必须把角色管理器里的链接也增量建好或删掉。不改链接的话，改完策略再求值时角色继承不会变，试算就会说「没影响」，而实际上是有影响的。

试算的意义就是提前知道会不会变，这里错了整个功能就没价值了。我会专门构造一条「删掉一层角色链接之后某个请求从放行变拒绝」的用例来盯住它。

## 空策略是单独的路径

策略列表为空的时候，上游会拿空值去求值一次匹配式。这个效果是引擎给的，不属于任何一条规则，所以别为了让输出看起来完整就凭空造一条规则出来。结论还是按上游的效果语义给。

## 变更影响分析要回答什么

变更影响分析只回答一个问题：结论会不会变。所以它要给出变更前的结论、变更后的结论、以及两者是否不同这三个值。

有几条底线：

- 整个过程不改真实引擎，不落盘，不通知监听者，不调用适配器。
- 规则比较按元素逐一相等，别用字符串拼起来再比。
- 变更序列为空的时候，前后结论必然相同，不能报错也不能给个含糊的结果。
- 角色区段的变更同样要把角色链接带上（见前面那一节）。

## 把公开命名当成契约本身

题目会点名要导出的类型、字段顺序、字段名和允许的取值。我吃过亏之后固定了一个习惯：动笔前先把题面里出现的每个公开名字抄成一张表——类型叫什么、有哪几个字段、按什么顺序、哪些取值合法——然后照着表写代码。

不要自己另起一套名字，哪怕语义完全等价也不行。判定方看的是题面点名的那些名字：返回对象的属性名、构造参数的顺序、非法取值该抛什么异常，都按题面来。实现写得再对，名字对不上也算没完成。反过来，名字照抄了，语义再按前面几节做，就不会有意外。

## 我会怎么自查

写完先跑一遍效果族的全组合，逐个核对停下来的是哪条规则、区间里记了哪些规则。再单独跑拒绝覆盖和允许且拒绝的放行用例，确认决定规则为空。然后跑角色继承和域隔离，确认没有重复规则；角色用例至少要三层继承，间接依赖的错都是在更深的地方才露出来。接着跑引擎被禁用、以及带上下文打头的用例。最后做一次「追踪调用前后引擎状态逐字相同」的对比。

手边最好一直放一组对照：先记下既有布尔入口的结论，再调追踪入口，两者必须永远一致。这条不变量覆盖全部组合，别靠抽样。
